## 1. 실행 창 — 05:38 은 성립하는가

### 시간값이 사는 곳을 전수 추적했다

```
config/settings.py            DOC_WORKER_START_TIME "02:00"   DOC_WORKER_END_TIME "04:00"
register_scheduler_tasks.ps1  PriorityRefresh 01:50 / DocWorker 02:00 / DailyCrawl 06:00
                              ExecutionTimeLimit 4시간
```

★ **`DOC_WORKER_START_TIME` 은 제품 코드가 한 줄도 쓰지 않는다.** 워커가 읽는 것은
`DOC_WORKER_END_TIME` 뿐이고, 실제 시작은 스케줄러 트리거가 정한다. 그래서 이 상수는
"창 길이 계산의 근거"로만 존재하고, PS1 과 어긋나면 산술 전체가 조용히 틀어진다
(그 관계는 Sprint 204 가 이미 잠갔다).

### 후보값을 **실제 가드에 태워** 판정했다

`config` 를 잠깐 바꿔 검사를 돌리고 되돌렸다(파일 바이트 동일 확인).

```
종료 04:00 (창 2.00h)   통과
종료 05:00 (창 3.00h)   통과
종료 05:38 (창 3.63h)   **통과**   <- 요청받은 값
종료 05:55 (창 3.92h)   안전 위반 없음 (능력 기준선 갱신 신호만)
종료 05:56 (창 3.93h)   **막힌다** - 크롤까지 여유 4분
종료 06:00 (창 4.00h)   **막힌다** - 여유 0분
종료 01:00 (창 -1.00h)  **막힌다** - 창이 음수
```

**결론: 05:38 은 성립한다. 안전 상한은 05:55다.**

### ★ 그런데 가드에 구멍이 두 개 있었다

**(A) 종료 == 크롤 시작을 통과시켰다.** 기존 검사는 `종료 <= 크롤시작` 이었다.
그런데 워커는 종료 시각에 딱 멈추지 않는다 — `is_time_up()` 은 루프 **맨 위**에서만
검사되므로 이미 처리 중이던 행 하나는 종료 시각을 **지나서도** 끝난다.

```
실측(logs/doc_run.log 907구간)  행 1개 처리 최대 **42.2초**
코드가 허용하는 이론 최대        wait_for_detail 20초(40x0.5) + 오버레이 15 + 새창 15 = 약 50초
```

END=06:00 이면 06:00 에 시작하는 사건 크롤과 **실제로 겹친다.** 둘은 서로의 락을 보지
않는다(각자 자기 중복만 막는다). 증상은 "가끔 실패"로만 나타난다.
-> **여유 5분**을 요구하도록 고쳤다(이론 최대의 6배).

**(B) 창이 음수면 실행시간 한계 검사가 공허했다.** `limit >= window` 는 window 가
음수일 때 **언제나 참**이다. 종료가 시작보다 앞서면 `is_time_up()` 이 기동 즉시 True 를
돌려주어 그날 수집이 통째로 사라지는데, 그것이 "한계 안에 들어온다"로 읽혔다.
-> 창이 양수인지 먼저 본다.

### 초과분이 **행 하나**로 제한된다는 것을 행동으로 잠갔다

여유 5분 계산은 "초과분 = 행 하나"라는 전제 위에 있다. batching 이 그 전제를
물건 하나(최대 4행)로 키웠다면 계산이 무너진다. `is_time_up()` 호출 횟수로 확인한다.

```
행 12개 처리 -> is_time_up 호출 **14회** (= 기동 전 1 + 행마다 12 + 종료 1)
변이(시각 검사를 묶음 단위로) -> 5회. **잡힌다.**
```

★ 처음에 `행+1 = 13` 을 기대했다가 14 로 울었다. 기동 전 검사(드라이버를 띄우기 전
창이 닫혔는지 보는 것)를 빼먹은 것이다 — **코드가 아니라 내 산술이 틀렸다.**

## 2. MAX_ITEMS — 하나의 손잡이가 **두 가지**를 돌린다 (BUGS #174)

### 정적 사실 (지금 코드에서 확인)

```
crawler/court_crawler.py  crawl_court()        collect_list_items(driver, MAX_ITEMS)
                                               -> 그날 이 법원에서 몇 건 가져올까 = **공급 상한**
crawler/base_crawler.py   go_to_case_detail()  collect_list_items(driver, MAX_ITEMS)
                                               -> 아는 사건을 찾으려고 몇 행 훑을까 = **조회 창**
```

두 번째는 정책이 아니다. 그런데 같은 손잡이를 돌린다.
**공급을 줄이려고 이 값을 내리면 이미 큐에 있는 사건을 찾지 못하게 된다** —
조용히, 원인을 짐작하기 어려운 "사건 매칭 실패" 로그만 남기고.

진입점도 확인했다(grep 이 아니라 import 그래프):
`doc_worker` -> `go_to_case_detail` (조회) / `mvp_scraper` -> `crawl_court` (공급).

### 절단이 진짜인지 **진짜 함수로** 확인했다

가짜 DOM(19건, DB 실측 최대치)을 만들어 실제 `collect_list_items` 를 태웠다.

```
19건짜리 페이지  상한 10 -> 10건 반환, 19번째 사건은 **찾을 수 없다**
                 상한 없음 -> 19건 반환, 찾는다 (대조군)
```

### 상한이 실제로 걸리고 있다 — 로그 1,698회

```
1건 264 / 2건 109 / 3건 173 / 4건 238 / 5건 209 / 6건 143 / 7건 116 / 8건 125 / 9건 116
10건 **205회**  <- 상한. 분포가 완만한데 상한값만 튄다 = 실제로 걸린다

상한에 걸린 실행 **12.1%** -> 그날 그 법원의 물건 일부가 아예 수집되지 않았다
```

### ★ 말할 수 없는 것을 말하지 않는다

**"상한을 N 으로 올리면 공급이 얼마가 된다"는 로그로 알 수 없다.** 자료가 10에서
오른쪽으로 잘려 있다(right-censored). 그 너머는 상한 없이 크롤을 돌려야 알 수 있고
그것은 승인 영역이다. 그래서 **반대 방향으로** 계산했다.

```
물건 1건 47.2초 (이동 15.2 + 4종 x 8.0)
창 ~04:00 (지금)  능력 153건/일  공급 중앙값 106 -> 여유 **1.44배**
창 ~05:38         능력 277건/일               -> 여유 **2.61배**
창 ~05:55         능력 299건/일               -> 여유 **2.82배**
```

**순서가 계산으로 확정된다: 창을 먼저 넓히고, 그 다음 MAX_ITEMS 다.**
지금 여유는 1.44배뿐인데 실행의 12.1% 가 상한에 걸려 있다 — 상한을 올리면 공급이
얼마나 늘지 모르는 채로 그 얇은 여유를 소진할 수 있다.

## 4. JSON API 캐시 — 감사하고, 안전한 것만 구현했다

### 실측 (HTTP, 인증 토큰 포함 9종)

```
검색/상세/통계/문서통계/관심물건/최근본/프리셋   Cache-Control **없음** / ETag 없음
문서 파일   ETag+LM -> 조건부 **304**, 395,675바이트 절약
사진 파일   ETag+LM -> 조건부 **304**, 235,194바이트 절약
```

★ 처음에 `/api/v1/item/{id}/documents` 와 `.../images` 가 404 여서 결함을 의심했다.
OpenAPI 를 보니 **그런 라우트가 없다** — 단일 자원 라우트만 있고, 목록은 상세 응답의
`documents[]` / `images[]` 에 들어 있다. **내가 지어낸 URL 이었다.**

### 구현한 것 — 사용자별 응답에 `no-store` (한 곳)

헤더가 없으면 브라우저는 휴리스틱 캐싱에 맡겨진다. 공용 PC 에서 앞사람의 관심물건
응답이 디스크에 남을 수 있다. `api_server.py` 의 기존 보안 헤더 미들웨어 한 곳에 붙였다.

```python
if request.headers.get("authorization"):
    has_validator = ("etag" in response.headers or "last-modified" in response.headers)
    if not has_validator:
        response.headers["Cache-Control"] = "no-store"
```

★ **검증자가 붙은 응답은 건드리지 않는다.** 그쪽은 문서/사진 파일이고, 전부
`no-store` 로 덮으면 위의 630KB 절약이 사라진다. 그 경계가 이 변경의 핵심이다.

**신선도 계약은 깨지지 않는다** — `no-store` 는 "헤더 없음"보다 엄격하기만 하다.
서버가 주는 데이터는 그대로고 브라우저가 덜 보관할 뿐이다.

`max-age` 는 **정하지 않았다.** `api/http_cache.py` 가 적어 둔 이유("실제 갱신 주기라는
운영 근거가 없다")가 지금도 유효하다.

### 검증 (별도 인스턴스 8010 에서, 사용자 서버는 건드리지 않음)

```
사용자별 JSON 3종  -> Cache-Control: no-store
공개 JSON 2종      -> 변화 없음
파일(인증 포함)     -> ETag 유지, 조건부 요청 **304** 그대로
```

## 6. 모바일 — 측정 방법을 고쳤다

### 전에 쓰던 min-content 기법이 과대보고한다

최근본 화면에서 leaf 114개 중 10개가 min-content > 320 으로 잡혔다. 전부
**`truncate`**(ellipsis + nowrap + hidden) 였다 — **넘칠 수 없고 잘릴 뿐이다.**

그래서 (1) 클리핑되는 요소를 제외하고 (2) **실제 320/360/390/430 상자에 넣어** 본다.

```
최근본  카드 11개 전부 320/360/390/430 에서 넘침 **0**
검색    카드 20개 + 검색폼 전부 넘침 **0**
클리핑 없는 leaf 중 320 초과: **0** (최근본 114개 중 / 검색 321개 중)
```

### iframe 으로 진짜 viewport 를 만들려 했으나 — 막혔다

clone 기법의 근본 한계는 미디어쿼리가 **바깥 창 너비(1905px)로 평가**된다는 것이다.
iframe 은 자기 너비로 평가하므로 이 문제를 없앤다. 시도했더니:

```
SecurityError -> 원인: 이 앱이 `X-Frame-Options: DENY` 를 보낸다 (next.config.ts, 의도된 보안 헤더)
```

**측정 편의를 위해 보안 헤더를 약화하지 않는다.** 헤더 쪽은 손대지 않았다.

### 헤더만은 시뮬레이션으로 판정 (측정이 아님을 표기)

320px 에서 실제로 일어나는 두 가지(`hidden sm:*`/`md:*` 요소 제거, `md:px-8` -> `px-4`)를
손으로 재현했다.

```
320/360/390/430 전부 **넘침 없음**
다만 320px 에서 브랜드 "콕찰" 이 폭 0 으로 눌린다(내비가 shrink-0 276px + 여백 32px = 308px)
-> 넘침이 아니라 **가독성** 문제. 디자인 결정이므로 SKIP, 기록만 남긴다
그냥 clone 하면 432px 로 나온다 -> 시뮬레이션이 필요했던 이유
```

### CSV 컬럼 계약을 **실제 응답과** 대조했다

타입 선언만 보면 "맞다"고 말할 수 있다. 실제 응답에 필드가 없으면 CSV 는 빈 칸으로
조용히 채워진다. 관심물건이 0건이라 **같은 모양의 최근본 응답**으로 대조했다.

```
ExportRow 12필드 전부 응답에 존재 / 전 항목이 빈 값인 컬럼 **0개**
샘플: 법원=서울중앙지방법원 · 사건번호=2024타경117502 · 감정가=380000000 · 유찰횟수=8
```
