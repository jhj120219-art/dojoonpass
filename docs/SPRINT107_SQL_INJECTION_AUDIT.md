## 왜 이 경계를 봤나

이 API는 WHERE 절을 **문자열로 조립한다.** 검색 필터가 20개가 넘어 조건 조합이
동적이기 때문이다.

```python
conditions.append("sigungu LIKE ?")
where = " AND ".join(conditions)
conn.execute(f"SELECT * FROM auction_item WHERE {where}", params)
```

f-string이 SQL 텍스트를 만드는 이 모양은 인젝션이 **있으면** 최상위 심각도다.
그런데 앞선 스프린트들에서 인가/트랜잭션은 봤어도 **인젝션은 한 번도 실측하지 않았다.**

## 1. 정적 ― SQL 텍스트 보간 지점 전수

AST로 저장소 전체를 훑어, f-string / `%` / `.format` 이 **SQL 텍스트**를 만드는 지점을
뽑았다. `f"%{case_no}%"` 같은 **바인딩 값**은 대상이 아니다(리터럴 부분에 SQL 키워드가
없으므로 자동으로 걸러진다) ― 이 구분을 안 하면 22곳이 아니라 수백 곳이 나온다.

**22곳**이 나왔고, 그중 **요청으로 도달 가능한 것은 7곳**이다.

| 파일 | 보간 | 조립 방법 | 판정 |
|---|---|---|---|
| `search.py:309,321` | `where` | `" AND ".join(상수 조각들)` | 안전 |
| `search.py:321` | `order_clause` | `SORT_COLUMNS` 화이트리스트 + `ASC`/`DESC` | 안전 |
| `search.py:333` | `placeholders` | `?,?,?` (id 개수) | 안전 |
| `admin.py:259,269` | `where` | `" AND ".join(상수 조각들)` | 안전 |
| `audit.py:116,119` | `%s` | `" AND ".join(상수 조각들)` | 안전 |
| `payments.py:296` | `%s` | `",".join("?" * len(log_ids))` | 안전 |

나머지 15곳은 backfill / load / reset 같은 **CLI 스크립트**이고, 보간되는 `table` 은
소스에 박힌 리터럴이다. `migrate_v4_1.py:207` 의 `t[0]` 은 `sqlite_master` 가 돌려준
**DB 자신의 테이블명**이다.

핵심은 **조각이 전부 상수**라는 것이다. 값은 예외 없이 `?` 로 바인딩된다.
f-string으로 만든 조각은 딱 하나 있는데,

```python
or_clause = " OR ".join(["property_type LIKE ?"] * len(patterns))
conditions.append(f"({or_clause})")
```

`property_type` 은 **길이에만** 영향을 준다. 정수 개수는 인젝션을 만들 수 없다.

## 2. 동적 ― 실제 요청으로 재현

정적 판독을 믿지 않고 같은 결론을 **다른 방법으로** 확인했다.
페이로드 6종(`' OR '1'='1`, `'; DROP TABLE auction_item; --`, UNION 21컬럼,
`%' OR 1=1 --`, 백슬래시 이스케이프, 서브쿼리)을 8개 파라미터에 넣어 실제로 호출했다.

```
문자열 파라미터   전부 리터럴로 취급 ― 결과 0건 (기준 total 9와 같아진 것 없음)
정렬 파라미터     화이트리스트 밖은 HTTP 400 (조용한 폴백 아님)
경로 파라미터     타입 불일치 422 / 문서 종류 화이트리스트 400 / 경로탈출 404
결과              테이블 26개 그대로, auction_item 1,876행 그대로
```

**정적과 동적이 일치한다. 인젝션 없음.**

> 정렬이 400으로 **거부**하는 것이 중요하다. 정렬은 값 바인딩이 불가능해
> 화이트리스트가 유일한 방어인데, 조용히 기본값으로 넘어가면 방어가 동작하는지
> 밖에서 알 방법이 없다. 지금 구현은 거부하고 사유를 준다.

## 3. 그래서 무엇을 남겼나 ― 검사 두 겹

인젝션이 없다는 사실은 **오늘의 사실**이지 구조적 보장이 아니다.
지금 구조에서 뚫리는 방법은 단 하나, 누가 조각 하나를 상수가 아니게 쓰는 것이다.

```python
conditions.append(f"sido = '{sido}'")   # <- 이 한 줄
```

### (a) 구조 검사 ― `test_schema_hygiene.py`

- SQL 텍스트 보간 지점을 **핀으로 고정**한다. 새 보간이 생기면 실패한다.
- `%`-포맷 SQL은 좌변 템플릿 자체를 고정한다.
- 허용 목록에 **죽은 항목**이 남으면 실패한다(가드가 조용히 헐거워지는 것을 막는다).
- `conditions.append(...)` 인자가 상수가 아니면 실패한다.

### (b) 런타임 검사 ― `test_api_regression.py`

기존에는 `sido` 한 줄뿐이었다. 뚫리는 곳은 **검사하지 않은 쪽**이므로
6개 파라미터 × 3개 페이로드로 넓히고, 정렬 화이트리스트와 "테이블이 살아 있는가"를 더했다.

두 검사는 **같은 것을 다른 방법으로** 본다. 구조 검사는 내가 생각 못 한 공격도 막고,
런타임 검사는 구조 검사가 놓친 우회를 잡는다.

전체 1,876행이 조건을 통과했다 ― 조건이 "항상 참"이 됐다는 뜻이고, 검사가 **공허하지 않다**.
