## 1. Customer — 본업이 있는 투자자

콕찰의 고객은 **본업을 유지하면서 부동산에 투자하는 사람**이다.

    직장인 · 사업자 · 전문직
    경매를 전업으로 하지 않는 개인 투자자

이 고객의 결정적 제약은 지식도 자본도 아니라 **시간**이다. 물건을 볼 수 있는 시간이
평일 밤과 주말로 한정되고, 그 시간에 검색·권리·문서·현장을 전부 훑어야 한다.

### 쓰지 않는 표현

외부 제품 정의(README / PRD / 이 문서)에서 다음을 **핵심 고객이나 핵심 가치로
쓰지 않는다**:

| 쓰지 않는다 | 이유 |
|---|---|
| 저빈도 투자자 / 월 1~5건 / 가끔 경매하는 사람 | 사용 빈도는 **행동 결과**이지 고객의 정체가 아니다. 빈도로 정의하면 "더 자주 쓰게 만들기"가 목표가 되는데, 우리 목표는 반대다 — **덜 쓰고 더 빨리 판단하게** 하는 것이다 |
| 저렴한 / 가격이 싼 경매서비스 | 가격은 경쟁축이 아니다. 싸다는 이유로 선택된 제품은 더 싼 제품에 진다 |
| AI 경매서비스 | AI 는 수단이다. 고객이 사는 것은 AI 가 아니라 **줄어든 시간**이다 |
| 정부/공공 경매정보 서비스 | 정보 제공이 아니라 의사결정 지원이다 |

**내부 분석에서는 빈도를 쓴다.** 월 검토 물건 수 · 사용 빈도 · 유료 전환 · 사용량은
행동 세그먼트로 유효하다. 금지되는 것은 그것을 **제품 정의**로 쓰는 것뿐이다.

## 2. Problem — 정보가 없는 게 아니라 시간이 든다

경매 정보는 이미 많다. 문제는 **한 물건을 판단하기까지의 과정이 길다**는 것이다.

    검색 → 자료 확인 → 권리 확인 → 임차인 확인 → 문서 확인 → 시세 확인 → 현장 확인 → 판단

이 과정이 여러 사이트·문서·수첩에 흩어져 있어서, 본업이 있는 사람은 한 물건을
끝까지 보지 못하고 중간에 놓는다.

---

## 3. Value — 경매에 쓰는 시간을 줄이고, 판단에 집중하게 한다

콕찰은 **판단을 대신하지 않는다.** 판단에 이르는 시간을 줄인다.

이 구분이 제품 경계다. `docs/decision-log.md` 가 투자점수 · AI 추천 · 수익률 계산 ·
자동 투자판단을 프로젝트 범위 밖으로 못박은 것과 같은 선이다.

---

## 4. 경쟁축 — TIME-TO-DECISION

우리가 이기려는 축은 다음이 **아니다**:

    데이터 양     지지옥션·탱크옥션이 더 많다. 양으로는 이기지 못하고, 이길 필요도 없다
    가격          더 싼 곳은 언제나 나온다
    AI            수단이지 축이 아니다

우리가 이기려는 축은 하나다:

> **한 물건을 판단하기까지 걸리는 시간(T2D)이 가장 짧은 서비스**

## 5. Workflow — DISCOVER → REVIEW → FIELD → DECIDE

제품의 모든 기능은 이 네 칸 중 하나에 속한다. 어디에도 속하지 않는 기능은
왜 존재하는지 다시 묻는다.

| 단계 | 사용자가 하는 일 | 지금 구현 |
|---|---|---|
| **DISCOVER** | 물건을 찾는다 | 검색 · 필터 · 정렬 · 검색조건 저장 · 물건 카드 |
| **REVIEW** | 앉아서 검토한다 | 상세 · 권리분석 · 임차인 · 문서 뷰어 · 사진 · 등기부 신청 · 관심물건 · 최근 본 물건 |
| **FIELD** | 현장에서 확인한다 | 임장 기록 (체크리스트 · 메모 · 위험요소) |
| **DECIDE** | 입찰 여부를 정한다 | 임장 결과에 붙는 판단(BID / HOLD / DROP) |

### 단계 간 연결이 제품이다

각 칸이 있는 것보다 **칸과 칸이 이어지는 것**이 중요하다. 끊긴 자리에서 사용자는
콕찰 밖으로 나가고, 나가는 순간 시간이 늘어난다.

    DISCOVER → REVIEW   검색 결과 카드 → 상세 (구현됨)
    REVIEW  → FIELD     상세의 "임장" 버튼 → 임장 화면 (2026-09-04 연결)
    FIELD   → DECIDE    임장 화면 하단의 판단 버튼 (2026-09-04 연결)
    DECIDE  → 기록      판단이 물건에 남아 다시 열면 보인다 (구현됨)

## 6. 기능 분류 (2026-09-04 기준)

분류 기준은 하나다 — **T2D 를 줄이는가.**

### KEEP — 시간 절감/판단에 직접 기여

| 기능 | 어느 시간을 줄이나 |
|---|---|
| 검색 · 필터 · 정렬 | 볼 물건을 고르는 시간 |
| 검색조건 저장 | 매번 조건을 다시 입력하는 시간 |
| 물건 카드(썸네일·가격·유찰) | 상세로 들어가 보고 나오는 왕복 |
| 상세 화면 | 흩어진 정보를 모으는 시간 |
| 권리분석 · 임차인 | 등기부·명세서를 직접 읽는 시간 |
| 문서 뷰어(명세서/현황조사/감정평가) | 법원 사이트를 다시 여는 시간 |
| 사진 갤러리 | 현장에 가야만 알 수 있던 것 일부를 앞당김 |
| 관심물건 · 최근 본 물건 | 다시 찾는 시간 |
| **임장 기록** | 현장에서 본 것을 콕찰 밖에 적었다가 되찾는 왕복 |
| **입찰 판단 기록** | "이 물건 어떻게 하기로 했더라"를 다시 판단하는 시간 |

### REWORK — 필요하지만 workflow/UX 개선 필요

| 기능 | 무엇이 문제인가 |
|---|---|
| 등기부 신청 | **2026-09-04 재조사로 서술 정정.** "흐름이 끊긴다"는 부정확했다 — 실측하면 신청 후 **화면을 떠나지 않고**(`setRegistryRequest` 로 제자리 갱신), 다시 들어오면 상태가 복원되며(`item_id` 매칭), 마이페이지에 목록도 있다. 실제로 잰 friction 은 다른 것이다: 상세를 열 때마다 `GET /api/v1/registry-requests` 로 **사용자의 신청 전부를 받아 하나를 찾는다** — 가장 자주 열리는 화면에 왕복이 하나 더 붙고 비용이 신청 건수를 따라간다. `is_favorited` / `field_visit` 처럼 상세 응답에 실으면 없앨 수 있다 |
| 마이리스트 가져오기 | 진입점이 관심물건 화면 안쪽이라, 처음 온 사용자가 발견하지 못한다 |
| 최근 본 물건 20건 상한 | 화면에는 맞지만 **T2D 측정의 시작점**이 함께 지워진다 (`audit_time_to_decision.py` 참고) |

### DEPRIORITIZE — 핵심 workflow 기여도가 낮음

| 기능 | 판단 근거 |
|---|---|
| 마이리스트 내보내기 | 콕찰 밖으로 나가는 경로다. 나쁘지 않지만 T2D 를 줄이지 않는다 |
| 관리자 화면 | 운영 도구다. 고객 workflow 밖이다 |

### REMOVE — 없음

전략과 명백히 충돌해 **지금 지워야 하는 기능은 없다.** 코드 의존성을 확인하지 않은
채 지우지 않는다는 규칙(`docs/CLAUDE.md`)을 지킨다.

## 7. KPI — Time to Decision

### 정의

    T2D = 물건을 **처음** 발견한 시점  →  입찰 여부를 **판단**한 시점

### 지금 잴 수 있는 것 / 없는 것

측정 도구는 `audit_time_to_decision.py`(읽기 전용)다. **새 이벤트 테이블을 만들지
않았다** — 필요한 시각이 이미 대부분 있고, 같은 사실을 두 곳에 두면 갈라진다.

| 구간 | 근거 시각 | 상태 |
|---|---|---|
| 임장 시작 → 판단 | `field_visits.started_at` → `decided_at` | 잴 수 있다 (migration 030) |
| 임장 시작 → 임장 완료 | `field_visits.started_at` → `completed_at` | 잴 수 있다 |
| 처음 발견 → 판단 | `recent_items.first_viewed_at` → `field_visits.decided_at` | migration 031 적용 후 |

**측정의 한계를 숫자와 함께 항상 보고한다:**

- `recent_items` 는 사용자당 20건까지만 남는다 → 물건을 많이 보는 사용자일수록
  처음 본 기록이 먼저 사라진다. 지금 T2D 는 **가벼운 사용자 쪽으로 치우쳐** 측정된다.
- 임장 없이 판단한 물건은 잡히지 않는다(판단이 임장 기록에 붙어 있다).
- **표본이 없는 상태에서 "몇 % 단축" 같은 숫자를 만들지 않는다.**

### 보조 지표

T2D 를 대신하지 않고 보완한다: 검토 완료율(상세를 열고 판단까지 간 비율) ·
임장 완료율 · 재방문율 · 유료 전환율.

## 9. 아직 하지 않은 것 (정직하게)

| 항목 | 상태 | 왜 |
|---|---|---|
| 임장 **사진** | 미구현 | **2026-09-04 재조사로 서술 정정.** 재사용 가능한 조각은 **있다** — `crawler/image_assets.py` 의 `decode_image_data_uri()`(base64 정본) · `sniff_image_ext()`(매직바이트) · `MIN_IMAGE_BYTES` · `IMAGE_MEDIA_TYPES`. 즉 JSON base64 로 받으면 `python-multipart`(신규 의존성) 없이도 기술적으로 가능하다. **진짜 blocker 는 저장 위치다** — 사용자 사진을 기존 `documents/<법원>/<사건>/<물건>/images/` 에 두면 `audit_asset_integrity` 가 `auction_image` 행과 대조해 **매 실행 고아 파일로 잡는다**(이름 규칙에 맞으면 `orphan_count`, 안 맞으면 `stray_image_files`). 감사기가 영구히 붉어진다. 따라서 **별도 저장 뿌리 + 용량/보존/삭제 정책**이 먼저 정해져야 한다 — 제품 결정 |
| migration 030 / 031 운영 적용 | 미적용 | 스키마 적용은 승인 영역(`docs/CLAUDE.md`). 적용 전에도 API 는 503 + `FIELD_UNAVAILABLE` 로 정직하게 답한다 |
| 임장 없이 내리는 판단 | 미지원 | 판단이 임장 기록에 붙어 있다. 임장을 건너뛰는 물건이 많다면 판단을 물건에 직접 붙이는 구조로 옮긴다 |
| T2D 목표 수치 | 미정 | 표본이 쌓이기 전에는 정하지 않는다 |
