# Sprint 198 — "변경 0건"의 원인 분리, 그리고 Sprint 196 결론 정정

2026-08-18. 기준 커밋 `73ac6eb`.

Sprint 196 은 CSV 연속 스냅숏 비교에서 **변경 0건**을 관측하고
*"변경 감지 트리거는 구조적으로 옳지만 관측 기회 자체가 거의 없다"* 고 결론지었다.

**그 결론은 틀렸다.** 0건은 "안 바뀐다"가 아니라 **"바뀌는 순간을 못 봤다"** 였다.

---

## 1. 무엇을 잘못했나

연속 스냅숏(어제 vs 오늘)만 비교했다. 그런데 이 크롤러는 `MAX_ITEMS = 10`(법원당)으로
목록 상위 10건만 가져온다. **물건이 유찰되어 값이 바뀌는 시점에는 이미 그 슬라이스에서
빠져 있다.** 그래서 "연속 비교에서 0건"은 관측 설계의 결과이지 데이터의 성질이 아니었다.

Sprint 196 은 이 점을 *원인으로는* 지적했지만(`MAX_ITEMS` 언급), 결론 문장은
**"사실상 변경이 없다"** 쪽으로 기울어 있었다. 그것이 오독을 만든다.

---

## 2. 원인을 분리하는 측정

물건별 **등장 이력**을 만들고 세 가지를 따로 쟀다.

```
[1] 연속 스냅숏 비교            공통 4,455건
[2] 물건별 처음 등장 vs 마지막   1,228물건 (2회 이상 등장)
[3] 중간에 빠졌다 돌아온 물건    45개 (관측 공백이 실재하는 물건)
```

### 결과

```
                      [1] 연속    [2] 처음<->마지막   [3] 공백 물건
auction_date            0회          44회 (3.58%)        44회
minimum_bid_price       0회          44회 (3.58%)        44회
status                  0회          44회 (3.58%)        44회
appraisal_price         0회           0회 (0.00%)         0회
```

**[3] 이 결정적이다.** 값이 바뀐 44물건이 **전부** "빠졌다 돌아온" 45물건 안에 있다.
즉 **변경은 정확히 관측 공백 동안 일어난다.**

### 표본 (실제 값)

```
2023타경1173-1   07-07 -> 08-11   3,551,000 -> 2,841,000   유찰 20회 -> 21회
2023타경5687-1   07-07 -> 08-11   604,800,000 -> 483,840,000   유찰 1회 -> 2회
2024타경3787-1   07-07 -> 08-11   1,736,000,000 -> 1,388,800,000   유찰 5회 -> 6회
```

---

## 3. 측정 도구를 검증했다 (도메인 시그니처)

숫자가 그럴듯하다고 믿지 않고, **조작할 수 없는 도메인 특성**과 대조했다.

```
최저가 비율 분포   0.7 -> 34건 / 0.8 -> 10건
```

한국 경매의 유찰 저감률은 법원별로 **20% 또는 30%** 다. 측정된 비율이 정확히
0.8 과 0.7 두 값에만 몰린다 — 이건 우연히 나올 수 없는 모양이다.
`status` 도 84%가 `유찰 N회 -> N+1회` 형태다.

**데이터는 진짜이고 측정은 옳다.**

---

## 4. 정정된 결론

| 필드 | 판정 | 근거 |
|---|---|---|
| `auction_date` | **변경 실재** — 관측 범위 부족으로 연속 비교에서 안 보였을 뿐 | 44/1,228 (3.58%) |
| `minimum_bid_price` | 동상 (저감률 0.7/0.8) | 44/1,228 |
| `status` | 동상 (유찰 N -> N+1) | 44/1,228 |
| `appraisal_price` | **실제로 안 바뀐다** — 6주 1,228물건에서 0건 | 0/1,228 |

### 재수집 트리거에 대한 함의

`REFRESH_DOC_TYPES_BY_FIELD` 기준으로 실제 변경 조합을 풀면:

```
auction_date + minimum_bid_price + status  ->  {spec, status} = **2행/물건**
appraisal_price (-> appraisal, image)      ->  한 번도 발동하지 않음
```

- **문서 재수집(spec/status)은 실제로 발동한다.** 44물건/약 1개월 ≈ 하루 1.5물건 ≈
  **하루 3행 ≈ 72초**. 실행 창 7,200초 대비 1%.
- **사진 재수집은 발동하지 않는다.** 감정가가 안 바뀌기 때문이고, 이건 관측 공백 탓이
  아니다([2] 에서도 0건이다 — 처음과 마지막을 비교해도 안 바뀐다).

### Sprint 196 의 용량 모델이 오히려 보수적이었음이 확인됐다

모델은 "최악 4행/물건"으로 상한 60 을 잡았다. 실측 조합은 **항상 2행**이고
빈도도 하루 1.5물건이다. 상한 60 은 **실측 대비 40배 여유**다 — 안전 쪽으로 틀렸다.
값을 바꾸지 않는다(최악 대비 안전이 상한의 목적이다).

## 6. 무엇을 바꿨고 무엇을 안 바꿨나

**바꾼 것**: 문서(`docs/CURRENT_STATE.md`, `SPRINT195...md`)의 결론 문장.
실측이 뒤집혔으므로 코드가 아니라 **기록**을 고친다.

**안 바꾼 것**:
- `REFRESH_MAX_ITEMS_PER_RUN = 60` — 최악 기준 안전값이고 실측은 그보다 훨씬 작다.
- `REFRESH_DOC_TYPES_BY_FIELD` — 트리거 매핑은 실측과 일치한다(유찰 조합 -> spec/status).
- `MAX_ITEMS = 10` — 관측 범위를 늘리면 변경을 더 잘 보겠지만, 수집량·법원 부하·실행
  창을 동시에 건드리는 **용량 결정**이라 승인 영역이다.

**교훈**: "0건"을 보면 **관측 설계부터 의심한다.** 이번에는 같은 데이터에서
비교 축을 바꾸는 것만으로 0 -> 132 가 나왔다.
