## 1. 모바일 — 재지 못한 것과, 대신 확인한 것

### 재지 못했다 (SKIP 사유를 남긴다)

브라우저 자동화의 창 리사이즈가 **페이지 뷰포트에 반영되지 않는다**(`innerWidth` 가
1920 에서 안 바뀐다). 같은 출처 iframe 으로 390px 를 만드는 우회는 앱의
`X-Frame-Options: DENY` 가 막는다 — **그 헤더 자체는 올바른 보안 설정**이라
검사를 위해 낮추지 않았다.

그래서 **"모바일에서 깨지지 않는다"는 주장하지 않는다.** 실기기 또는 DevTools
디바이스 모드로 **사람이 한 번 봐야 한다.**

### 대신 전수로 확인한 것 — "넘칠 원인이 없다"

가로 넘침을 만드는 원인을 목록화해 소스 18파일을 훑었다.

```
고정 w-[NNNpx]         0곳
고정 min-w-[NNNpx]     0곳
w-screen / 100vw       0곳     (스크롤바 폭 때문에 실제로 넘치는 대표 원인)
min-w-max / min-w-fit  0곳
인라인 width: NNNpx    0곳
<table>                0곳     (열이 줄지 않아 모바일에서 가장 잘 깨진다)
반응형 없는 3열 이상 그리드  0곳
```

컨테이너는 `max-w-[1320px] mx-auto px-4 md:px-8` — **고정 폭이 아니라 상한**이고
모바일 좌우 패딩이 있다. 화면 5곳이 이 상수를 공유한다(폭을 화면마다 새로 정하지 않는다).

`overflow-x-auto` 2곳(썸네일 줄, 정렬 바)은 **컨테이너 내부**의 의도된 가로 스크롤이다 —
페이지 루트가 아니다.

그리드는 전부 mobile-first 다: `grid gap-3 md:grid-cols-2 xl:grid-cols-3`.

**이것은 "넘치지 않는다"의 증명이 아니라 "넘칠 원인이 없다"의 증명**이다.
그 구분을 문서에 그대로 남긴다.

### 긴 텍스트 렌더 지점

실제 JSX 렌더 지점 11곳 중 9곳에 `truncate`/`line-clamp`/`min-w-0` 같은 넘침 가드가
없다. 다만 한국어는 임의 위치에서 줄바꿈되므로 **구조적 넘침 원인으로 세지 않았다.**
확정하려면 실제 뷰포트가 필요하다 — 위와 같은 이유로 **확인하지 못함**이다.

★ 이 목록을 만들 때 도구가 한 번 틀렸다. 처음엔 타입 선언(`case_no: string`)과
쿼리 조립 코드까지 "렌더 지점"으로 세어 59곳을 보고했다. JSX 요소가 있는 줄로
좁혀 11곳이 됐다.

## 2. 검색목록 계약 — API -> 타입 -> 렌더

세 곳이 **서로 다른 파일**에 각자 적혀 있는데, 이를 대조하는 검사가 없었다.

```
api/v1/search.py              row_to_item() 의 딕셔너리 키      19개
src/app/search/types.ts       SearchResultItem 선언 필드         19개
src/app/search/ResultList.tsx item.<필드> 로 실제 그리는 것      17개
```

어긋남 **0**. (`crawl_date`, `validation_status` 는 응답에만 있다 — 그리지 않는 것은
화면의 선택이지 결함이 아니다.)

**왜 위험한가**: `item.foo` 가 `undefined` 면 React 는 오류 없이 **빈칸**을 그린다.
콘솔에도 서버에도 흔적이 없다. "조용한 실패"의 프런트 판본이다.

검사 방향은 한쪽만이다.

```
렌더가 쓰는데 API 가 안 준다     -> 결함 (빈칸)
타입이 선언했는데 API 가 안 준다  -> 결함 (타입이 거짓말한다)
API 가 주는데 안 쓴다            -> 결함 아님
```

변이 3종 전부 검출 — 특히 **API 키 이름 변경**(`thumbnail_url` -> 다른 이름)이
타입/렌더 양쪽에서 동시에 울었다. 그것이 실제로 가장 일어나기 쉬운 사고다.

## 3. 데이터 신선도 — 옛 값을 보여줄 경로가 없다

```
api/v1/item.py, search.py     Cache-Control / max-age  0곳 (매 요청 SQLite 직접 조회)
src/lib/api.ts                fetch 5곳 / cache: no-store 5곳
```

즉 법원 데이터가 바뀌면 **다음 요청부터 바로 새 값**이다. stale 이 생길 자리가 없다.

사진 바이트만 ETag 로 캐시되는데, 그것은 의도이고 교체 시 갱신되는지는
`test_asset_pipeline.py` 12-O 가 따로 본다(**크기가 같은 다른 사진**으로 검증).

지금은 선택일 뿐 강제된 적이 없었다 — 성능을 이유로 캐시 한 줄을 넣으면 그 순간
"매각기일이 어제 값으로 보인다"가 가능해지고, **그 실패는 화면에 오류로 나타나지 않는다.**
그래서 잠갔다. 변이 2종 검출(fetch 하나를 `force-cache` / 상세에 `Cache-Control` 주입).

## 4. ★ 직전 Sprint 의 내 기록을 정정했다

Sprint 219 는 이렇게 적었다 —
*"지금 크기가 대부분 px 고정(`text-xs`, `text-[11px]`)이라 루트 글꼴만 키워도
본문이 따라 커지지 않는다. 큰글씨의 선행 작업은 `rem` 전환이다."*

**빌드된 CSS 를 열어 보니 사실이 아니었다.**

```
--text-xs: .75rem       .text-xs { font-size: var(--text-xs) }
--text-sm: .875rem      .text-sm { font-size: var(--text-sm) }
```

Tailwind v4 의 이름 있는 크기는 **rem 기반**이다. `text-xs`(111곳)는 루트 글꼴을
키우면 **그대로 따라 커진다.** 닿지 않는 것은 대괄호 임의값뿐이고, 실측하면:

```
임의 px 값 전체        10곳
  그중 글자 크기         8곳   text-[11px] 6 + text-[10px] 2   <- 큰글씨가 닿지 않는 곳
  그 외                  2곳   max-h-[420px], max-w-[180px] (상한이라 무관)
```

**선행 작업은 "전면 rem 전환"이 아니라 그 8곳 교체**다. 훨씬 작은 일이고,
큰글씨 토글은 그 뒤 바로 붙일 수 있다.

교훈: *"대부분 px 고정"* 은 **소스의 겉모습만 보고 내린 추정**이었다.
빌드 결과를 열어 봤어야 했다. 정정을 `SPRINT219` / `roadmap` / `frontend.md`
세 곳에 남겼다(원문도 함께 남겨 무엇을 근거로 틀렸는지 보이게).
