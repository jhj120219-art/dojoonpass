## 1. ★ "WCAG 2.5.8 위반"은 사실이 아니었다

### 문서가 하던 주장

`docs/SPRINT219_ACCESSIBILITY_AUDIT.md`

> 내비게이션 5개는 높이가 **16px** 다. WCAG 2.5.8(Target Size Minimum, AA)의 24px
> 미만이라 **규격 위반**이고, Apple HIG 권장(44px)의 36% 다.

그리고 그 문서의 개선안 표는 헤더 내비를 **1순위**로 올리며 근거를 이렇게 적었다.

> WCAG 2.5.8 AA **위반**이라 디자인 논쟁 여지가 가장 적다

### 실측

SC 2.5.8 에는 예외가 다섯 개 있고, 그중 **간격(Spacing) 예외**가 그대로 적용된다.

> 24 CSS px 지름의 원을 각 타깃 bounding box 중심에 놓았을 때 그 원들이 서로 겹치지
> 않으면, 크기가 24px 미만이어도 적합이다.

실브라우저에서 그 기하를 직접 계산했다(Chrome, 2026-08-20).

```
화면              타깃수   24px 미만   원이 겹치는 쌍
/search             29        5개          0쌍
/properties/505     21        9개          0쌍
/mypage              8        5개          0쌍

가장 가까운 중심 간 거리   54px      (임계 24px 의 2.25배)
-> SC 2.5.8 위반 **0건**. 간격 예외로 적합.
```

### 왜 중요한가

1순위의 근거가 *"규격 위반이라 논쟁 여지가 없다"* 였다. 그 전제가 사라지면
헤더 내비 확대는 **규격 준수가 아니라 순수한 디자인 판단**이 되고, 1순위 자리도 잃는다.
그리고 **진짜 규격 위반은 대비(SC 1.4.3) 쪽에만 있다** — 거기에는 쓸 수 있는 예외가 없다.

크기가 작다는 사실 자체는 그대로다(어르신 사용성에 불리하다).
다만 그것을 "규격 위반"이라고 불러서는 안 된다.

### 전수 정정

같은 문장이 **6곳**에 퍼져 있었다. 하나만 고치면 나머지가 계속 거짓말을 한다.

```
docs/SPRINT219_ACCESSIBILITY_AUDIT.md   본문 + 개선안 표
docs/roadmap.md                          실측 요약 + 우선순위 목록
docs/frontend.md                         실측 요약
docs/CHANGELOG.md                        2곳
docs/CURRENT_STATE.md                    1곳
test_frontend_accessibility.py           파일 상단 주석
```

정정이 지워지면 다음 사람이 같은 오판을 반복하므로, 문서 근거 검사에
`간격(Spacing) 예외` 토큰을 추가해 **정정 자체를 잠갔다**(변이로 확인).

## 2. ratchet 가드가 보지 못하던 곳

`test_frontend_accessibility.py` 는 저대비/작은 글자 클래스의 **사용 횟수를 상한으로**
잠근다. 그 방식 자체는 옳은데, 두 군데가 비어 있었다.

### 사각지대 A — `src/components/` 를 아예 안 봤다

```python
def _tsx_files():
    return glob(ROOT/src/app/**/*.tsx)      # <- 화면만
```

```
src/app          text-xs 111 / text-gray-400 106     <- 예전 상한
src/components   text-xs   7 / text-gray-400   4     <- **한 번도 세지 않았다**
합계             text-xs 118 / text-gray-400 110
```

★ 하필 그 사각지대에 `SiteHeader.tsx` 와 `PrimaryNav.tsx` 가 있다 —
**Sprint 219 가 "가장 나쁘다"고 지목해 실측한 헤더 내비 바로 그것**이다.
즉 문서의 "text-xs 111회 / text-gray-400 106회"는 **과소 집계**였다.

더 나쁜 성질: 이 구조에서는 **공용 컴포넌트로 옮기는 순간 그 글자가 검사에서 사라진다.**
리팩터링이 곧 검사 회피가 된다. (Sprint 224 에 `ResultThumbnail.tsx` 를 그쪽으로
옮기면서 드러났다.)

### 사각지대 B — 추적 밖의 색으로 갈아타면 상한이 오히려 내려간다

상한은 표에 적힌 클래스만 센다. `text-gray-400`(2.6:1) 을 **더 나쁜**
`text-gray-200` 으로 바꾸면 `text-gray-400` 개수가 줄어 **초록불이 된다.**
실제로 `text-red-400`(2.89:1) 이 2곳에 쓰이고 있었는데 표에 없었다.

**해결**: 쓰이는 저대비 계열(`text-<색>-100~400`)을 전부 열거하고, 표에 없는 것이
나타나면 실패시킨다. 스캔이 죽으면 공허하게 통과하므로 하한도 함께 걸었다.

## 3. 범위를 넓히자 검사기 자신의 버그가 드러났다

범위를 `src/components` 까지 넓힌 첫 실행에서 이렇게 나왔다.

```
[FAIL] 가로 넘침 원인 - 고정 w-[NNNpx]: ['src/components/SiteHeader.tsx:72']
```

그 줄은 `max-w-[180px]`(이메일 말줄임 **상한**)이다. **고정 폭이 아니다.**

```python
"고정 w-[NNNpx]": r"\bw-\[\d{3,}px\]"      # max-w-[180px] 안의 w-[180px] 에도 걸린다
```

`-` 가 비단어 문자라 `max-w-` 의 `w` 앞에서도 `\b` 가 성립한다.
앞 판본이 `max-w-[1320px]` 로 한 번 당해서 `\d{3,}` 을 붙였지만, 문제는
자릿수가 아니라 **접두사**라서 막히지 않았다.

이 버그가 그동안 안 보인 이유는 단순하다 — `max-w-[...]` 를 쓰는 곳이
`src/components/SiteHeader.tsx`(스캔 밖)와 `src/lib/layout.ts`(`.ts` 라 스캔 밖)
**둘뿐**이었다. **범위가 좁으면 검사기 자신의 버그도 함께 숨는다.**

```python
"고정 w-[NNNpx]": r"(?<!max-)(?<!min-)\bw-\[\d{3,}px\]"
```

`min-w-` 는 진짜 원인이 맞지만 바로 아랫줄에서 따로 세므로 여기서는 뺀다(이중 계수 방지).

그리고 검출기를 **넣기 전에** known-good/known-bad 로 시험하게 했다.

```
반드시 잡아야       w-[420px] / w-[1024px]
절대 잡으면 안 됨   max-w-[1320px] / max-w-[180px] / min-w-[360px] / w-[80px] / w-full
```

## 4. 색 대비 실측 — 도구가 또 한 번 거짓말할 뻔했다

Tailwind v4 는 색을 `oklch()` 로 낸다(Chrome 은 계산값을 `lab()` 로 돌려주기도 한다).
**문자열에서 숫자를 뽑아 RGB 로 읽으면 반드시 틀린다** — Sprint 219 가 이미 당한 함정이다.

그래서 이번에는 **캔버스에 그 색 문자열을 그대로 칠하고 픽셀을 읽어** 진짜 sRGB 를 얻었다
(변환을 브라우저 자신에게 맡긴다).

### ★ 그런데 그 도구도 한 번 거짓값을 냈다

없는 클래스를 붙여도 아무 일이 일어나지 않고 **상속색이 읽힌다.**
Tailwind v4 는 **소스에 실제로 쓰인 클래스만** CSS 로 만들기 때문이다.

```
text-blue-700  ->  rgb(23,23,23)   대비 17.93   <- 이것은 --foreground 다. 파란색이 아니다.
bg-blue-600    ->  흰글씨 대비 21   <- 검은 배경으로 읽혔다
```

그래서 **"클래스를 붙였을 때 색이 실제로 바뀌었는가"** 를 먼저 확인하고,
바뀌지 않으면 수치를 내지 않고 *"CSS 에 없음 — 측정 불가"* 라고 말하게 고쳤다.
아래 표는 **전부 실제로 적용이 확인된 값**이다.

### 실측 (흰 배경, 2026-08-20)

```
클래스              rgb              대비      AA(4.5:1)
text-gray-300       209,213,220      1.47      ✗   기준의 33%
text-gray-400       153,161,175      2.60      ✗   기준의 58%
text-red-400        255,100,103      2.89      ✗   ← **오류 문구**에 쓰인다
text-blue-500        43,127,255      3.76      ✗
text-gray-500       106,114,130      4.84      ✓
text-blue-600        21, 93,252      5.25      ✓
text-gray-600        74, 85,101      7.56      ✓
text-gray-700        54, 65, 83     10.30      ✓

흰 글씨 on bg-blue-500                3.76      ✗   ← **주 CTA(검색/저장/정렬칩)**
```

화면별 실패율(캔버스 래스터화 기준):

```
/search           36개 중 20개 실패 (56%)
/properties/505  100개 중 49개 실패 (49%)   14px 미만 텍스트 38개
                 최악 1.47:1 (text-gray-300 on white)
```

### 새로 드러난 것 두 가지

Sprint 219 의 표는 `text-gray-400` 계열 본문에 집중했다. 다음 둘은 기록이 없었다.

1. **흰 글씨 on `bg-blue-500` = 3.76:1** — 화면에서 가장 크고 중요한 버튼
   (검색 / 저장 / 정렬 칩)이 AA 미달이다.
2. **`text-red-400` = 2.89:1** — 오류 문구다. **가장 읽혀야 하는 글자가
   본문 회색(2.6:1)보다 겨우 나은 수준**이다.

### 최소 교체안 (제품 결정용 — 임의로 적용하지 않았다)

같은 색 계열 안에서 **한 단계만** 내리면 전부 AA 를 넘는다. 색조는 그대로다.

```
text-gray-400  2.60  ->  text-gray-500  4.84   ✓
text-red-400   2.89  ->  text-red-600          (미사용이라 측정 불가 — 쓰면 잴 수 있다)
text-blue-500  3.76  ->  text-blue-600  5.25   ✓
bg-blue-500 + 흰글씨   ->  bg-blue-600 + 흰글씨  5.25   ✓ (text-blue-600 실측값에서 도출)
text-gray-300  1.47  ->  최소 gray-500 이상    (5곳, 전부 상세페이지)
```

> `bg-blue-600` 의 5.25 는 **직접 잰 값이 아니라** `text-blue-600` 실측값에서 도출한 것이다
> (같은 색 토큰). `bg-blue-600` 은 아직 소스에 없어 CSS 에도 없으므로 직접 잴 수 없다.
> `text-red-600` 도 같은 이유로 측정하지 못했다 — 모른다고 적는다.

## 8. 확인하지 못한 것

**모바일 폭에서의 탭 타깃과 대비.** 이번 SC 2.5.8 판정은 **데스크톱 1920px** 기하다.
좁은 폭에서 헤더 항목이 서로 가까워지면 간격 예외가 깨질 수 있다 — 그때는 **진짜 위반**이 된다.
`resize_window` 는 `innerWidth` 를 바꾸지 못하고(Sprint 223 확인), iframe 은
`X-Frame-Options: DENY` 에 막힌다(Sprint 224 확인). **모바일 판정은 여전히 못 한다.**

`text-red-600` / `bg-blue-600` 의 실제 대비 — 소스에 없어 CSS 에도 없으므로 측정 불가.
