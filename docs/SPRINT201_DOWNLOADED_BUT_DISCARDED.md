## 2. BUGS #135 — 다운로드가 성공할수록 탭이 안 생긴다

### 근본 원인

`get_download_driver_options()` 는 `plugins.always_open_pdf_externally: True` 를 켠다.
그래서 Chrome 은 PDF 를 **렌더링하지 않고 곧바로 내려받는다.**
`window.open(pdf_url)` 로 연 탭은 **그릴 것이 없으니 뜨지도 않고 사라진다.**

그런데 `collect_appraisal()` 은 새 탭이 뜨기를 기다리고, 안 뜨면
**`wait_for_download()` 를 부르지도 않고** 실패로 끝냈다.

```python
if not new_handle:
    logger.warning("appraisal PDF 탭 생성 실패")
    return result            # <- 도착한 파일을 확인조차 안 한다
```

즉 **다운로드가 성공할수록 탭은 안 생기는데, 탭을 성공 조건으로 삼고 있었다.**

### 증거는 하나가 아니었다

`downloads/` 최상위에 고아 PDF 가 쌓여 있었다.

```
2023타경118942_..._매각물건명세서_....pdf        (원본)
2023타경118942_..._매각물건명세서_... (1).pdf
2023타경118942_..._매각물건명세서_... (2).pdf
2023타경118942_..._매각물건명세서_... (3).pdf
```

Chrome 의 이름 충돌 회피 규칙(`(1)`, `(2)`, `(3)`)이 붙어 있다 —
**같은 사건의 문서를 네 번 받아 네 번 버렸다는 뜻이다.** 재시도가 매번 다시 받고
매번 버렸다.

### 영향

```
수집 실패 보고        실제로는 성공했는데
재시도 예산 소모       MAX_DOC_RETRY 3회를 헛되이 쓴다
디스크 누적            downloads/ 에 14.0MB 고아
사용자 영향            받을 수 있는 문서가 FAILED 로 남는다
```

그리고 이것은 Sprint 197 의 결론 — *"수집 실패와 원래 없음을 구분할 신호가 없다"* —
을 더 무겁게 만든다. **실패의 상당수가 사실은 성공이었다.**

### 해결

탭이 없으면 **다운로드가 왔는지부터 확인한다.** 둘 다 없을 때만 실패다.
더하기만 하는 변경이라 지금 성공하는 경로는 그대로다.

### 실환경 확인

수정 후 같은 물건으로 다시 돌렸다.

```
appraisal  success=True   19.8초    <- False 였다
```

**실제 법원에서, 실제 다운로드가, 이제 저장된다.**

### 회귀

`test_doc_storage_atomicity.py` 7j — **탭을 절대 만들지 않는 가짜 드라이버**로
(`plugins.always_open_pdf_externally` 환경의 실제 조건) 세 경우를 고정한다.

```
탭 없음 + 다운로드 도착   -> 저장한다 (고아를 남기지 않는다)
탭 없음 + 다운로드 없음   -> 실패한다 (대조군)
탭 없음 + 가짜 PDF        -> 거부한다 (기존 방어 유지)
```

변이 검증: `if not new_handle: return result` 를 되살리면 즉시 2건 FAIL.

**대역이 실물보다 좁아 한 번 막혔다** — `switch_to.default_content()` / iframe `src` 를
안 갖고 있어 `AttributeError` 가 났다. Sprint 189 에 같은 일을 겪었으므로(대역이 좁아
TypeError 가 "수집 실패"로 삼켜졌다) 대역을 실물 표면에 맞춰 넓혔다.

## 3. BUGS #136 — 명세서 쪽은 다른 경로다 (탐지만)

수정 후 실행에서 `spec` 은 여전히 실패했고, 이번에는 **파일이 아예 오지 않았다**
(`downloads/` 에 새 파일 0개). 즉 #135 와 **다른 메커니즘**이다.

그러나 `downloads/` 의 고아 8개 중 **5개가 매각물건명세서**다. 즉 명세서 다운로드도
과거에 도착했는데 저장되지 않았다.

가설(확정 아님): `wait_for_download(timeout=30)` 이 끝난 **뒤에** 파일이 도착하면,
그 실행은 이미 실패로 끝났고 파일은 고아가 된다. 다음 실행의 `before_files` 에는 그
고아가 이미 들어 있으므로 영원히 회수되지 않는다.

**원인을 확정하지 못했으므로 코드를 바꾸지 않는다.** 타임아웃을 늘리는 것은 운영
로그 없이 정할 수 없는 튜닝이고(실행 창 예산과 얽힌다), 고아를 물건에 붙이는 것은
파일 이름만으로 소유자를 확정할 수 없어 위험하다.

대신 **상시 탐지**를 붙였다 — `audit_asset_integrity.py` [8].

```
[8] 다운로드 폴더에 남은 고아 파일
    고아 8개 / 14.0 MB
```

이제 이 계열이 재발하면 감사기가 즉시 드러낸다.

> **[정정 2026-08-18 Sprint 202] 위의 "코드를 바꾸지 않는다"는 뒤집혔다.**
> 원문은 기록으로 남긴다.
>
> 다음 스프린트에서 **#135 계열 전수검색**을 돌리자 `collect_spec()` 이
> `collect_appraisal()` 과 **완전히 같은 모양**임이 드러났다 — 탭이 안 뜨면
> `wait_for_download()` 를 부르지도 않고 실패로 끝낸다. 명세서 고아 5개는
> "타임아웃 뒤 도착"이 아니라 **이 분기가 버린 것**으로 설명된다.
>
> 위 §3 이 틀린 지점은 결론이 아니라 **관측의 해석**이다. 그날 실행에서 spec 은
> 파일이 오지 않았고, 나는 그것을 "#135 와 다른 메커니즘"의 근거로 삼았다.
> 그러나 그것은 **그날 그 물건**에 대한 사실일 뿐, 고아 5개가 어떻게 생겼는지에
> 대한 사실이 아니다. **관측 1건으로 계열 전체를 배제한 것**이 오류다.
>
> 고친 내용과 회귀(7k)는 `docs/BUGS.md` #136 갱신 항목에 있다.
> 다만 "뷰어 탭은 뜨는데 30초 안에 안 오는" 경로는 여전히 미확정이고,
> `audit_asset_integrity.py` [8] 은 계속 필요하다.

-> DOM 읽기).

```
이동 1회 19.1초
spec 32.8 / appraisal 19.8 / status 0.7 / image 0.1
모든 종류 처리 후: 창 1개, URL 유지, 사진요소 5개 계속 읽힘

묶어서   19.1 + 53.5 = 72.6초
현재     19.1 x 4 + 53.5 = 129.7초
```

**여전히 착수하지 않는다** — 근거는 Sprint 199 와 같다(claim 단위·재시도 예산이 행 단위
전제, 현재 대기 물건 2개). 다만 이제 "가능하다"는 4종 전부에 대해 실측 근거를 갖는다.
