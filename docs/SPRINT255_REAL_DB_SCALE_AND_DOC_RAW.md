## 1. 검색 성능 — 지금은 빠르다. 규모가 커지면 **가격 필터에서 무너진다**

### 1-a. 현재 규모(2,444행)에서의 실측

```
필터                          결과수   시간      쿼리 계획
-------------------------  --------  --------  ------------------------------------
없음                          2,444   0.112ms  SCAN idx_auction_item_default_sort
sido                            342   0.177ms  SEARCH idx_ai_sido
sido+sigungu                      5   0.125ms  SEARCH idx_ai_sido
+property_type                    1   0.105ms  SEARCH idx_ai_sido
+가격범위                          1   0.751ms  SEARCH idx_auction_item_minimum_bid_price  <- 계획이 바뀐다
+기일+유찰+낙찰가율                 1   0.783ms  SEARCH idx_auction_item_default_sort
full_address LIKE             1,151   0.426ms  SCAN idx_auction_item_default_sort
```

실 API 실측(HTTP): 기본 검색 20.4ms / sido 3.0ms / 가격범위 24.5ms / include_closed 2.6ms.
**지금 규모에서는 어떤 조합도 문제가 아니다.**

### 1-b. ★ 500,000행 합성 DB 에서의 실측 (임시 DB, 실 DB 무변경)

```
쿼리                        시간         계획
------------------------  -----------  ----------------------------------------
필터 없음                      4.44ms   SCAN idx_auction_item_default_sort
sido                         24.61ms   SEARCH idx_ai_sido
sido + 가격범위            2,856.47ms   SEARCH idx_auction_item_minimum_bid_price
가격범위만                 1,455.80ms   SEARCH idx_auction_item_minimum_bid_price
full_address LIKE           114.48ms   SCAN idx_auction_item_default_sort
기일 이후만                    4.49ms   SEARCH idx_auction_item_default_sort
깊은 offset (500페이지)         4.50ms   SCAN idx_auction_item_default_sort
```

**가격 필터 하나가 2.9초를 만든다.** 경매 제품에서 "예산으로 거르기"는 부차적 필터가
아니라 **주된 진입 경로**다.

### 1-c. 왜 그런가 — 계획이 정렬을 잃는다

기본 정렬은 `auction_date DESC, fail_count DESC, id DESC` 이고
`idx_auction_item_default_sort(auction_date DESC, fail_count DESC)` 가 그것을 **순서대로**
준다. 그 계획은 인덱스를 출력 순서로 걸으며 가격을 걸러 **20건에서 멈춘다.**

가격 인덱스를 쓰면 정렬을 잃어 **조건에 맞는 행을 전부 꺼내 임시 B-tree 로 정렬**해야 한다.
LIMIT 20 이 아무 소용이 없다.

### 1-d. 선택도별 실측 — **어느 한쪽이 항상 옳지 않다**

```
조건에 맞는 행    플래너(가격 인덱스)   강제(default_sort 순서 주사)
--------------  ------------------  ---------------------------
             1              0.03ms                    1,396ms
            81              0.11ms                      340ms
           205              0.17ms                      140ms
           410              1.31ms                       86ms
        31,630             92.16ms                     0.11ms
       500,000          1,455.02ms                     0.13ms
```

그래서 **`INDEXED BY` 로 계획을 박아 넣으면 안 된다** — 좁은 가격대에서 정반대로 무너진다.

### 1-e. 고칠 수 있는 방법 (구현하지 않았다 — 지금은 병목이 아니다)

`api/v1/search.py` 는 페이지 쿼리 **직전에 이미 `COUNT(*)` 를 돌린다.** 그 `total` 이 곧
선택도다. 그리고 그 COUNT 는 커버링 인덱스라 싸다(실측 0.02~4.82ms).
즉 **추가 비용 0 으로 이미 선택도를 알고 있다.** 임계값을 넘으면 순서 주사 형태를,
아니면 지금 형태를 고르면 양쪽 최선을 취한다. 교차점은 대략 `matched > sqrt(20N)`
(N=500k 이면 약 3,162 / N=2,444 이면 약 221).

### 1-f. 얼마나 급한가 — **급하지 않다. 다만 잰 값을 남긴다**

플래너 계획의 비용은 맞는 행 수에 선형이다(실측 약 2.9us/행).

```
200ms 를 넘는 지점   auction_item 약   69,000행
1초를 넘는 지점                 약  345,000행
지금                                2,444행
이 머신의 순증           하루 약 40~260행 (created_at 기준)
```

**결론: 지금 고칠 이유는 없다. 운영 크롤(전국·매일)이 붙어 규모가 5만 행에 접근하면
1-e 를 구현한다.** 그 전에 이 문서의 숫자를 다시 잰다.

## 2. 큐 claim 은 O(N) 이지만 **병목이 아니다** (실측으로 기각)

claim 쿼리는 `idx_queue_priority` 를 순서대로 훑다가 조건에 맞는 첫 행에서 멈춘다.
큐가 소진될수록 앞부분이 전부 `done` 이라 훑는 거리가 길어진다.

```
소진율     claim 1회
    0%      0.034ms
   50%      0.217ms
   90%      0.321ms
  100%      0.323ms
```

10배 늘지만 **절대값이 0.32ms** 다. 문서 1건 수집은 브라우저 작업이라 **초 단위**다.
6,033행에서 claim 비용은 전체의 0.001% 미만이다. **고치지 않는다.**

## 3. 워커 처리량 — backlog 5,314행은 **겁줄 만한 숫자가 아니다** (자기 정정)

### 3-a. 처음 센 방식이 틀렸다

처음에는 `backlog 5,314행 / 4종 = 1,329물건 -> 8.7일치` 라고 셌다. **틀렸다.**
큐 행의 대부분은 브라우저를 열지 않는다.

```
claim 가능 행 (pending + refresh)                     5,314
  기일 경과 -> doc_worker 2차 방어선이 **브라우저 없이** 종결      4,275   (80.4%)
  날짜 없음                                                3
  기일 미도래 -> **실제로 브라우저를 여는 것**                  1,039   (19.6%)

실제 수집이 필요한 물건 수                                 270
Sprint 236 실측 능력                                    153 물건/일
-> 실제 소요                                          **1.8일**
```

근거는 `doc_worker.py:285-298` 이다 — `auction_date < today` 면 `continue` 로
**드라이버 호출 이전에** 끝난다. 그리고 실행 예산은 건수가 아니라 벽시계
(`is_time_up()` 이 `DOC_WORKER_END_TIME` 까지)라, 싼 종결은 예산을 사실상 쓰지 않는다.
`audit_asset_integrity.py` 도 같은 결론을 이미 적고 있다("지금 낭비되는 수집 비용은 0").

**8.7일 과 1.8일 은 서로 다른 결정을 부른다** — 전자는 "병렬 워커가 급하다", 후자는
"이틀만 돌리면 따라잡는다" 다. 그래서 정정해 남긴다.

### 3-b. 우선순위 정렬도 결함이 아니었다 (기각한 가설)

`calc_priority()` 는 `days_left <= 3` 이면 1을 주는데 **기일이 지난 것도 음수라 1** 이다.
claim 정렬이 `priority ASC, auction_date ASC` 이므로 **가장 오래 지난 것이 큐 맨 앞**에 온다.
실제로 앞 153물건은 100% 기일 경과분이고 기본 검색에 보이는 것은 0개다.

처음에는 이것을 "하루 능력을 안 보이는 물건에 다 쓴다"는 결함으로 읽었다. **아니다** —
3-a 대로 그 153물건은 브라우저 없이 초 단위로 종결된다. 그리고 실제로 브라우저를 여는
270물건은 **기본 검색에 보이는 270건과 정확히 같은 집합**이다. 즉 남은 실작업은 전부
사용자가 볼 수 있는 것이다. **고칠 것이 없다.**

### 3-c. 그래도 남는 관찰

공급이 능력을 넘는 날이 있다(오늘 크롤 신규 262물건 vs 능력 153). 공급 중앙값은 106물건/일
(Sprint 236 기록)이라 평균적으로는 따라가지만 여유가 1.4배뿐이다. 전국·매일 운영 크롤이
붙으면 여기가 먼저 막힌다. 다음 지렛대는 **병렬 워커**다(현재 `SPRINT142` 의 단일 인스턴스
락이 동시 실행을 막는다). 물건당 47.2초 = 이동 15.2초 + 수집 4종 x 8.0초 이므로 이동을 더
줄이는 것보다 인스턴스를 늘리는 쪽이 여지가 크다. 데스크탑1 자원 결정이라 **승인 영역**이다.

## 4. 베타 사용자가 실제로 막히는 지점

기본 검색에 **보이는** 270건만 대상으로 쟀다.

```
문서가 전부 COLLECTING("수집중")인 물건    249 / 270  = **92.2%**
READY 문서를 하나라도 가진 물건             21 / 270  =    7.8%
rights_summary 가 있는 물건                 16 / 270  =    5.9%
사진이 있는 물건                             0 / 270  =    0%
document_status 행이 아예 없는 물건           0
```

**검색은 되고 상세도 열리는데, 열 것이 없다.** 이것은 코드 결함이 아니라 3절의 공급
부족이 화면에 나타난 것이다 — 즉 **P0-A(빈 화면)를 닫아도 그 다음 벽이 이것**이다.

## 5. "끝나지 않는 수집중" 2,113건 — 이유 미상 639 -> **210 으로 줄였다**

`measure_endless_collecting.py` 가 639건을 "(b3) 이유 미상" 으로 두고 있었다.
**증거로 대부분을 설명했다.**

```
document_queue MIN(enqueued_at)     2026-07-08T12:24:57   <- 큐가 처음 채워진 시각

crawl_date    물건수   그중 큐 행이 있는 것
2026-07-06       71        7
2026-07-07       91       12
2026-07-08       76        6
2026-07-09       44       44   <- 이후 100%
```

**큐가 생기기 전에 수집된 물건은 넣을 큐가 없었다.** 그리고 `enqueue_documents()` 는
기일이 지난 것을 다시 넣지 않으므로(1차 방어선) 영원히 채워지지 않는다.
**일회성 유물이지 지금도 벌어지는 결함이 아니다** — 그 구분이 대응을 정반대로 가른다.

`no_queue_reason()` 에 `queue_epoch`(= DB 에서 읽은 `MIN(enqueued_at)`, 하드코딩 아님)를
넘겨 `(b3-old)` 를 분리했다. **날짜 증거가 있을 때만** 유물로 부르고 나머지는 여전히
모른다고 한다. selftest 4건을 추가했다(증거가 없으면 유물로 몰지 않는 것까지 고정).

```
(b2) 018 이전 UNIQUE 충돌                      1,299
(b3-old) 큐 도입(2026-07-08) 이전 수집           429   <- 새로 설명됨
(b3) 이유 미상                                   210   <- 639 에서 줄었다
(a)  SKIPPED_EXPIRED                            175
```

`(b2) 1,299` 에 대한 정정 — migration 018 헤더는 *"빠져 있던 물건들은 다음
`enqueue_documents()` 실행 때 자연히 채워진다"* 고 적었다. **그 문장은 틀렸다.**
`enqueue_documents()` 는 `auction_date < today` 를 건너뛰므로, 018 적용 시점에 이미 기일이
지난 물건은 **영원히 채워지지 않는다.** 다만 이 1,299건은 전부 기일 경과분이라 기본 검색에
보이지 않는다(기일 남은 것 0건). 표시 정책은 여전히 제품 결정이다.

## 6. 결함이 아니라고 판정한 것

- **`case_no` 중복 7쌍** — 같은 사건번호가 다른 법원에 있는 것이다(한국 사건번호는
  법원 단위로만 유일하다). `UNIQUE(case_id, item_no)` + `auction_case(case_no, court_code)`
  구조가 옳다. 예: `2024타경195` 가 장흥지원(전남 장흥군)과 서울동부지방법원(서울 성동구)에
  각각 있다.
- **`documents/` 빈 디렉터리 1,958개** — 조회 함수가 `makedirs()` 를 부르던 과거의 잔재다.
  `doc_paths.py` / `image_assets.py` 둘 다 이미 경로 계산과 생성을 분리해 뒀다(재발 없음).
  정리는 승인 영역.
- **`sido='서울'` 인데 서울 자치구가 아닌 행 3건** — 전부 자동차 경매이고 `full_address` 가
  "사용본거지 : 인천광역시 계양구 ..." 형태다. 2,444행 중 3건. 기록만 남긴다.

## 7. 승인이 필요해 하지 않은 것

| 항목 | 왜 필요한가 | 왜 여기서 못 하나 |
|---|---|---|
| `.env` 에 `SUPABASE_JWT_SECRET` 추가 | 이것 하나로 `test_auth_jwt` / `test_search` 2건이 붉다. HS256 토큰 검증 전면 불가 | `.env` 운영값은 승인 영역 |
| `.env` 에 `SUPABASE_URL` 추가 | 지금 ES256 검증이 `.env.local` 의 `NEXT_PUBLIC_SUPABASE_URL` 폴백에 걸려 있다. 백엔드만 배포하며 그 파일을 빠뜨리면 **로그인 전원 401** (BUGS #206) | 같음 |
| 중복 인덱스 4개 제거 (migration 021) | `auction_item` 인덱스 17개 중 4개가 완전 중복(`idx_ai_case_no` = `idx_auction_item_case_no`, `idx_ai_auction_date` = `idx_auction_item_auction_date`, `idx_minimum_bid_price` = `idx_auction_item_minimum_bid_price`, `idx_ai_sido` 는 `idx_auction_item_sido_sigungu` 의 접두). **실측: 쓰기 15.1% 빨라지고 계획·지연은 하나도 나빠지지 않는다**(10개 쿼리 전수 대조, `sido` 만 동등한 상위 인덱스로 바뀜) | 스키마 변경(DROP INDEX)은 승인 영역. **`.sql` 파일도 일부러 만들지 않았다** — 미적용 마이그레이션이 디스크에 있으면 `test_schema_hygiene` 가 붉어진다(020 이 정확히 그 상태였다). 승인 시 파일 생성 + 적용을 함께 한다 |
| 병렬 doc_worker | 3절 — 능력 153/일 vs 오늘 공급 262 | 데스크탑1 자원 결정 |
| 스케줄러 등록 / 실크롤·워커 실행 | 4절(92.2%가 "수집중")을 실제로 여는 유일한 방법. 3-a 실측으로 **약 1.8일이면 따라잡는다** | 승인 영역 |
