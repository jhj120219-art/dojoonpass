## 1. 왜 재계산이 불가능하다고 했나 (기존 결론, 정확하다)

판정의 주 입력인 `appraisal_summary`(감정평가요항표 전문)가
**어느 테이블에도 저장되지 않는다** ― 크롤 중 메모리에만 존재한다.

```python
validator/validation_engine.py:74
    appraisal_sido = extract_sido(item.appraisal_summary)
```

전 테이블 컬럼을 다시 확인했다 ― `auction` / `auction_item` 둘 다 없다.
`revalidate.py` 가 있지만 하드코딩 CSV를 읽고 `appraisal_summary=""` 로 넘기며
결과를 DB에 쓰지 않는다. **재검증 경로가 사실상 없다**는 기존 서술은 사실이다.

## 2. ★ 그런데 `address_mismatch` 는 재판정할 수 있다

사유 문자열이 **판정의 양쪽 값을 모두 들고 있다.**

```
"address_mismatch: addr=세종 appraisal=제주"
                        ^^^^          ^^^^
                   주소 쪽 판정    감정요항 쪽 판정
```

주소는 DB에 남아 있다. 그러니 `addr` 쪽만 **지금 함수로 다시 뽑아** `appraisal` 과
비교하면, 그 행이 오늘 규칙으로도 FAIL 인지 알 수 있다. **감정요항 원문이 없어도 된다.**

실 DB의 FAIL **12건 중 11건이 `address_mismatch`** 이므로 사각지대의 대부분이 덮인다.

### 재판정 결과

```
FAIL 12건
  address_mismatch  11건
      지금 규칙으로도 FAIL   9건   <- 진짜 불일치
      지금 규칙으로는 통과   2건   <- 옛 버그(BUGS #78)가 만든 오탐
  auction_date missing  1건
```

오탐 2건은 이렇다.

```
2025타경513824-1  "사용본거지 : 인천광역시 계양구 ... (효성동, 뉴서울아파트)"
                  옛 판정 addr=서울  <- 건물명 "뉴서울아파트"의 '서울'
                  지금    addr=인천  = appraisal 인천  -> 통과

2016타경3104-1    "제주특별자치도 제주시 구좌읍 세화리 산29"
                  옛 판정 addr=세종  <- "세화리"에 걸린 오매칭
                  지금    addr=제주  = appraisal 제주  -> 통과
```

**상세 화면은 이 물건에 "검증실패"를 그대로 띄운다**
(`src/app/properties/[id]/page.tsx:74` 의 `FAIL: '검증실패'`).
둘 다 기일이 지나 기본 검색에는 안 나오지만 직접 URL / 찜 / 최근 본 물건으로는 보인다.

> 이 숫자 **2건**은 `test_pipeline_integrity.py` §12 의 꼬리 주석이 이미
> *"백필로 sido를 고쳐도 저장된 FAIL은 그대로 남는다"* 며 기록해 둔 그 2건이다.
> 내 재판정이 **독립적으로 같은 값**을 냈다 ― 저장소 기록이 또 정확했다.
> `validation_engine.py:40` 의 주석도 이 상황을 정확히 예측하고 있었다:
> *"그 불일치는 address_mismatch 오탐으로 나타나 화면에 '검증실패'로 뜬다."*

## 3. 그래서 남긴 것 ― 사각지대를 가드로 덮었다

기존 결론("재계산 불가")대로라면 이 영역에는 **아무 검사도 둘 수 없었다.**
실제로 §12는 `validation_status` 에 대해 "값이 알려진 범위 안인지만" 봤다.

이제 11/12를 재판정할 수 있으므로 §12에 상한 검사를 더했다.

```
    FAIL 12행 중 address_mismatch 11행
[PASS] 지금 규칙으로는 통과할 FAIL이 늘지 않았다 (현재 2, 상한 2)
      오탐: 2025타경513824-1 (서울->인천 vs 인천)
      오탐: 2016타경3104-1 (세종->제주 vs 제주)
```

**고치지 않고 상한만 둔다** ― §12의 나머지(sido 4 / sigungu 207)와 같은 이유다.
저장값을 바꾸는 것은 백필이고 백필 실행은 승인 영역이다. 여기서 막는 것은 **증가**다:
누가 정규화 규칙을 또 건드려 새 오탐이 생기면 이 검사가 알려준다.
지금까지는 그 변화를 감지할 방법이 **아예 없었다.**

> 구현 중 하나 확인했다 ― `validation_reasons` 는 **레거시 `auction` 에만** 있다.
> `auction_item` 으로는 `validation_status` 만 넘어오고 사유는 동기화되지 않는다.
> 그래서 이 검사만 `auction` 을 읽는다(두 테이블의 PASS/FAIL 건수는 1864/12로 동일).
