# Sprint 235 — 문서 워커 **처리 능력**: 출시 후 조용히 무너지는 쪽

> ## ★ 2026-08-20 Sprint 236 정정 — 이 문서의 핵심 숫자 두 개가 틀렸다
>
> - **'navigate 중앙값 10.9초'는 이동 비용이 아니다.** `법원 선택` 줄 사이의 간격을
>   쟀는데, 그 간격에는 **수집 시간과 sleep 까지** 들어 있다. 즉 **한 행의 전체 주기**다.
>   실측: 행 1개당 **23.2초**(897행/5.8시간), 이동 1회는 **15.2초**.
> - 따라서 **능력 165건/일이 아니라 78건/일**이었다. 이 문서가 *"중앙값 공급 106건은
>   감당한다(여유 36%)"* 라고 적은 것은 사실이 아니다 — **평상시에도 못 따라가고 있었다.**
> - **'batching 4.0배'는 처리량이 아니라 이동 감소 배수**다. 이동은 4배 줄지만 수집과
>   sleep 은 종류마다 그대로 들어, 실제 처리량 이득은 **1.97배**(78 -> 153건/일).
>
> 아래 본문은 그때의 판단 기록으로 남긴다. **숫자는 `SPRINT236_ITEM_BATCHING.md` 를 따른다.**

## 1. 비어 있던 자리 — 정확성은 촘촘한데 **능력**은 아무도 안 봤다

이 저장소에는 큐의 **정확성** 검사가 많다(claim 원자성 / 재시도 / 회수 / 멱등 / 7일 누적).
그런데 **처리 능력**을 보는 검사가 **하나도 없었다.**

출시 후 조용히 무너지는 쪽은 정확성이 아니라 능력이다 —
큐는 정상적으로 쌓이고 워커도 정상적으로 돌지만 **따라잡지 못한다.**
그 상태는 오류를 남기지 않는다. **큐 길이만 매일 조금씩 늘어난다.**

## 3. ★ 능력 vs 공급 — 지금 균형이 어떤가

### 공급은 추정하지 않고 DB 에서 셌다 (`auction_item.crawl_date`)

```
크롤이 실제로 돈 날 20일
  중앙값 106건/일     최대 278건/일 (2026-08-01)
```

### 능력 (실측 상수로 계산)

```
창 02:00~04:00 = 7,200초
doc_type 4종(현재 config) x 10.9초 = 물건당 43.6초
-> 하루 처리 가능 **165건**
```

### 판정

```
중앙값 공급 106건    -> **감당한다** (여유 36%)
최대 공급  278건    -> **밀린다** (부족 113건 — 그날 밀린 것은 다음 날 창을 먹는다)
이론 최대  600건    -> **크게 초과** (MAX_ITEMS 10 x 법원 60, 부족 434건)
```

### ★ image 가 아직 큐에 없다 — 능력은 앞으로 더 떨어진다

```
큐의 실제 doc_type    spec / status / appraisal  (image **0행**)
config DOC_TYPE_LIST  spec / status / appraisal / image
```

지금 큐에 있는 행들은 **image 가 추가되기 전에** 적재된 것이다.
새로 적재되는 물건부터는 4종이 되어 물건당 이동이 3회 -> **4회**가 된다.
그래서 위 계산은 3종(220건)이 아니라 **4종(165건)** 기준으로 했다.

특히 아깝다 — 사진 수집 자체는 상세페이지 DOM 에서 바로 읽어 **0.0초**인데
(Sprint 199 실측), 그것을 위해 **10.9초짜리 이동을 한 번 더** 한다.

## 4. batching 이 바꾸는 것

```
현재    물건당 이동 4회 x 10.9초 = 43.6초  ->  하루   165건
묶으면  물건당 이동 1회 x 10.9초 = 10.9초  ->  하루   661건   (**4.0배**)
```

**4.0배는 이론 최대 공급(600건)까지 덮는다.**

Sprint 199 는 batching 이 **가능하다**는 것을 실브라우저로 실증하고도 구현하지 않았다.
그때 이유는 *"지금 이득이 0이다 — 대기 물건이 2개뿐"* 이었고, 그 판단은 그때 옳았다.
**지금은 이득이 4배다.** 다만 여전히 구현하지 않는다 —

```
claim 단위가 행 -> 물건으로 바뀐다 (Sprint 191 의 경쟁 처리, Sprint 189 의 refresh 보존이
                                    전부 행 단위를 전제로 짜여 있다)
재시도 예산이 행 단위다             (물건 중간에 죽으면 어느 행의 예산을 깎을지 새로 정해야 한다)
```

구조 변경이고 **운영 판단이 필요하다.** 근거만 숫자로 남긴다.

## 5. MAX_ITEMS 와의 관계 — 결론이 분명해졌다

```
MAX_ITEMS=10 x 법원 60 = 이론상 최대 공급 600건/일
현재 능력                              165건/일
                                       -> 초과 434건/일
```

**상한을 올리기 전에 처리 능력을 먼저 올려야 한다.**
지금 상한을 올리면 크롤은 더 많이 가져오지만 문서 큐가 그만큼 밀린다 —
사용자에게는 *"검색에는 뜨는데 문서는 계속 수집중"* 으로 보인다.

정책 변경은 승인 영역이라 **하지 않는다.** 순서가 있다는 사실만 기록한다.

## 6. 회귀 신설 — `test_worker_capacity.py` (15단언)

세 값의 **산술 관계**를 잠근다. 하나만 바뀌어도 능력이 달라지는데 지금은 아무도 안 지켰다.

```
1. 실측 상수가 말이 되는가 (창 > 0, p90 > 중앙값)
2. doc_type 수 = 물건당 이동 횟수
   + **모델 근거를 코드에서 확인** — 워커가 행마다 go_to_case_detail 을 부르는가,
     한 번에 한 행만 claim 하는가 (batching 이 들어오면 여기서 먼저 운다)
3. 능력 vs 실제 공급 (중앙값 감당 / 최대일 부족분 계산)
   + ★ **래칫** — 능력이 기록된 기준선(165건) 아래로 조용히 떨어지지 않는다
4. MAX_ITEMS 이론 최대 vs 능력
5. batching 이득이 doc_type 수와 같은가 (모델 일관성)
6. 큐를 실제로 셀 수 있는가 + config 에 있는데 큐에 없는 종류를 지목
```

### 래칫을 넣은 이유

중앙값(106)만 보면 **doc_type 을 6종까지 늘려도 통과한다**(132건 > 106).
그래서 "기준선보다 나빠지지 않았는가"를 따로 건다. 개선은 언제나 통과하고,
나빠지면 **숫자를 갱신하며 이유를 적게** 만든다.

### 변이 3/3 검출

```
실행 창을 절반으로(120 -> 60분)   -> 능력 83건. 중앙값 검사 + 래칫 **둘 다** FAIL
doc_type 을 하나 추가(4 -> 5종)   -> 능력 132건. **래칫만** FAIL  <- 래칫이 없었으면 놓쳤다
워커의 호출 형태를 바꾼다          -> "모델 근거" FAIL
```

두 번째가 래칫을 넣은 이유를 그대로 보여 준다.

```

     9개 전부 실제 함수 존재
3. 실행 중에 **실제로 호출되는가** (런타임 추적)
     claim_next_queue_item      402회
     mark_queue_skipped_expired 200회

     mark_queue_failed           73회
     enqueue_documents           13회
     reset_stale_queue           13회
     upsert_batch                12회
     refresh_queue_priority       7회

```

**가짜 함수를 부르고 초록불을 내는 상태가 아니다.**
