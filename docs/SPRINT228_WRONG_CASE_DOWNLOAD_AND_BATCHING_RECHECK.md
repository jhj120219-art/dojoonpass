## 1. ★ 다운로드가 어느 사건의 것인지 아무도 확인하지 않았다 (수정)

### 어떻게 발견했나

`audit_asset_integrity.py` 의 [8] 이 남긴 한 줄에서 출발했다.

```
[8] 다운로드 폴더에 남은 고아 파일
    고아 8개 / 14.0 MB
      -> 받아 놓고 목적지로 못 옮긴 것이다. 원인은 수집기 쪽이고,
```

감사는 이것을 **정리 대상**(승인 영역)으로만 적어 두었다. 그런데 파일 **이름**을 보면
정리 문제가 아니라 **코드 문제**의 흔적이다.

```
2023타경118942_..._매각물건명세서(재작성,1)_참여_오해주.pdf
2023타경118942_..._매각물건명세서(재작성,1)_참여_오해주 (1).pdf
2023타경118942_..._매각물건명세서(재작성,1)_참여_오해주 (2).pdf
2023타경118942_..._매각물건명세서(재작성,1)_참여_오해주 (3).pdf     <- 같은 파일이 네 번
2023타경103287_..._매각물건명세서(재작성,6)_참여_김윤회.pdf
HR2025-0609-0001.pdf / JDG231207-2-001.pdf / sw24-041101.pdf      <- 감정평가서(업체 코드)
```

같은 문서를 **네 번 받고 네 번 다 못 옮겼다**는 뜻이다.
`docs/SPRINT199` 도 실행 중에 `spec` 다운로드 타임아웃(30초)을 겪었다고 적고 있다.

### 결함

`crawler/doc_crawler.py:wait_for_download()` 는 이렇게 고른다.

```python
new_files = [f for f in (after_files - before_files) if not ...crdownload]
pdf_files = [f for f in new_files if f.lower().endswith(".pdf")]
candidate = pdf_files[0]
```

**"새로 생긴 PDF" 이면 무엇이든 집는다. 어느 사건의 것인지는 보지 않는다.**

받은 뒤의 검증도 사건과 무관하다.

```
크기가 0보다 크고 두 번 연속 같은가       (wait_for_download)
실제로 PDF 매직 바이트인가                (_looks_like_pdf)
-> 이 사건의 것인가                        **아무도 확인하지 않는다**
```

### 도달 경로

```
1. 사건 A 수집 -> 30초 안에 안 옴 -> 포기(타임아웃). **다운로드는 계속 진행 중**
2. 사건 B 수집 시작 -> before_files 스냅샷 (A 의 것은 아직 .crdownload 라 여기 포함)
3. A 의 다운로드 완료 -> Chrome 이 `A.crdownload` 를 `A.pdf` 로 바꾼다
   -> `A.pdf` 는 before_files 에 없다 = **새 파일**
4. wait_for_download() 가 그것을 집는다 -> **A 의 문서가 B 의 것으로 저장된다**
```

1번(타임아웃)은 실측으로 확인된 사실이고, 고아 파일 8개가 그 흔적이다.

### 왜 결과 검사로는 절대 안 잡히나

저장된 것은 **진짜 PDF** 다. 크기도 정상, 해시도 계산되고, `document_status` 는 READY 가
되고, 화면에서도 정상으로 보이고 열린다. 어떤 무결성 감사도 걸리지 않는다 —
`audit_asset_integrity.py` 의 [1]~[9] 는 전부 통과한다(지금도 통과한다).

**사용자는 다른 사건의 매각물건명세서를 보고 입찰을 판단하게 된다.**
이 저장소가 쫓아 온 "조용한 실패" 중에서 결과가 가장 나쁜 쪽이다.

### 해결 — 확실할 때만 막는다

법원이 내려주는 매각물건명세서 파일명에는 **사건번호가 박혀 있다**(위 실측).
감정평가서는 업체 코드라 **없다**. 그래서 판정을 이렇게 나눈다.

```
파일명에 사건번호가 있다 + 다르다   ->  거부 (확실히 남의 것이다)
파일명에 사건번호가 있다 + 같다     ->  통과
파일명에 사건번호가 없다            ->  통과 (판단할 근거가 없다 - 추측하지 않는다)
```

마지막 줄이 핵심이다. "없으면 거부"로 만들면 **감정평가서 수집이 전부 막힌다.**
모르는 것을 결함으로 단정하지 않는다.

병합 사건(`"2008타경25092 / 2015타경19958"`, 실측 22.7%)은
`crawler/resume.py:case_no_matches_list_entry()` 를 **재사용**해 구성요소 각각과
정확히 비교한다 — 같은 판정을 두 벌 만들면 한쪽만 고쳐진다(이 저장소가 이미 겪은 일).

거부해도 **파일을 지우지 않는다.** 원래 주인이 있는 파일이고, 지우면 그 사건의
재수집까지 잃는다. 고아로 남는 것은 감사 [8] 이 계속 보고한다.

### 회귀 (`test_asset_pipeline.py` 21번 신설, 14검사)

실측 파일명을 그대로 표본으로 쓴다.

```
실제 파일명에서 사건번호 추출 / Chrome 의 " (3)" 중복 접미사에도 동작
★ 다른 사건 -> 거부   같은 사건 -> 통과   사건번호 없음 -> 통과
병합 사건 앞/뒤 각각 통과, 어느 쪽과도 다르면 거부
★ 접두 부분 문자열 함정 양방향 (2024타경1009 vs 2024타경100920)
디렉터리 경로에 든 숫자에 속지 않는다
★ 두 다운로드 경로(spec/appraisal)에 **실제로 배선돼 있는가**
```

마지막 줄을 넣은 이유: 함수만 만들고 부르지 않으면 아무 일도 일어나지 않는다.

### 변이 4/4 검출

```
판정을 무력화(항상 통과)                     -> 3검사 FAIL
정확 비교를 부분 문자열 비교로 되돌린다        -> FAIL
사건번호가 없으면 거부하도록 바꾼다            -> FAIL (감정평가서가 막히는 것을 잡는다)
배선 하나를 떼어낸다                          -> FAIL (2 -> 1)
```

## 2. doc_worker 묶기 — 착수 조건을 다시 쟀다 (구현하지 않음)

Backlog 는 *"실제 병목이 발생하는 조건을 확인한 뒤 구현"* 이라고 지시한다. 확인했다.

`docs/SPRINT199` 는 묶기가 **가능**함을 실증하고도 구현하지 않았고, 그 근거 중 하나가
*"지금 이득이 0 — 대기 중이면서 기일이 남은 물건이 2개뿐"* 이었다.
**문서의 숫자를 믿지 않고 다시 쟀다.**

```
document_queue     pending 2,753 / done 559 / SKIPPED_EXPIRED 186   합계 3,498
대기 + 기일이 남은 물건                    **0개**   (Sprint 199 당시 2개)
한 물건에 대기 행이 2개 이상인 것            0개
묶어서 아낄 수 있는 이동 횟수                0회  -> 절감 0초
```

즉 착수 조건은 **더 나빠졌다.** 2,753개 대기 행이 **전부 기일이 지난 것**이라
워커가 집을 수 있는 실제 작업이 하나도 없다(크롤이 2026-08-12 이후 멈춰 있다).

**구현하지 않는다.** 이득이 0인데 Sprint 189~194 가 막 고친 claim/retry/partial 의
전제(행 단위)를 흔드는 것은 순서가 나쁘다. Sprint 199 의 결론이 그대로 유효하다.

### 곁다리로 확인한 것 — 만료 행이 실제 작업을 굶기는가

2,753개가 앞에 쌓여 있으면 워커가 그것을 훑느라 시간을 다 쓰지 않을까 의심했다.
**추정하지 않고 사본에서 실제 함수로 쟀다.**

```
reconcile_queue_auction_date 1회      0.79 ms   (50회 실측)
claim -> reconcile -> mark 한 바퀴     5.8 ms   (60개 실측)
2,753개 전부 훑기                      약 16.1 초  (외삽)
비교: 문서 1건의 이동 비용             18.2 초
```

**문서 한 건 받는 것보다 싸다.** 굶기지 않는다 — 내 의심이 틀렸다.
고칠 것이 없으므로 고치지 않는다.

## 5. 남은 위험 (정직하게 적는다)

이 방어선은 **파일명에 사건번호가 있을 때만** 동작한다. 감정평가서처럼 없는 종류는
여전히 남의 파일이 섞여도 알 수 없다. 더 확실한 방어는 다음 둘인데 둘 다 이번 범위 밖이다.

```
1. 수집 시작 전에 downloads/ 를 비운다      -> 진행 중인 다른 다운로드를 죽일 수 있다
2. 다운로드를 사건별 하위 폴더로 분리한다     -> Chrome 프로필 설정 변경(승인 영역)
```

지금 한 것은 **확실히 남의 것인 경우를 막는 것**이고, 그것만으로도 관측된 사고 경로
(같은 spec 이 네 번 쌓인 그 상황)는 막힌다.
