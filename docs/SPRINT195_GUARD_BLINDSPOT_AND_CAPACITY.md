## 1. BUGS #133 — 전수 가드가 BOM 파일 16개를 조용히 건너뛰고 있었다

### 발견

Sprint 191/192 에 추가한 두 AST 전수 가드가 이렇게 쓰고 있었다.

```python
with open(path, encoding="utf-8") as fh:
    try:
        tree = ast.parse(fh.read())
    except SyntaxError:
        continue          # <- 여기서 파일이 통째로 사라진다
```

이 저장소 소스 **70개에 UTF-8 BOM** 이 있다. `encoding="utf-8"` 로 읽으면 BOM 이
`﻿` 로 남고 `ast.parse` 가 거부한다. 그걸 `continue` 로 넘기면 **그 파일들이
감사 대상에서 통째로 빠진다.**

### 실측 — 스캔 범위 안에서만 16개

```
crawler/__init__.py            crawler/court_crawler.py      crawler/image_crawler.py
storage/__init__.py            storage/checkpoint.py         storage/database.py
storage/migrate_v4_1.py        storage/migrations/run_migrations.py
api/__init__.py                api/v1/__init__.py            api/v1/doc_stats.py
api/v1/favorites.py            api/v1/item.py                api/v1/recent_items.py
api/v1/registry.py             api/v1/search_presets.py
```

그중 `crawler/image_crawler.py` 에는 **실제 삭제 지점이 3곳** 있었다.
삭제 지점 전수 가드가 "8곳"이라고 보고했지만 진짜는 **12곳**이었다.

즉 Sprint 192 의 "삭제 지점 8곳을 AST 로 분류한 결과 DB 출처는 하나뿐" 이라는 결론은
**결론은 맞았지만 방법이 부실했다** — 안 본 파일이 16개 있었다.

### 이 저장소는 이미 답을 알고 있었다

기존 가드 7개는 **전부 `utf-8-sig`** 를 쓰고 있었다(`test_schema_hygiene.py`,
`test_console_encoding.py`, `test_api_regression.py` …). 새로 추가한 둘만 빠져 있었다.
규칙이 이미 있었는데 새 코드가 그것을 따르지 않은 것이다.

### 해결 — 두 가지를 함께

```
(1) encoding="utf-8" -> "utf-8-sig"
(2) 파싱 실패를 조용히 넘기지 않는다:
    unparsed 목록을 모아 `check("스캔 범위의 모든 파일을 실제로 읽고 팠다", unparsed, [])`
```

(2)가 핵심이다. **"결함이 없어서 통과"와 "안 봐서 통과"는 겉으로 같다.**
못 본 파일이 하나라도 있으면 그 검사의 결론 자체가 성립하지 않는다.

### 변이 검증 — 두 번

```
BOM 파일에 결함 주입   storage/database.py 에 shutil.move 삽입
                       -> 수정 전: 안 보임 / 수정 후: FAIL (storage/database.py:1265)
파싱 불가 파일 주입     crawler/resume.py 를 깨뜨림
                       -> 두 가드 모두 FAIL ("crawler/resume.py (SyntaxError)")
```

수정 전이었다면 첫 번째 결함은 **영원히 안 잡혔다.**

## 3. BUGS #134 — `REFRESH_MAX_ITEMS_PER_RUN = 300` 은 실행 창의 400% 였다

### 근거 없이 정해진 숫자였다

Sprint 189 가 상한을 도입하며 300 을 적었는데, **그 숫자의 근거는 어디에도 없었다.**
문서에도 "아직 실측 근거가 없는 값"이라고 적혀 있었다. 이번에 쟀다.

### 실측 (실행 창 02:00~04:00 = 7,200초)

```
기일 경과 적체 2,733행 소진   14초   (브라우저 없이 5.1ms, continue 로 sleep 도 건너뜀)
한 번도 못 받은 물건 20행      480초  (24초/행 = 이동 15.2 + 수집 + sleep 2)
                              ------
남는 예산                      6,706초
재수집 1물건의 최악            4행 (spec/status/appraisal/image 동시)
-> 최악 기준 상한              6,706 / (4 x 24) = 69 물건

옛 값 300 의 최악 소요         300 x 4 x 24 = 28,800초 = 8.0시간 = 창의 400%
```

**최악 기준으로 잡는다** — 어느 필드가 바뀔지 미리 알 수 없고, 여러 필드가 한꺼번에
바뀌는 날이 바로 재수집이 가장 필요한 날이다. 69 에서 여유를 두고 **60** 으로 정했다
(최악 5,760초 = 창의 80%).

### 모델을 코드로 검증했다

처음 계산은 기일 경과 행에도 `sleep(2)` 를 더해 **5,480초**가 나왔다. Sprint 146 의
실측치(13.9초)와 맞지 않아 코드를 다시 읽으니, 그 분기는 `continue` 로 루프 끝의
sleep 을 건너뛰고 있었다(`doc_worker.py:328`). **모델은 실측과 코드 양쪽에 맞아야 한다.**

### 숫자가 아니라 산술을 고정했다

`test_refresh_trigger.py` §17 이 네 상수의 관계를 검사한다.

```
REFRESH_MAX_ITEMS_PER_RUN x (물건당 최악 행 수) x DOC_COLLECT_SECONDS_PER_ROW
    <= (DOC_WORKER_END_TIME - DOC_WORKER_START_TIME)
```

숫자만 바꾸면 다음에 누가 창을 줄이거나, 수집이 느려지거나, 재수집 대상 종류를 늘리면
**조용히 다시 넘친다.** 변이 검증: 60 -> 300 으로 되돌리면 즉시 2건 FAIL(400% 진단 포함).

**이 검사가 잡지 못하는 것**도 적어 뒀다 — `DOC_COLLECT_SECONDS_PER_ROW` 는 실측을
사람이 옮겨 적은 값이라, 실제 수집이 느려졌는데 상수를 안 고치면 검사는 통과하면서
현실은 넘친다.

## 6. doc_worker 비용 구조 — 이동이 63%다

### 실측

```
행당 24.0초 =  이동 15.2  +  수집 6.8  +  sleep 2.0
                (63%)
```

`doc_worker` 는 큐 **행 단위**로 돈다. 같은 물건의 doc_type 마다 따로 claim 하고,
그때마다 `go_to_case_detail()` 로 **같은 상세페이지에 다시 들어간다.**
사건 단위 문서(status)의 형제 재사용은 **다른 물건** 사이에서만 동작하고,
같은 물건 안의 doc_type 사이에는 적용되지 않는다.

```
물건 하나를 4종 전부 수집할 때
  현재  4 x (15.2 + 6.8 + 2.0) = 96.0초
  이론  15.2 + 4 x (6.8 + 2.0) = 50.4초
  차이  45.6초/물건 (47% 절감 여지)
```

### 착수하지 않는 이유

물건 단위로 묶으려면 `doc_worker` 의 루프 구조(행 단위 원자적 claim)를 바꿔야 하고,
그것은 claim 원자성·재시도 예산(`MAX_DOC_RETRY` 는 행 단위다)·부분 실패 처리와 전부
얽혀 있다. Sprint 189~194 가 그 셋을 각각 고쳐 놓은 직후에 구조를 흔드는 것은
위험 대비 이득이 나쁘다.

**그리고 지금은 얻을 것도 없다** — 대기 중이면서 기일이 남은 물건이 **2개**뿐이다.
이 최적화가 의미를 갖는 것은 스케줄러가 돌아 큐가 다시 수천 행으로 자란 뒤다(BUGS #123).

`DOC_COLLECT_SECONDS_PER_ROW = 24.0` 은 **현재 구조 기준값**이라고 상수 주석에 적어 두었다.

### 재시도 비용

```
실패 1건 = 최대 3회 x 24.0초 = 72초를 쓰고 결과는 0
현재 failed 행 0개 / FAILED 물건 1개(2022타경55450-7, 기일 2026-07-06 경과)
```

## 8. 문서의 "원래 없음" — 신뢰할 positive signal 이 **없다**

### 사진과 문서는 구조가 다르다

```
사진   상세페이지 DOM 에 base64 로 박혀 온다.
       -> "요소가 하나도 없다" = 법원이 안 준다는 **양성 신호**  (no_asset)
       -> "요소는 있는데 alt 규칙에 하나도 안 맞는다" = DOM 변경 **실패**
       두 단계로 구분한다.

문서   버튼을 눌러야 나온다. 버튼 id 는 `config/settings.py:get_doc_button_id()` 의
       **정적 표**에서 오고 DOM 에서 읽지 않는다.
       -> "버튼을 못 찾았다" 는 (a) 법원이 그 문서를 안 준다 (b) DOM 이 바뀌었다
          (c) 페이지가 덜 떴다 를 **구분하지 못한다.**
```

### 확인해 봤지만 근거를 얻을 수 없었다

양성 신호를 찾으려면 "문서가 원래 없는 물건"을 실제로 열어 DOM 을 봐야 한다.
현재 데이터에서 그 후보는 FAILED 물건 하나뿐인데(2022타경55450-7),
**기일이 2026-07-06 로 지나 법원 사이트에서 조회 자체가 안 된다**
(기일 경과 사건은 사건번호 직접검색으로도 안 나온다 — Step 13/14 실측).

### 판단

**새 상태를 만들지 않는다.** 지금 만들 수 있는 것은 "버튼을 못 찾았다"를 "원래 없음"으로
단정하는 것뿐이고, 그것은 DOM 변경으로 전 물건의 문서가 사라진 날 **조용히 "원래 없음"으로
기록**하는 최악의 실패 방식이 된다. 목표 문서의 원칙 그대로다 —
*"없는 문서를 만들어내지 않는다."*

필요한 선행 작업(승인/데이터 확보 뒤):
```
1. 스케줄러 등록 후 기일이 남은 물건에서 FAILED 가 쌓이는지 관찰
2. 그중 하나를 실제로 열어 버튼 컨테이너는 있는데 특정 버튼만 없는지 확인
   -> 있으면 그것이 사진의 no_asset 에 대응하는 두 단계 신호가 된다
3. 그때 비로소 상태를 논의한다
```
