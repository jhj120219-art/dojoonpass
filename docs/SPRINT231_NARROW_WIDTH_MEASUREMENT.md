# Sprint 231 — 좁은 폭 레이아웃을 처음으로 **실측**했다

**날짜** 2026-08-20. 코드 변경 없음(측정 + 기록). 운영 DB 무접근.

---

## 0. 왜 그동안 못 쟀나

Sprint 219 이래 이 저장소는 *"모바일에서 깨지지 않는다는 것은 아직 주장할 수 없다"* 를
계속 적어 왔다. 측정 경로가 전부 막혀 있었기 때문이다.

```
resize_window(390x844)   호출은 성공하지만 innerWidth 가 안 바뀐다   (Sprint 223)
iframe 에 앱을 띄우기     X-Frame-Options: DENY 에 막힌다            (Sprint 224)
실기기                    승인 영역
```

이번에도 **다시 확인했다**(문서를 믿지 않는다).

```
resize_window(390, 844) -> "Successfully resized ... to 390x844"
그 직후 실측    innerWidth 1568 / outerWidth 1920
                matchMedia('(min-width: 768px)') -> true   (md: 가 여전히 적용된다)
-> 결론 변동 없음: 뷰포트는 못 줄인다
```

---

## 1. 그래서 다른 각도로 쟀다

뷰포트를 줄일 수 없다면, **서브트리를 고정 폭 컨테이너에 복제해** 브라우저에게
그 폭에서의 레이아웃을 진짜로 계산시키면 된다.

```js
const box = document.createElement('div')
box.style.cssText = `position:fixed;left:-9999px;top:0;width:${w}px`
const clone = el.cloneNode(true)
box.appendChild(clone); document.body.appendChild(box)
const overflow = clone.scrollWidth - w        // > 0 이면 그 폭에서 넘친다
box.remove()
```

이것은 **가짜 계산이 아니라 진짜 레이아웃**이다 — 브라우저가 실제로 줄바꿈·축소·
`min-content` 를 계산해서 `scrollWidth` 를 준다.

### ★ 한계를 먼저 못 박는다

복제본도 **실제 뷰포트(1568px)** 로 미디어쿼리를 평가한다.
그래서 `md:` / `xl:` 접두사가 붙은 **열 수 변화는 재현되지 않는다.**

실제로 이 함정에 한 번 걸렸다 — 결과 그리드가 288px 안에서 **157px 넘친다**고 나왔다.

```
grid gap-4 md:grid-cols-2 xl:grid-cols-3 items-start   -> 288px 안에서 3열을 그리려 했다
```

진짜 390px 화면에서는 `md:` 가 적용되지 않아 1열이 된다. **결함이 아니라 기법의 한계다.**

```
쓸 수 있는 대상   자기 안에 반응형 열 클래스를 갖지 않는 서브트리
                  (결과 카드, 상세 카드, 버튼 줄 …)
쓸 수 없는 대상   md:/xl: 로 열 수가 바뀌는 컨테이너
```

## 2. 실측 결과 — 넘치는 곳이 없다

`over` = 그 폭에서 넘친 픽셀. 0 이면 그 폭에 들어간다.

### 검색목록 (`/search?include_closed=true`, 총 1,876건)

```
결과 카드 20개
  320px 화면(가용 288)   초과 0개
  360px 화면(가용 328)   초과 0개
  390px 화면(가용 358)   초과 0개
```

### 상세페이지 (`/properties/505`)

Sprint 219 가 *"목록보다 나쁘다. 사용자가 실제로 판단을 내리는 화면"* 이라고 지목한 곳이다.

```
잰 카드 10개 (물건 요약 / 가격 / 물건 사진 5장 / 권리분석 / 신뢰도 …)
  320px · 360px · 390px   전부 초과 0개
```

### 마이리스트 내보내기 줄 (Sprint 227 에서 내가 넣은 것)

버튼 둘 + 상태 메시지가 한 줄에 있어 좁은 폭에서 넘칠 것으로 **의심했다.**
가장 긴 실패 문구를 넣고 쟀다.

```
'복사하지 못했습니다 — 브라우저가 클립보드 접근을 막았습니다'

390px(가용 358)   필요 358 / 초과 0   줄 높이 58px
360px(가용 328)   필요 328 / 초과 0   줄 높이 78px  (문구가 줄바꿈됐다)
320px(가용 288)   필요 288 / 초과 0   줄 높이 78px
구성  [CSV 내려받기 77px] [복사 42px] [상태 문구 224px]
```

**내 의심이 틀렸다.** 상태 문구가 flex 안에서 축소되고 한글이 글자 단위로 줄바꿈되어
어느 폭에서도 넘치지 않는다. 산술로 추정했으면 "넘친다"고 잘못 보고했을 것이다 —
**추정하지 말고 재야 하는 이유**가 그대로 나왔다.

## 3. 이제 말할 수 있는 것과 여전히 말할 수 없는 것

```
말할 수 있다    결과 카드 / 상세 카드 / 내보내기 줄은 320px 폭에서도 **가로로 넘치지 않는다**
                (브라우저가 계산한 진짜 레이아웃 기준)

말할 수 없다    md:/xl: 로 열 수가 바뀌는 지점의 동작
                실제 모바일 브라우저의 폰트 렌더링/터치 동작
                실기기에서의 스크롤·확대 체감
```

기존 가드(`test_frontend_accessibility.py` 5번)는 여전히 **"넘칠 원인이 없다"** 를
소스에서 확인한다(고정 폭 · `w-screen` · `min-w-max` · 반응형 접두사 없는 3열 · `<table>`).
이번 실측은 그 가드가 **실제 레이아웃에서도 참임을 처음으로 뒷받침**한다.
둘은 대체 관계가 아니라 보완 관계다 — 가드는 상시 자동, 실측은 사람이 돌릴 때.
