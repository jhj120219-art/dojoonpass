## 1. ★ 먼저 발견한 것 — Sprint 235 의 측정이 틀렸다

batching 을 구현하기 전에 지시대로 *"이전 문서의 숫자를 그대로 믿지 않고"* 다시 쟀다.

Sprint 235 는 `logs/doc_run.log` 의 `법원 선택` 줄 사이 간격을 **navigate 비용(10.9초)**
이라고 적었다. 그런데 그 간격에는 **수집 시간과 sleep 까지 들어 있다.**
즉 그것은 이동 비용이 아니라 **한 행의 전체 주기**였다.

같은 로그를 구간으로 분해했다.

```
법원선택 -> 결과          중앙값 14.1초  (652구간)  이동의 뒷부분 + 그 종류의 수집
결과 -> 다음 법원선택      중앙값  9.2초  (647구간)  sleep 2초 + 이동의 앞부분
                                                   최소 9.1 / p90 9.3 - 매우 일정
법원선택 -> 법원선택       중앙값 23.9초  (899구간)  = 위 둘의 합
```

그리고 **모델 없이 잴 수 있는 것**을 따로 쟀다. 나눗셈 하나라 논쟁의 여지가 없다.

```
의미 있는 실행 7회 합계   행 897 / 이동 897 / 물건 313 / 5.8시간
  -> 행 1개당 **23.2초**
  -> 행/이동 = **1.00** (7회 전부)   <- 예전 코드는 행마다 이동했다
```

**Sprint 235 의 결론 두 개가 모두 틀렸다.**

| | Sprint 235 | Sprint 236 실측 |
|---|---|---|
| 이동 1회 비용 | 10.9초 | **15.2초** (아래 참조) |
| 현재 능력 | 165건/일 | **78건/일** |
| batching 이득 | 4.0배 | **1.97배** |

이동 1회 비용 15.2초는 **Sprint 147 이 형제 재사용 이득을 재며 독립적으로 측정한 값**이다.
이번 구간 분해가 주는 16.4초와 일치한다 — 서로 다른 두 측정이 같은 값을 가리킨다.
둘 중 **작은 쪽**을 채택했다: 이득을 부풀리지 않기 위해서다.

★ 그래서 능력은 165건이 아니라 **78건/일**이었다. 실측 공급 중앙값(106건)조차
**감당하지 못하는 상태**였다. Sprint 235 는 "평상시는 여유 36%"라고 적었다.

## 2. ★ 그리고 더 나쁜 것 — 가드가 자기 목적을 배신하고 있었다

Sprint 235 는 `test_worker_capacity.py` 에 "모델 근거" 검사를 넣으며 이렇게 적었다.

> *"이 관계가 깨지는 유일한 경우는 batching 을 넣었을 때이고, 그때는 이 검사도
> 함께 고쳐야 한다(**그게 이 검사의 목적이다**)."*

이번에 batching 을 넣었다. 그런데 **그 검사는 초록불을 유지했다.**

```python
check_true("워커는 한 번에 한 행만 claim 한다(모델 근거)",
           "claim_next_queue_item()" in src, ...)
```

`doc_worker.py` 에서 그 함수 호출은 전부 사라졌는데도 통과했다. 이유:

```
doc_worker.py:266   # 판단은 `claim_next_queue_item()`이 이미 했다(어휘를 여기서...)
                    ^^^ 주석이다
```

**주석 한 줄에 걸려 있었다.** 같은 파일의 다른 검사도 마찬가지였다 —
`"go_to_case_detail(driver, court_code, case_no, item_no" in src` 는 새로 만든
`_ensure_detail_page()` **안쪽의 호출**에 걸려 통과했다. 워커가 행마다 이동하는지는
전혀 보지 않은 것이다.

이 저장소가 함정 목록에 적어 둔 *"주석/문자열을 코드로 오인"* 과
*"grep 결과만으로 실행 경로 판정"* 을, 그 목록을 아는 상태로 만든 검사가 그대로 밟았다.
**공허한 가드는 없는 가드보다 나쁘다** — 없으면 불안하기라도 하다.

## 3. 구현 — claim 단위만 바꾼다

호출 그래프를 먼저 관통했다(grep 으로 결론 내지 않았다).

```
claim_next_queue_item()   CAS UPDATE ... WHERE id=? AND status=?   원자적 claim
                          경쟁에서 지면 **다른 행을 다시 조회**(Sprint 191/BUGS #130)
                          waiting -> claimed 사상은 QUEUE_CLAIM_STATUS 가 쥔다
mark_queue_done/failed    전부 queue_id 단위. retry_count 는 **행의 것**이다
reset_stale_queue         in_progress 회수 시 retry_count 를 건드리지 않는다
collect_document          새 창을 열고 닫은 뒤 main_handle 로 **돌아온다**
                          (doc_crawler.py 의 finally 두 곳, 전부 try/except: pass)
image_crawler             driver 사용처가 `find_elements` 한 줄 - 페이지를 떠나지 않는다
```

### 새 함수 (`storage/database.py`)

```python
claim_next_item_rows(max_rows=QUEUE_BATCH_MAX_ROWS)   # 한 물건의 행을 한꺼번에
release_queue_rows(queue_ids)                          # 시도하지 않은 행을 되돌린다
```

첫 행은 **기존 `claim_next_queue_item()` 을 그대로 부른다.** 어떤 행을 먼저 볼지,
재시도 간격, 경쟁 재조회까지 **판단을 복제하지 않기 위해서다** — 그 어휘가 두 곳에
생기면 한쪽만 고쳐지는 날이 온다. 형제 행은 같은 CAS 로 best-effort claim 한다.

★ **형제에도 재시도 간격을 똑같이 건다.** 묶어 온다는 이유로 그 규칙을 건너뛰면
같은 실행 안에서 같은 행을 연달아 태워 재시도 예산 3회를 몇 분 만에 태운다.

### 워커 (`doc_worker.py`)

기존 분기(기일경과 / 버튼미지원 / 형제복사 / 부분성공 / 재시도)는 **한 줄도 바꾸지 않았다.**
바뀐 것은 네 곳뿐이다.

```
1. 루프가 묶음 버퍼에서 행을 꺼낸다 (claim 단위만 바뀐다)
2. go_to_case_detail() -> _ensure_detail_page()   이미 서 있으면 이동하지 않는다
3. 드라이버 재시작 시 page.clear()                 기억을 버린다
4. finally 에서 시도하지 않은 행을 release          방치하지 않는다
```

### ★ 재사용은 **믿지 않고 확인한다**

"아까 들어갔으니 아직 그 페이지일 것"이라고 가정하지 않는다. 문서 수집기의 창 복구는
전부 `try/except: pass` 라 실패할 수 있고, 그대로 다음 종류를 처리하면
**엉뚱한 화면에서 남의 문서를 긁는다.** 그래서 재사용 전에 `wait_for_detail()` 로
화면을 실제로 확인한다 — 이미 그 페이지면 첫 폴에서 곧바로 True 라 비용이 사실상 없다.

### ★ 사진을 **먼저** 처리한다

사진만 `require_exact_item=True` 로 들어가야 한다(버튼이 없어 페이지에 그려진 것을
그대로 읽으므로 물건이 틀리면 사진도 틀린다 — Sprint 230). 사진을 먼저 처리하면
그 **엄격한** 이동 한 번을 나머지가 재사용한다. 반대 순서면 느슨하게 들어갔다가
사진 차례에 다시 들어가야 해서 이동이 2회가 된다.

엄격한 페이지는 느슨한 요구에도 쓸 수 있지만 **그 반대는 안 된다.**

## 4. 결과 — 실측

### 이동 횟수 (구조적 사실, 시간이 아니라 **횟수**를 셌다)

`test_worker_batching.py` 가 **진짜 `doc_worker.main()`** 을 돌린다. 브라우저와
수집기만 가짜고 claim / 순서 / 재사용 / 종결은 전부 제품 코드다.

```
물건 12개 x 4종 = 큐 48행
  예전(로그 실측: 행마다 1회)   이동 48회
  지금                          이동 **12회**   = 물건당 정확히 1회
  수집 횟수                     48회 -> 48회    (일을 덜 한 것이 아니다)
```

### 처리량 (이동 감소 != 처리량 증가)

```
예전  이동 4회 x 15.2초 + 4종 x 8.0초 = 92.8초  ->  하루  78건
지금  이동 1회 x 15.2초 + 4종 x 8.0초 = 47.2초  ->  하루 153건
                                                    -> **1.97배**
```

★ **이동은 4배 줄지만 처리량은 2배다.** 수집과 sleep(행당 2초)은 종류마다 그대로
들기 때문이다. Sprint 235 가 그 둘을 구분하지 않아 4.0배라고 적었다 —
그 숫자는 처리량이 아니라 **이동 감소 배수**였다. 이제 검사가 그 혼동을 막는다:

```python
check_true("★ 처리량 이득이 이동 감소 배수보다 작다(수집/sleep 은 남는다)",
           gain < nav_ratio, ...)
```

### 공급 대비

```
하루 능력 153건
공급 중앙값 106건  ->  **감당한다** (예전 78건으로는 감당하지 못했다)
공급 최대   278건  ->  여전히 밀린다 (부족 125건)
이론 최대   600건  ->  크게 초과
```

**batching 이 고친 것은 "평상시조차 못 따라가던" 상태다.** 최대일은 아직 아니다.

## 5. 실행 창 / MAX_ITEMS 재평가 (계산만, 정책 무변경)

```
최대 공급일(278건)을 덮으려면 창 **3.6시간** 필요 (지금 2.0시간)
  -> 02:00 시작이면 **05:38** 까지.  06:00 일일 크롤 전에 **끝난다**
```

즉 창 확대는 크롤과 충돌하지 않는 선에서 **가능하다.** 다만 Task Scheduler 의
`ExecutionTimeLimit` 이 4시간이라 여유가 크지 않다. 정책 변경은 승인 영역이라
**하지 않았다.**

`MAX_ITEMS` 는 **올리지 않는다.** 이론 최대 600건은 능력 153건을 여전히 4배 넘는다.
다만 이론 최대는 *"모든 법원이 매일 상한까지 채우는"* 경우이고, 실측 공급 중앙값은
106건이다. 그래서 지금 상한이 실질적 병목은 아니다 — **먼저 필요한 것은 창 확대다.**

### 큐 현황 (운영 DB, 읽기 전용)

```
큐 3,498행 / 대기 2,753행 / 대기 물건 **944개**
-> 능력 153건/일 기준 소진에 약 **6.2일**
```

## 6. 변이 테스트

### batching 가드 **8/8**

```
M1 페이지 재사용 제거        -> 이동 48회 (12 기대)          FAIL
M2 느슨한 페이지를 사진이 재사용 -> 사진 정확일치 가드          FAIL
M3 사진을 맨 뒤로 (정렬 뒤집기) -> 이동 24회                   FAIL
M4 시도않은 행을 안 되돌림     -> in_progress 3행 방치          FAIL
M5 재시작 후 페이지 기억 유지   -> page.clear() 부재            FAIL
M6 형제에 재시도 간격 미적용    -> 방금 실패한 형제를 집는다      FAIL
M7 물건 키 대신 아무 행이나 묶음 -> 이동 24회                   FAIL
M8 종결 행이 나오면 묶음 폐기    -> 나머지가 in_progress 로 버려짐 FAIL
```

★ M2 는 batching 검사만으로는 잘 드러나지 않는다(정렬이 사진을 앞에 두어 실제로는
엄격한 이동만 일어난다). 그 변이를 직접 겨냥한 가드는 `test_asset_pipeline.py` 에
있으므로 **두 파일을 함께** 돌려서 확인했다.

★ 처음에 M4/M5 가 "앵커 없음"으로 조용히 건너뛰어졌다(CRLF 파일에 `\n` 앵커).
**건너뛴 것을 잡은 것으로 세면 변이 테스트 자체가 공허해진다** — 정규화해서 다시 돌렸다.

### 처리 능력 가드 **5/5** (그중 하나는 *통과해야* 정상)

```
C1 페이지 재사용 제거     -> "종류가 4개여도 이동은 1회다(실제 호출)"  FAIL
C2 행 단위 claim 복귀     -> "옛 모델의 흔적이 코드에 없다"           FAIL
C3 실행 창 절반           -> 능력 계산 붕괴                          FAIL
C4 doc_type 추가          -> 래칫(152건) 130 < 152                   FAIL
C5 옛 이름을 **주석**에 삽입 -> **통과**  <- 주석을 코드로 읽지 않는다
```

C5 가 이번 수정의 핵심이다. 같은 문자열을 주석에 넣으면 통과하고 코드에 넣으면
실패해야 **"주석을 무시한다"가 증명된다.** 한쪽만 보면 검사가 그냥 죽은 것과
구별되지 않는다.

## 8. 곁다리 — 저장소 가드가 내 코드를 두 번 잡았다

```
[FAIL] %-포맷 SQL 에 새 템플릿 없음: ('storage/database.py',
       'UPDATE document_queue SET status=? WHERE status=? AND id IN (%s)')
```

`IN (%s)` 로 물음표만 채우는 것은 안전하지만 **검사기는 그것을 구별할 수 없다.**
예외 목록에 넣어 가드를 무디게 만드는 대신 **동적 SQL 자체를 없앴다** — 한 번에
되돌리는 행은 많아야 8개라 반복문으로 충분하다.

그리고 fixture 를 `init_db()` 만으로 세웠다가 `mark_queue_done()` 이 매번 예외로
떨어졌다. 워커는 그것을 "수집 실패"로 처리하고 드라이버를 재시작했고, 그러면
페이지 기억이 지워져 **이동이 줄지 않은 것처럼 보였다.** 검사의 "공허하지 않다"
가드가 먼저 울어서 알았다. 이제 fixture 가 실제 부트스트랩 3단계를 쓰고,
필요한 테이블이 없으면 **즉시 죽는다.**
