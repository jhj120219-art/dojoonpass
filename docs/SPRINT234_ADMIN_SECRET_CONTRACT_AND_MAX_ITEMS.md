## 1. P0 — Admin Secret: 설정 로딩 경로 전수 Audit

### 실효 상태 (값은 열람하지 않고 이름/길이만)

```
SUPABASE_JWT_SECRET                       설정됨(88자)     <- 로그인 사용자 API 는 살아 있다
SUPABASE_URL / NEXT_PUBLIC_SUPABASE_URL   설정됨(40자)
ADMIN_API_KEY                             **이름 없음**
SUPER_ADMIN_API_KEY                       **이름 없음**
PAYMENT_WEBHOOK_SECRET                    **이름 없음**
```

### ★ 여기서 도구가 두 번 틀렸다

```
1차: load_dotenv() 없이 os.getenv        -> 앱은 .env 를 로드한다. 무효
2차: 스크래치에서 load_dotenv() 인자 없이 -> find_dotenv() 는 **호출한 파일의 디렉터리**부터
     훑는다. 스크립트가 scratchpad 에 있어 저장소 .env 를 못 찾고
     "SUPABASE_JWT_SECRET 이름 없음"이라는 **거짓 결과**를 냈다
3차: 경로를 명시                          -> 88자로 정상 확인
```

2차에서 멈췄다면 *"인증이 통째로 죽었다"* 는 **없는 P0** 를 보고했을 것이다.

### 필수 / 선택 구분 (코드 근거)

```
필수  SUPABASE_JWT_SECRET      없으면 HS256 검증 불가 -> 로그인 사용자 API 전체
      ADMIN_API_KEY 계열       없으면 /admin/* 전부 500
선택  CORS_ALLOW_ORIGINS(''), LOG_LEVEL('INFO'), PAYMENT_PROVIDER('mock'),
      DOC_WORKER_TEST_MODE     — 전부 코드에 기본값이 있다
```

### startup validation 은 **없다**

`api_server.py` 에 startup 훅이 없고, 언급하는 환경변수는 `CORS_ALLOW_ORIGINS` /
`LOG_LEVEL` 뿐이다. 즉 **필수 Secret 이 비어도 서버는 정상 기동**하고, 그 사실은
그 기능을 실제로 부를 때서야 드러난다(Admin 500 / 인증 401).

> 기동 시 경고를 띄우는 것은 개선안이지만, **운영 기동 동작을 바꾸는 변경**이라
> 이번에는 넣지 않았다(§6 개선안에 남긴다).

## 2. Admin 500/403/200 계약 — 회귀 신설 (`test_admin_secret_contract.py`, 30검사)

`test_api_regression.py` 31-B 가 *"두 키 모두 없으면 500"* 과 *"되돌리면 200"* 은 이미
잠그고 있었다. **비어 있던 것은 그 사이의 상태들**이다.

```
1. 키가 하나도 없을 때          헤더 유무와 무관하게 500 / 응답에 키 값이 실리지 않는다
2. ★ 키는 있는데 틀린 키        **403** (500 도 200 도 아니다)  <- 비어 있던 자리
   헤더 자체가 없을 때           403
   대조군: 맞는 키               200 (검사가 공허하지 않다)
3. ★ 등급 분리                  ADMIN 키로 SUPER 라우트 -> 403
                                SUPER 키로 ADMIN 라우트 -> 200 (포함 관계)
                                SUPER 미설정이어도 SUPER 라우트는 열리지 않는다
4. ★★ Secret 부재가 일반 사용자 API 에 영향을 주지 않는다
      공개    /search /stats /plans                        200
      인증    /favorites /recent-items /search-presets
              /subscriptions/me (토큰 있음)                 200
      토큰 없음 -> 401 (500 으로 바뀌지 않는다)
      대조군: 같은 조건에서 Admin 만 500
5. ★ Admin 라우트 **전체**(OpenAPI 에서 16개 추출)가 같은 가드를 지난다
      키 없이 500 이 아닌 라우트 0개 — 하드코딩 목록을 쓰지 않는다
```

4번이 이 파일의 핵심이다. Admin 키는 운영자용인데 그것이 없다고 로그인 사용자의
관심물건/검색까지 죽으면 **장애 범위가 완전히 달라진다**(운영 불편 -> 서비스 장애).
지금 이 환경이 정확히 그 상태라 **가정이 아니라 현재 상태를 그대로 확인**했다.

### 원칙 — 운영 Secret 을 만들지 않는다

키는 **이 프로세스 환경에만** 주입하고 끝나면 되돌린다. `.env` 는 읽지도 쓰지도 않는다.

### 변이 4/4 검출

```
등급 검사를 끈다                     -> ADMIN 키로 SUPER 작업 가능해진다  FAIL
키 미설정 가드를 끈다                -> 500 이 403 으로 바뀐다            FAIL
틀린 키를 거부하지 않는다             -> 403 이 사라진다                   FAIL
헤더가 없으면 최고 등급을 준다(치명적) -> 403 이 200 이 된다                FAIL
```

마지막 변이는 **인증 없이 관리자 권한**이 되는 최악의 경우다. 잡힌다.

## 3. MAX_ITEMS = 10 — 추측 없이 실측

### 상한에 실제로 걸린 적이 있는가 (`logs/daily_run.log`)

```
"목록 수집 완료: N건" 관측 104회
  10건 12회  <- 상한 도달 (11.5%)
   9건 14회 / 7건 16회 / 4건 16회 / 1건 14회 ...
```

**11.5% 는 무시할 수 없다.** 다만 정확히 10건이라 잘림이 없었을 수도 있어
*"12회가 전부 잘렸다"* 로 읽으면 안 된다 — 로그만으로는 구분되지 않는다.

### DB 쪽에서 본 상한 밖 물건

```
(법원, 매각기일) 조합 316개 중 10건 초과 14개 (4.4%)
앞 10건 밖 물건 31건 / 전체 1,875건 (1.7%)
```

### 비용 (로그 타임스탬프에서 계산)

```
물건 1건당 크롤   중앙값 3.5초 (최소 1.5 / 최대 17.0, 구간 104개)
등록 법원         60개
최악의 추가 시간   MAX_ITEMS=20  +2,077초 (0.6시간)
                  MAX_ITEMS=30  +4,154초 (1.2시간)
                  MAX_ITEMS=50  +8,309초 (2.3시간)
```

'최악' 은 **모든 법원이 상한만큼 갖고 있다고 가정**한 값이다. 실제 분포는 대부분
10건 미만이라 훨씬 작다 — 상한을 올려도 **없는 물건을 만들지는 않는다.**

### 실행 창과의 관계 — 여기가 진짜 제약이다

```
일일 크롤에는 **명시적 종료 시각이 없다** (DocWorker 의 DOC_WORKER_END_TIME 같은 개념 없음)
-> 실제 상한은 스케줄러의 ExecutionTimeLimit 4시간
   MAX_ITEMS=20 (최악 +0.6h) 은 4시간 안에 들어간다
```

**그런데 일일 크롤만의 문제가 아니다.**

```
물건 1건이 늘면 document_queue 행이 **4개** 늘어난다 (spec/status/appraisal/image)
그 큐는 02:00~04:00 = **120분** 창에서 소진된다
```

두 창을 함께 보지 않고 상한만 올리면 **큐가 소진되지 않고 쌓인다.**

### 결론 — 바꾸지 않았다

수치는 갖췄지만 *"물건을 더 많이 볼 것인가 vs 문서 수집 창을 늘릴 것인가"* 는
**제품·운영 판단**이다. 승인 영역이라 정책은 그대로 두고 근거만 남긴다.

## 4. 큰글씨 — 기술적 장애물 재측정

디자인은 정하지 않는다. **막고 있는 구조**만 찾는다.

```
글자 px 고정  text-[NNpx]        **0개**   <- Sprint 223 의 rem 전환이 유지되고 있다
줄간격 px     leading-[NNpx]     **0개**
인라인 fontSize px               **0개**
높이 px 고정  h-[NNpx]            1개  -> properties/[id]:787 `max-h-[420px]`
```

그 1개를 확인했다 — **`<img>` 의 최대 높이**다(`w-full h-auto max-h-[420px] object-contain`).
글자가 아니라 **사진**이라 큰글씨와 무관하다. **진짜 장애물은 0개다.**

```
truncate 12곳 / line-clamp 1곳 / overflow-hidden 4곳
  -> 장애물이 아니라 **선택**이다. 글자가 커지면 더 잘릴 뿐 레이아웃은 깨지지 않는다.
     큰글씨 모드에서 완화할지는 제품 결정.
```

**기술 기반은 이미 준비돼 있다. 남은 것은 토글을 켤지와 배율뿐이고 그것은 제품 결정이다.**

## 6. 문서 ↔ 코드 환경변수 이름 대조

코드가 **실제로 읽는** 이름을 AST 로 전수 추출해(주석/문자열 제외) 문서와 대조했다.
이 저장소는 이름 불일치로 사고를 겪은 적이 있다(`JWT_SECRET` vs `SUPABASE_JWT_SECRET`).

### 발견 1 — `DOC_WORKER_TEST_MODE` 가 문서 어디에도 없었다

```python
if os.environ.get("DOC_WORKER_TEST_MODE") == "1":
    return False        # 실행 창 검사를 통째로 무력화한다
```

운영에 실수로 들어가면 **워커가 종료 시각을 무시하고 계속 돈다** —
06:00 일일 크롤과 겹칠 수 있다(둘 다 Chrome, 서로의 락을 보지 않는다).
`docs/ENVIRONMENT_VARIABLES.md` 에 용도·위험·운영값(설정하지 않는다)을 기록했다.

### 발견 2 — `SUPABASE_ANON_KEY` 는 `.env` 에 있는데 읽는 코드가 0곳

기능 영향은 없지만 *"설정했는데 왜 안 되지"* 의 원인이 되기 쉬워 문서에 남겼다.
실제로 쓰이는 것은 `NEXT_PUBLIC_SUPABASE_ANON_KEY`(`.env.local`, 프런트 전용)다.
`.env` 정리는 승인 영역이라 건드리지 않았다.

### 문서에만 있는 나머지는 드리프트가 아니다

`KG_*` / `SMTP_*` / `SMS_*` / `SENTRY_DSN` / `SLACK_WEBHOOK_URL` / `GA4_*` 는
**아직 도입하지 않은 연동**의 계획 항목이다(문서의 §B/§C 분류 그대로).
