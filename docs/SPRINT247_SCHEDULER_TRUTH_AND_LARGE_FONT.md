## 4. ★ 큰 글씨(200%)에서 레이아웃이 깨지고 있었다 (P2, 수정 완료)

### 발견 — 접근성 검사가 **소스만 세고 있었다**

`test_frontend_accessibility.py` 는 1,143줄이다. 그런데 하는 일은 `text-xs` 가 몇 개인지,
`text-[11px]` 가 rem 으로 바뀌었는지 같은 **문자열 세기**다. 그 문서 주석에
*"text-[0.6875rem] 은 루트 글꼴을 키우면 따라 커진다"* 라는 **가정**이 적혀 있는데,
**키웠을 때 레이아웃이 견디는지는 한 번도 렌더링해서 재지 않았다.**

WCAG 1.4.4 는 200% 확대에서 내용/기능 손실이 없을 것을 요구한다. 어르신 사용자가 많은
서비스라 더 직접적인 요구사항이다.

### 도구를 먼저 검증했다

글꼴 스케일이 **실제로 먹었는지** 확인하지 않으면, 안 먹은 채 "정상"이 나와도 알 수 없다.

```
100%  root=16px body=16px
200%  root=32px body=32px      루트 글꼴 배율 2.00x   -> 스케일이 실제로 적용됐다
```

### 실측 — 36칸 중 2칸이 깨졌다

로그인 없이 도달 가능한 3화면 × 4폭 × 글꼴 3단계.

```
/        320px 글꼴 200%   DIV.py-4 flex gap-2 > BUTTON.flex-1      (+8px, 부모 175 / 자식 26)
/search  320px 글꼴 200%   DIV.flex gap-2 > BUTTON.shrink-0         (+7px, 부모 175 / 자식 116)
```

360/390/430px 은 전부 통과. 100%/150% 도 전부 통과. **320px + 200% 에서만** 깨진다.

원인은 이 저장소가 이미 여러 번 밟은 flex `min-width:auto` 다. `shrink-0` 버튼이 글꼴을
따라 커지는데 옆 형제는 자기 콘텐츠 폭 아래로 줄지 못해 부모를 넘긴다.

### 고치기 전에 후보를 **브라우저에서 재 봤다**

소스를 건드리기 전에 세 후보를 실제 페이지에 주입해 측정했다:

```
현행                          FAIL  부모넘침 2
A: 부모에 flex-wrap            OK    부모넘침 0
B: shrink-0 제거 + min-w-0     OK    부모넘침 0
C: A+B                        OK    부모넘침 0
```

**셋 다 넘침은 없앤다. 그래서 넘침만 보면 고를 수 없다.** 사용자 입장에서 갈린다 —
B 는 버튼이 찌그러져 "초기화"/"저장" **라벨이 잘린다.** WCAG 1.4.4 가 요구하는 것은
"내용 손실 없음"이므로, 줄을 바꿔 글자를 온전히 보여 주는 **A** 가 맞다.
보통 크기에서는 두 버튼이 한 줄에 들어가 화면이 달라지지 않는다.

```
src/app/search/SearchForm.tsx     py-4 flex gap-2  ->  py-4 flex flex-wrap gap-2
src/app/search/SearchPresets.tsx  flex gap-2       ->  flex flex-wrap gap-2
```

`SearchPresets` 의 입력칸은 **이미 `flex-1 min-w-0`** 인데도 넘쳤다 — `shrink-0` 인
"저장" 버튼 자체가 116px 까지 커지기 때문이다. 즉 기존 `min-w-0` 처방으로는 부족했다.

### 재측정 + 회귀

```
큰 글씨 36칸        결함 0          (수정 전 2)
보통 글씨 18칸       결함 0          (audit_viewport.py, 320~1400px 전 폭)
```

`tests/source-contract.test.mjs` 에 가드 2건 신설(이 저장소가 Sprint 240/242/243 에서
같은 계열 수정을 고정한 방식 그대로).

```
MUT-LF1  SearchForm 의 flex-wrap 제거      -> [잡힘] "큰 글씨에서 검색 버튼 줄이 접힐 수 있다"
MUT-LF2  SearchPresets 의 flex-wrap 제거   -> [잡힘] "큰 글씨에서 검색조건 저장 줄이 접힐 수 있다"
```

## 5. ★ 명암비를 처음 **재 봤다** — 77개 중 44개가 WCAG AA 미달 (1건 수정 -> 43개)

### 발견 경로

§4 에서 "접근성 검사가 소스만 센다"는 것을 확인했으니, 같은 파일이 관리하는 **대비**도
같은 상태일 것이라 보고 실제로 쟀다. 기존 관리 방식은 `text-gray-400` 이 소스에 몇 번
나오는지 세고 상한(110개)을 거는 것이다. 그건 **개수**지 명암비가 아니다.

### 도구를 두 번 고쳤다 — 두 번 다 도구가 틀렸다

**(1) 색 공간 눈멂.** 처음 돌리니 12건이 전부 "흰 글자 on 흰 배경 1.00:1" 로 나왔다.
`bg-blue-500` 버튼들이었다 — 파란 버튼 위 흰 글자가 흰 배경일 리 없다. 제품이 아니라
도구를 의심하고 계산값을 찍어 봤다:

```
getComputedStyle(...).backgroundColor  ->  lab(54.1736 13.3368 -74.6839)
```

Tailwind v4 는 `lab()` / `oklch()` 로 계산된다. `rgb()` 정규식만 있던 파서가 전부
null 을 돌려주고 배경이 흰색으로 떨어진 것이다. **캔버스에 실제로 칠해서 sRGB 바이트를
읽는 방식**으로 바꿨다 — 색 공간과 무관하게 브라우저가 그리는 값이 나온다.

**(2) 셀프테스트의 전제가 틀렸다.** 색공간 검증을 "파랑 위 흰 글자는 통과해야 한다"로
넣었더니 계속 실패했다. 그런데 계산해 보니 **그 전제가 틀렸다** — Tailwind blue-500 위
흰 글자는 실제로 **3.68:1** 로 AA(4.5:1) 미달이다. 도구가 아니라 내 기대가 틀렸다.
그래서 판정 결과가 아니라 **파서 반환값**을 직접 보도록 바꿨다.

지금은 매 실행마다 두 가지를 확인하고 어긋나면 **결과를 쓰지 않고 종료한다**:

```
판정 로직   검정(21:1) 통과 / 흰 글자(1:1) 결함 / #767676(4.54:1) 통과
색공간      lab -> [43,127,255,1]  oklch -> [43,127,255,1]
            #767676 -> [118,118,118,1]  rgba(0,0,0,0) -> 알파 0
```

### 실측 (390px, 로그인 없이 도달 가능한 3화면)

```
/         텍스트 노드 35개 중 기준 미달 20개
/search   텍스트 노드 35개 중 기준 미달 19개
/login    텍스트 노드  7개 중 기준 미달  5개
합계      77개 중 **44개**
```

| 색 / 배경 | 크기 | 실측 | 기준 | 곳 | 어디 |
|---|---|---|---|---|---|
| `text-gray-300` on 흰색 | 12px | **1.47:1** | 4.5 | 1 | 로그인 화면 약관 안내문 |
| `text-gray-400` on `gray-50` | 14px | **2.49:1** | 4.5 | 3 | 검색 빈 화면 안내문 |
| `text-gray-400` on 흰색 | 12px | **2.60:1** | 4.5 | 13 | 아코디언 `▼` |
| `text-gray-400` on 흰색 | 14px | **2.60:1** | 4.5 | 6 | "면적 조건" / "특수조건" 라벨 |
| `text-blue-500` on 흰색 | 12px | **3.76:1** | 4.5 | 8 | 하단 내비 라벨 |
| 흰 글자 on `bg-blue-500` | 12/14/16px | **3.76:1** | 4.5 | 11 | **"검색" / "저장" / "로그인" 기본 버튼** |
| `text-gray-500` on `gray-100` | 14px | **4.39:1** | 4.5 | 2 | "초기화" 버튼 (아슬하게 미달) |

가장 무거운 것은 **기본 동작 버튼 11곳**이다. "검색"·"로그인"은 서비스의 주 동선이고,
어르신 사용자가 많은 서비스라 더 직접적이다. 가장 나쁜 값은 약관 안내문의 **1.47:1** 이다.

### 한 곳만 고쳤다 — 가장 나쁘고, 저장소 자신의 규칙이 허용하는 곳

`text-gray-300` on 흰색 **1.47:1** 은 이 화면에서 가장 낮았고, 하필 그 문장이
**"로그인 시 서비스 이용약관 및 개인정보처리방침에 동의하게 됩니다"** — 동의 고지다.
읽을 수 없는 동의 문구는 접근성 문제이자 고지 자체가 무의미해지는 문제다.

`test_frontend_accessibility.py` 의 상한 규칙이 *"줄이는 것은 자유, 늘리는 것은 막는다"*
라 이 한 곳만 `text-gray-500` 으로 내렸다. 한 줄 변경이다.

```
수정 전   /login 기준 미달 5개   전체 44개   최악 1.47:1
수정 후   /login 기준 미달 4개   전체 43개   1.47:1 항목 소멸
test_frontend_accessibility.py  [PASS] text-gray-300 사용 횟수: 5 (상한 6, 줄었다)
```

나머지 `text-gray-300` 5곳은 전부 `properties/[id]`(로그인 뒤)라 **실측하지 못했다.**
재지 않은 것을 짐작으로 고치지 않는다.

### 나머지는 고치지 않았다 — 이유를 분명히 한다

브랜드 파랑과 회색 텍스트 110곳을 한꺼번에 바꾸는 것은 **모든 화면의 인상을 바꾸는
디자인 결정**이지 결함 수정이 아니다. 게다가 이 저장소는 이미 이 부채를
`test_frontend_accessibility.py` 의 **상한(ratchet)** 으로 점진 관리하기로 정해 놓았다.
그 방침을 에이전트가 임의로 뒤집지 않는다.

대신 관리 지표를 **"클래스 개수" 에서 "실측 명암비" 로** 끌어올렸다. `audit_contrast.py`
(읽기 전용, 온디맨드 — `audit_viewport.py` 와 같은 위치/같은 사용법)를 신설했고,
위 표가 그 기준선이다.

**권고(제품 판단 필요):** 브랜드 파랑을 `blue-500`(#3b82f6, 3.68:1)에서 `blue-600`
(#2563eb, 약 4.5:1) 또는 `blue-700`(#1d4ed8, 약 6.3:1)로 한 단계 낮추면 버튼 11곳이
한 번에 해소된다. 색상 결정은 승인 영역이라 제안만 남긴다.

### 6-A. 만료 큐 2,753행 — 용량 문제가 아니다

```
실행 창(02:00~04:00, 7,200초) 대비   0.132%
```

종결은 브라우저를 열기 **전에** 끝나고, 종결 전에 권위 값과 한 번 대조한다(Sprint 145).

### 6-B. Cache/성능 — 계약대로다

```
검색 1페이지      중앙값 4.6ms   11,288바이트
검색 지역필터      중앙값 3.6ms
검색 깊은 페이지(90) 중앙값 5.4ms
상세             중앙값 4.5ms
지역/통계/요금제    중앙값 2.9 / 3.6 / 1.0ms
```

공개 JSON 에 `Cache-Control` 이 없다. 처음엔 결함으로 보였지만 **테스트를 먼저 읽었다** —
`test_api_cache_headers.py` 의 계약은 *"사용자별 JSON 은 `no-store`, 공개 JSON 에는
`no-store` 를 씌우지 않는다, 파일 응답은 ETag/304 를 유지한다"* 이다(Sprint 237).
즉 **의도된 설계**다. **결함 없음.**

### 6-C. 면적/특수조건 필터 — 사용자에게 거짓말하지 않는다

`SearchForm.tsx` 에 `TODO(API 미지원)` 3건이 있고 `min_building_area` 등을 백엔드로
보내지만, 백엔드는 읽지 않는다. "입력했는데 안 걸러진다"면 P2 결함이다 — 그래서
**화면을 실제로 확인했다.**

```
<SearchAccordionSection title="면적 조건" muted>  <p>준비 중입니다</p>
<SearchAccordionSection title="특수조건"  muted>  <p>준비 중입니다</p>
```

접힌 상태(`aria-expanded="false"`)로 흐리게(`muted`) 렌더링되고, **입력칸이 아예 없다.**
`form.buildingAreaMin` 등은 URL 파라미터로만 채워질 수 있다. 즉 손으로 URL 을 만들지
않는 한 사용자는 이 값을 넣을 방법이 없고, 화면은 "준비 중입니다"라고 **정직하게** 말한다.

**결함 없음** — 정직하게 라벨링된 미구현 기능이다. 데이터는 있다(`full_address` 의
98.8% 가 ㎡ 표기를 포함: 집합건물 1,100 / 토지 713 / 건물 49 / 차량·선박 등 14).
다만 다층 건물 44건은 층별 면적이 여러 개라 "건물 면적"의 정의가 갈리고, 컬럼 신설은
스키마 변경(승인 영역)이다. **제품 판단이 필요하므로 그대로 둔다.**
