# Sprint 158 — Admin 쓰기 경로 실패 주입, 그리고 **살아남은 mutant를 정직하게 다루기**

작성 2026-08-17. 모든 수치는 실행 결과다. 공유 문서는 다른 세션이 편집 중이라 건드리지 않았다.

**결함은 나오지 않았다.** 네 경로 전부 계약대로 동작했다. 대신 **내 검사가 약하다는 것**을
mutation이 알려 줬고, 그 처리 과정이 이 문서의 핵심이다.

---

## 1. 먼저 내 측정을 정정한다

Sprint 153·154 문서에 "admin.py의 rollback·409 동시성 분기는 미커버"라고 적었다.
**그 근거가 틀렸다** — 커버리지를 5개 파일로만 돌렸고 거기에 `test_race_conditions.py`가
빠져 있었다. 경합 테스트를 포함해 다시 재니 409 분기는 이미 덮여 있었다.

```
5개 파일로 측정   95%   409 분기가 미커버로 보임      <- 틀린 측정
8개 파일로 측정   96%   409 분기 덮여 있음, 남은 것은 except Exception 4곳
```

`test_race_conditions.py`는 admin registry 전이 / 환불 / webhook 재처리 /
구독 상태 변경의 경합을 이미 다룬다(§4·5·9·10·14). **없는 줄 알고 다시 만들 뻔했다.**

## 2. 진짜로 안 덮인 것 — "작업 도중 오류"

```
api\v1\admin.py   396 stmts   16 miss   96%
   412-414   registry 상태 전이     except Exception: conn.rollback(); raise
   546-548   등기부 무료횟수 조정    〃
   876-878   webhook 재처리         〃
   945-947   결제 환불              〃
```

네 곳 전부 **돈이나 권한이 걸린 조작**이다. 정상 경로와 경합은 검증돼 있는데,
"도중에 예상 못 한 오류가 났을 때"만 한 번도 실행된 적이 없었다.

## 3. 주입 방식 — 아무것도 안 쓰고 터지면 의미가 없다

핵심 설계 판단이다. 주입 함수가 그냥 예외만 던지면 **되돌릴 것이 없으니 무조건 통과한다.**
그래서 **실제 쓰기를 성사시킨 뒤** 터뜨렸다.

```python
def boom(conn, payment_id, ...):
    conn.execute("UPDATE payments SET status='REFUNDED' WHERE id=?", (payment_id,))
    raise RuntimeError("주입된 실패")
```

핸들러 내부(커넥션 계층)에서 터뜨려야 하는 경우를 위해 `FailAfterWrite` 래퍼도 만들었다 —
지정한 SQL을 **실행한 뒤** 예외를 내는 커넥션이다. DB 잠금·디스크 오류를 흉내 내는
방식이라 프로덕션 코드를 고치지 않고 분기를 결정적으로 태울 수 있다.

### 결과 — 네 경로 전부 계약을 지킨다

| 경로 | 주입 | 응답 | 부분 상태 |
|---|---|---|---|
| 결제 환불 | UPDATE 후 예외 | 5xx | 없음 (SUCCESS 유지) |
| 신청 상태 전이 | UPDATE 후 예외 | 5xx | 없음 (PROCESSING 유지) |
| webhook 재처리 | UPDATE 후 예외 | 5xx | 없음 (RECEIVED 유지) |
| 무료횟수 조정 | INSERT 후 예외 | 5xx | 없음 (0행 유지) |

구독 동시 변경은 `ConcurrentStatusChange`를 주입해 **409**(500 아님)를 결정적으로 확인했다.

## 4. ★ mutation이 4/4 살아남았다 — 그리고 그게 옳았다

검사를 만든 뒤 `conn.rollback()`을 한 곳씩 지워 봤다.

```
블록#0 rollback 제거 -> exit=0 잡힘=False
블록#1 rollback 제거 -> exit=0 잡힘=False
블록#2 rollback 제거 -> exit=0 잡힘=False
블록#3 rollback 제거 -> exit=0 잡힘=False
```

**전부 생존했다.** 내 검사는 rollback 호출을 전혀 고정하지 못한다. 원인을 실증했다.

```
네 블록 뒤에는 전부  finally: conn.close()  가 있다 (소스에서 확인).
그리고 SQLite 는 커밋 안 한 트랜잭션을 close 시점에 버린다.

  실증:  UPDATE 후 rollback 없이 close  ->  다시 열면 값이 원래대로('A')
```

즉 이 네 `conn.rollback()`은 **관측 가능한 동작을 바꾸지 않는다**(equivalent mutant).
어떤 행위 기반 검사로도 죽일 수 없다 — 검사를 더 정교하게 만드는 문제가 아니다.

### 어떻게 처리했나

두 가지를 **구분해서** 남겼다.

* **1~5번(행위)** — "부분 상태가 남지 않는다"는 진짜 계약을 검증한다. 이 계약은 참이고,
  `rollback` 때문이 아니라 **"커밋되지 않았다"는 더 튼튼한 이유**로 성립한다.
* **6번(구조)** — `rollback()` 호출이 소스에 남아 있는지 본다. 행위로 못 잡으니 구조로 고정한다.

구조 검사를 추가하니 4/4 전부 잡힌다.

```
블록#0~#3 rollback 제거 -> exit=1 잡힘=True  (4/4)
```

**왜 지우면 안 되는 코드인가**: 커넥션 풀링을 도입하거나 `close` 관례가 바뀌면
close가 더 이상 트랜잭션을 버리지 않는다. 그때는 이 rollback이 유일한 방어가 된다.
지금 "동작이 같으니 불필요"하다고 지우면, 나중에 그 전제가 바뀌었을 때 아무도 모른다.

> 이 절을 길게 쓴 이유: mutation이 살아남았을 때 **검사를 통과시키려고 단언을 약하게
> 바꾸거나, 구조 검사를 행위 검사인 척 적는 것**이 가장 쉬운 유혹이다. 파일 docstring에도
> "이 검사는 rollback 호출 자체를 고정하지 못한다"를 명시해 두었다.
