## 1. 체인 전체를 코드로 훑었다

```
법원 원천 → Crawler → auction/auction_item → 변경 감지 → Refresh Queue
         → Image Queue → Collector → 파일 저장 → auction_image
         → Image API → 검색목록 썸네일 → 상세페이지 이미지
```

각 단계의 담당 코드와, 그것을 잠그는 검사:

| 단계 | 코드 | 잠그는 검사 |
|---|---|---|
| 변경 감지 → 큐 | `migrate_execute` → `requeue_changed_documents()` | `test_refresh_trigger` 20/21 |
| claim(overwrite) | `claim_next_queue_item()` | 12-J, `test_refresh_trigger` |
| 수집 → 저장 | `collect_images()` → `_write_image_atomically()` | 5-A~5-I |
| DB 기록 | `save_auction_images()` | 12-G, **12-P(신규)** |
| 성공 판정 | `doc_worker` | 12-G/H/I/J/K, **12-M** |
| 상세 API | `api/v1/item.py` | 16 |

| **교체 반영/캐시** | ETag(mtime,size) | **12-O(신규)** |

## 2. BUGS #148 — 기록은 되는데 서빙은 404

검색목록 관통 검사를 쓰다가 서빙이 404 를 냈다. 픽스처가 작아서였는데,
그 과정에서 **판정 기준이 두 벌**이라는 것이 드러났다.

```
save_auction_images()     size <= 0 만 거절        <- 행을 만드는 곳
image_exists()            >= MIN_IMAGE_BYTES(1,024)
api/v1/images.py (서빙)    >= MIN_IMAGE_BYTES
```

241바이트 사진 하나로 끝까지 흘려보낸 결과:

```
save_auction_images  saved=1              (기록된다)
image_exists()       False                (같은 저장소가 반대로 답한다)
API                  image_count=1 / images_status=READY / 대표 URL 제공
검색 목록            그 URL 을 썸네일로 제공
그 URL               404
```

**상세와 목록 양쪽에** "사진 있음"으로 표시해 놓고 열면 없다.
`image_exists()` 의 docstring 이 규약을 이미 적어 뒀는데 **행을 만드는 함수만** 그 밖에
있었다. `MIN_IMAGE_BYTES` 를 같은 상수로 참조하도록 고쳤다.

운영 실측: `auction_image` 45행의 최소 크기 **35,746바이트** — 영향 **0건**.
수집기가 이미 같은 하한으로 걸러내므로 정상 경로로는 도달하지 않는다.

### ★ 픽스처가 서빙 불가능한 데이터로 "정상"을 그리고 있었다

이 수정으로 **기존 검사 10건이 깨졌다.** 원인은 픽스처가 100~600바이트 사진으로
`auction_image 2행 / images_status=READY` 를 단언한 것 — 그 사진들은 **실제로는
한 장도 서빙될 수 없는 크기**다. 파이프라인 전체가 거부할 데이터로 정상 상태를 그렸다.

`MIN_FIXTURE_PAD` 를 두어 한 번에 올렸다. 개별 pad 는 "서로 다른 바이트"를 만들기
위한 것이므로 하한만 더하면 의도는 그대로다.

## 3. 새 관통 검사 3종

### 12-N — 목록 썸네일 == 상세 대표 사진

두 화면은 **서로 다른 코드**로 대표를 고른다.

```
검색목록   api/v1/search.py   SELECT item_id, MIN(seq) ... GROUP BY item_id
상세페이지 api/v1/item.py     ORDER BY seq 로 읽어 images[0]
```

같은 규칙의 **두 벌 구현**이다. 한쪽만 바뀌면 "클릭했더니 다른 집이 나온다"가 된다.
16번은 상세만, 17번은 목록만 봤고 **둘을 대조한 검사는 없었다.**

순번을 일부러 어긋나게 해 두 물건을 만든다(A=2,3 / B=1,4 / C=사진없음):

```
A 의 대표 = 2 / B 의 대표 = 1        각자 자기 물건 id 를 가리킨다
목록 URL == 상세 URL                 두 화면이 같은 것을 가리킨다
두 URL 이 **같은 바이트**를 준다      실제로 열어 대조
C 는 목록 null / 상세 대표 없음       깨진 자리를 만들지 않는다
파일이 사라져도 목록은 200            URL 은 그대로 주고 그 URL 만 404
                                     (프런트 `ResultThumbnail` 이 onError 로 감춘다)
```

### 12-O — 사진이 바뀌면 목록도 새 사진을 보여 주는가

URL 은 `/images/{순번}` 이라 사진이 교체돼도 **주소가 바뀌지 않는다.**
그래서 "최신을 보여 주는가"는 전적으로 **조건부 캐시**에 달려 있다.

**크기가 같은 다른 사진**으로 바꿔 본다 — 크기만 보는 구현이면 여기서 잡힌다.

```
바뀌지 않음  If-None-Match -> 304 / 0바이트     (아끼는 것)
교체됨       If-None-Match -> 200 + 새 바이트, ETag 변경   (보여 줘야 하는 것)
목록 URL     그대로. 다시 받으면 새 사진.
```

### 12-P / 12-Q — 기록된 사진은 반드시 서빙될 수 있어야 한다

12-P 는 시나리오(하한 미만/이상 대조군 + API + 목록)를, 12-Q 는 **모양**을 잡는다 —
판정처 3곳(`save_auction_images` / `image_exists` / 서빙)이 **같은 상수**를 보는가.

★ 12-Q 는 처음에 무효였다. 본문에 `"MIN_IMAGE_BYTES"` 문자열이 있는지만 봤는데,
변이가 만든 `_MIN_IMAGE_BYTES = 1024` 가 그 부분 문자열을 포함해 **그대로 통과했다.**
AST 로 **숫자 상수 대입**과 **단일 소스 import 여부**를 보도록 고친 뒤에야 잡혔다.

## 5. 실측 — 검색목록 이미지 비용과 캐시

```
검색 1페이지            물건 9건 / 썸네일 9개 / 검색 응답 42.9ms(콜드)
첫 방문(캐시 미스)      합계 0.91 MB / 장당 p50 4.1ms / 합 48ms
재방문(조건부 요청)     합계 0 바이트 / 전부 304 / 합 46ms
아끼는 바이트           0.91 MB (100%)
```

**조건부 캐시는 바이트를 100% 아낀다.** 다만 요청 수와 왕복 시간은 그대로다(304 도 요청이다).

★ **썸네일 한 장이 평균 약 101 KB** 다 — 80x80 으로 그리는데 **원본을 그대로** 내려
준다. 서버 측 썸네일 생성은 Pillow 의존성이 필요해 승인 영역이다
(`docs/SPRINT144_ASSET_PIPELINE.md` SKIP 항목). 지금은 사진 보유 물건이 적어 체감이
작지만, 보유율이 오르면 1페이지가 곧 수 MB 가 된다.

## 5-b. 실행 창 대비 하루 처리 가능 물량 (실측 상수로 계산)

```
실행 창           02:00~04:00 = 120분 = 7,200초   (config/settings.py)
행당 비용         24.0초 = 이동 15.2 + 수집 6.8 + sleep 2.0   (Sprint 146/147 실측)
=> 창 안에서 실제 수집 가능      약 300행 = 75물건(4종 기준)
```

**지금 적체는 문제가 아니다.**

```
큐 3,498행 / 집어갈 수 있는 상태 2,753행
  기일이 오늘 이후(브라우저를 여는 행)  17행   <- spec 6 / appraisal 6 / status 5
  기일 경과(브라우저 없이 5.1ms 종결)  2,736행
=> 적체 처리에 6.8분 = 창의 6% (여유 17.6배)
```

`image` 가 0행인 것은 **검색에 뜨는 9물건의 사진 수집이 이미 끝나서**다
(각 5장, `auction_image` 45행). 즉 지금 화면에 보이는 것은 전부 최신이다.

**병목은 적체가 아니라 최초 수집 총량이다.**

```
물건 1,876개 x 4종 = 7,504행
현재 방식으로 전부 받으려면   25.0일치 실행 창
```

### 개선안 — 물건 단위 배칭 (미착수, 근거만 갱신)

`docs/SPRINT199_BATCHING_FEASIBILITY.md` 가 실증한 "이동 1회 후 두 번째 종류 정상 수집"을
4종 기준으로 환산하면:

```
현재    물건당 96.0초  (24.0 x 4 — 이동을 4번 한다)
배칭시  물건당 44.4초  (이동 1회 + 수집 4회 + sleep)
절감    51.6초/물건 = 54%
창 기준 75물건 -> 162물건 (2.2배) / 최초 수집 25.0일 -> 11.6일
```

**착수하지 않는다.** Sprint 199 가 정한 착수 조건은 *"대기 + 기일 남은 물건이 수백 이상"*
인데 지금은 **17행**이다. 그 조건을 만든 이유가 그대로 유효하다 — 지금 배칭을 넣으면
얻는 것은 6.8분 중 일부이고, 잃는 것은 `doc_worker` 루프의 단순함이다.
**데이터 공급이 재개되어 그 수가 자란 뒤**가 옳은 시점이다.

## 7. 확인했지만 고치지 않은 것 (근거 포함)

**검색목록은 "사진 없음"과 "수집 실패"를 구분하지 못한다.** 실측:

```
검색 결과 항목의 이미지 관련 키   thumbnail_url 하나뿐
상세 응답의 이미지 관련 키        images, image_count, representative_image, images_status
```

세 상태(한 번도 안 해 봄 / 법원에 없음 / 수집 실패)가 목록에서는 **전부 같은 모양**
(썸네일 없음)이다. 목록에 상태 배지를 넣을지는 **제품 결정**이라 임의로 하지 않는다.
지금은 "없으면 조용히 자리만 비운다"가 일관되게 동작한다는 것까지 확인했다.
