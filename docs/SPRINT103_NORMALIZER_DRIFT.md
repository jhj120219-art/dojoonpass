## #103-1 ★ 정규화 규칙이 바뀌었는데 기존 행을 다시 계산한 적이 없다

`sido` / `sigungu` / `dong` / `lot_number`는 전부 `full_address` **하나에서** 계산된 값이다.
1,876행 전부를 지금 코드로 다시 계산해 저장값과 대조했다.

| 컬럼 | 불일치 | 성격 |
|---|---|---|
| `sido` | **4행** | 저장값이 **틀렸다** |
| `sigungu` | **207행 (11.0%)** | 저장값이 옛 형식(구가 빠짐) |
| `dong` | 0행 | — |
| `lot_number` | 0행 | — |

정규화 중 예외가 나는 주소는 0행이었다.

### (1) `sido` 4행 — 도로명을 시도로 잘못 읽던 옛 버그의 잔재

```
id=8160  '경기도 시흥시 서울대학로 59-21 ...'        저장 '서울'  ->  실제 '경기'
id=1787  '경상남도 양산시 물금읍 부산대학로 150 ...'  저장 '부산'  ->  실제 '경남'
id=9977  '제주특별자치도 제주시 구좌읍 세화리 산29'    저장 '세종'  ->  실제 '제주'
id=550   '사용본거지 : 인천광역시 계양구 ...'         저장 '서울'  ->  실제 '인천'
```

주소에 든 **도로명**("서울대학로", "부산대학로")을 시도로 오매칭한 결과다.
**지금 코드는 네 건 모두 올바른 값을 낸다**(재현 확인). 코드는 고쳐졌고 데이터만 남았다.

사용자가 겪는 것: **서울로 지역을 좁힌 사람에게 경기·인천 물건이 섞여 나온다.**

### (2) `sigungu` 207행 — 형식이 두 가지로 섞여 있다

```
저장 '고양시'   ->  지금 '고양시 일산동구'
저장 '용인시'   ->  지금 '용인시 수지구'
저장 '수원시'   ->  지금 '수원시 팔달구'
```

207행 **전부** 저장값이 새 값의 접두다(그 외 형태의 불일치 0행). 규칙이 넓어진
방향이므로 덮어써도 정보가 줄지 않는다. 반면 이미 새 형식으로 저장된 행도 64개 있다 —
**같은 컬럼에 두 형식이 공존한다.**

검색은 `sigungu LIKE '%값%'` 부분일치라(`api/v1/search.py:245`) 시 이름으로 찾으면 둘 다
나온다. 그러나 **구까지 넣어 찾으면 옛 행이 통째로 빠진다.**

```
sigungu LIKE '안산시 단원구'   ->    0행     (안산시 자체는 31행 존재)
sigungu LIKE '용인시 기흥구'   ->    0행     (용인시 자체는  9행 존재)
sigungu LIKE '고양시 일산동구'  ->    3행     (고양시 자체는 25행 존재)
sigungu LIKE '포항시 북구'     ->    2행     (포항시 자체는 28행 존재)
```

이쪽이 더 나쁘다. 오류 메시지도 빈 화면도 아니고 **그냥 그 구에 물건이 없는 것처럼
보인다** — 사용자도 운영자도 알아챌 방법이 없다.

### ★ 영향 범위를 정확히 (처음 측정보다 좁다 — 정정)

위 숫자는 **만료 물건을 포함한 전체** 기준이다. 실제로 누가 보게 되는지 따로 측정했다.

```
드리프트 211행 중
  매각기일이 남아 재크롤될 수 있는 행 :   0행   ← 다음 크롤에서 자동 교정될 것
  매각기일이 지나 재크롤되지 않는 행   : 211행   ← 백필이 유일한 수단
```

**211행 전부가 만료 물건이다.** 그래서 영향이 이렇게 갈린다.

| 화면 | 영향 |
|---|---|
| 기본 검색(D7, 종결 제외) | **없음.** 지금 뜨는 9건은 전부 `서울 / 종로구·관악구·서초구·중구`로 값이 정확하다 |
| **"종결물건 포함" 체크 시** | **211행이 영향.** 사용자가 켤 수 있는 실제 옵션이다(`SearchForm.tsx:635`) |

즉 **당장 첫 화면이 틀린 것은 아니다.** 다만 종결물건을 포함해 과거 사례를 찾는 사용자
(경매에서 흔한 사용 방식이다)에게는 그대로 보인다.

그리고 **재크롤로 저절로 낫지 않는다** — 만료 물건은 다시 수집되지 않으므로,
백필하지 않으면 **영구히 틀린 채로 남는다.**

> 앞선 초안에서 "안산시 단원구 검색 0행 → 19행"을 영향의 근거로 들었는데,
> 그 19행은 **전부 만료 물건**이다. 기본 검색만 쓰는 사용자에게는 차이가 없다.
> 숫자는 맞지만 인상이 과했으므로 여기서 바로잡는다.

## 조치 — 백필 스크립트를 만들고 **적용하지 않았다**

`backfill_region_normalize.py` 신설. `backfill_dong_normalize.py`(dong 백필)와
같은 계열이고 같은 관례를 따른다.

```
python backfill_region_normalize.py            # dry-run (기본)
python backfill_region_normalize.py --apply    # 실제 반영
```

설계상 지킨 것:

- **`auction`(크롤러 원본)과 `auction_item`(API가 읽는 표) 둘 다** 고친다.
  한쪽만 고치면 다음 `migrate_execute.py` 실행 때 옛 값이 다시 덮어쓴다.
- 새로 계산한 값이 **비어 있으면 건너뛴다** — 채워진 값을 빈 값으로 덮지 않는다.
- `dong` / `lot_number`는 불일치가 0행이므로 **UPDATE 대상에 넣지 않는다**(최소 수정).
- `--apply` 후 **남은 불일치를 다시 세어 보고**한다 — "썼다"가 아니라 "맞아졌다"를 확인한다.

이 저장소의 **명시된 관례**다. `backfill_dong_normalize.py`의 docstring이 직접 적어 두었다.

> 주의: 이 스크립트는 작성만 하고 PM(사용자) 승인 전에는 `--apply`로 실행하지 않는다.

실 데이터 422행을 고치는 일이고, 되돌리려면 다시 계산해야 한다.
**검증까지 끝내 두었으므로 사용자는 명령 한 줄이면 된다.**

## #103-2 드리프트 가드 (`test_pipeline_integrity.py` §12)

같은 일이 조용히 다시 쌓이지 않게 막는다. **결과가 아니라 증가를 막는다.**

이건 코드 결함이 아니라 쌓인 데이터이고, 고치려면 승인이 필요한 백필을 돌려야 한다.
그래서 "0이어야 한다"로 만들면 스위트가 계속 빨갛고 곧 무시하게 된다.
같은 파일 §8(차량 오분류)이 이미 쓰는 방식 — **상한을 두어 증가만 막는다.**

```python
NORMALIZE_DRIFT_CEILING = {"sido": 4, "sigungu": 207, "dong": 0, "lot_number": 0}
```

```
[PASS] 정규화 중 예외가 나는 주소 없음
[PASS] sido 드리프트가 늘지 않았다 (현재 4행, 상한 4)
       예: id=550 '서울'->'인천' / id=1787 '부산'->'경남' / id=8160 '서울'->'경기'
[PASS] sigungu 드리프트가 늘지 않았다 (현재 207행, 상한 207)
[PASS] dong / lot_number 드리프트 0
       고치려면: python backfill_region_normalize.py --apply  (기본은 dry-run)
```

`dong`과 `lot_number`의 상한은 **0**이다 — 지금 완벽하므로 한 건이라도 어긋나면 즉시 잡힌다.

백필을 적용하면 네 상한을 전부 **0으로 낮춰라.** 그 뒤로는 재발이 즉시 실패로 나타난다.
(그 절차를 검사 주석에 적어 두었다.)

## #103-3 이 드리프트가 **검증 실패까지 만들어 냈다** (12건 중 2건)

`validation_status='FAIL'`인 12행의 사유를 전부 읽었더니, **11건이 `address_mismatch`**였다.
검증기는 이렇게 판정한다(`validator/validation_engine.py:73`).

```python
addr_sido      = extract_sido(item.address)             # 주소에서 뽑은 시도
appraisal_sido = extract_sido(item.appraisal_summary)   # 감정평가요항표 전문에서 뽑은 시도
if addr_sido != appraisal_sido and not is_adjacent(...):  -> address_mismatch
```

그 12건 중 **2건은 #103-1의 시도 오류가 그대로 원인**이다.

```
id=550   2025타경513824   address_mismatch: addr=서울 appraisal=인천
         └ 저장된 sido 가 '서울'(틀림). 실제 주소는 인천광역시 → 감정요항의 '인천'과 맞다.

id=9977  2016타경3104     address_mismatch: addr=세종 appraisal=제주
         └ 저장된 sido 가 '세종'(틀림). 실제 주소는 제주특별자치도 → '제주'와 맞다.
```

**백필을 적용하면 이 두 건은 자동으로 해소된다** — `addr` 쪽이 각각 인천/제주가 되어
감정요항 값과 일치하기 때문이다. 사유 문자열만으로 증명되는 관계다.

즉 **정규화 드리프트 하나가 두 곳에서 사용자에게 보였다**: 검색에서 안 나오게 만들고,
멀쩡한 물건에 "검증실패" 표시를 붙였다. 이 파일 44행의 주석이 이미 같은 위험을
경고하고 있었다 — "그 불일치는 address_mismatch 오탐으로 나타나 화면에 '검증실패'로 뜬다."

> 나머지 9건은 주소 쪽 시도가 이미 옳다(드리프트 목록에 없다). 그쪽은 **감정평가요항표
> 전문에서 시도 하나를 뽑는 방식** 자체의 한계로 보인다 — 자유 문장이라 다른 지역이
> 참고로 언급되기만 해도 걸린다(같은 건물 4개 호실이 모두 `addr=부산 appraisal=서울`로
> 걸린 것이 그 정황이다). 다만 `appraisal_summary`는 DB에 저장되지 않아
> **지금은 원문을 확인할 방법이 없다.** 추측으로 단정하지 않고 여기까지만 남긴다.
>
> 현재 사용자 영향은 없다 — FAIL 12건 **전부 매각기일이 지났고**, 기본 검색에 뜨는
> 9건은 모두 PASS다(실측).

## #103-4 계산해서 저장한 나머지 두 컬럼도 함께 못 박았다

`bid_rate` / `fail_count`도 같은 부류다 — 다른 값에서 계산해 저장한다.
계산식이 바뀌면 정규화와 똑같이 조용히 어긋난다. 전수 대조 결과 **둘 다 완벽했다.**

| 검사 | 결과 |
|---|---|
| `bid_rate` == `calc_bid_rate(감정가, 최저가)` | 불일치 **0행** |
| `fail_count` == `extract_fail_count(status)` | 불일치 **0행** |
| `bid_rate` 가 0~1 범위 안 (비율이므로) | 위반 **0행** |
| 감정가 0인데 최저가가 있는 행(0으로 나누기) | **0행** |

완벽하므로 **상한을 0으로** 두어 그 상태를 못 박았다. 한 건이라도 어긋나면 즉시 실패한다.

판정은 `migrate_execute.py`의 **실제 함수**(`calc_bid_rate` / `extract_fail_count`)에
물어본다. 검사에 공식을 베껴 두면 코드가 바뀌어도 계속 통과한다 — 그게 드리프트가
생기는 방식이다.

범위 검사를 넣은 이유: 화면이 `bid_rate * 100`을 %로 그대로 보여 준다
(`ResultList.tsx:8`, `properties/[id]/page.tsx:633`). 범위를 벗어나면 "200%" 같은 값이
사용자에게 그대로 뜬다.

### 변이 검증

| | 변이 | 결과 |
|---|---|---|
| M25 | `bid_rate`를 공식과 다르게 변경 | O |
| M26 | `fail_count`를 status와 다르게 변경 | O |
| M27 | `bid_rate`를 범위 밖(2.0)으로 변경 | O (공식 + 범위 두 검사가 함께 잡음) |

## #103-5 `validation_status`는 **다시 계산할 수 없는 값**이다 (구조적 한계, 기록)

위 네 컬럼은 전부 재계산해 대조할 수 있었다. `validation_status`만 못 했다.
이유를 찾아보니 구조 문제였다.

```
validator/validation_engine.py:74
    appraisal_sido = extract_sido(item.appraisal_summary)
```

판정의 주 입력인 `appraisal_summary`(감정평가요항표 전문)가 **어느 테이블에도 저장되지
않는다** — 전 테이블 컬럼을 전수 확인했다. 크롤 중 메모리에만 존재하고 버려진다.

`revalidate.py`가 있지만 재검증 경로가 되지 못한다.

```
(1) 하드코딩된 CSV(auction_20260703.csv)를 읽는다 — DB가 아니다
(2) appraisal_summary="" 로 넘긴다 — address_mismatch 는 아예 발생할 수 없다
(3) 결과를 출력만 하고 DB에 쓰지 않는다
```

그래서 `validation_status`는 **한 번 쓰이고 나면 검증도 재계산도 불가능한 값**이다.

### 실제 영향

#103-3의 오탐 2건은 **백필로 sido를 고쳐도 저장된 `FAIL`이 그대로 남는다.**
원인은 사라지는데 표시는 남는다.

### 두 번째 간극 — 사유를 API로 알 수 없다

`validation_reasons`는 **레거시 `auction` 테이블에만** 있고, API가 읽는 `auction_item`에는
없다. 즉 화면은 "검증실패"라고 말할 수 있지만 **왜인지는 말할 수 없다.**

### 조치 — 재계산이 불가능하므로 값 범위만 고정했다

`test_pipeline_integrity.py` §12에 두 검사를 추가하고, **왜 드리프트 검사를 못 하는지**를
같은 자리에 적어 뒀다(다음 사람이 "빠뜨렸나?" 하고 다시 파지 않도록).

```
[PASS] validation_status가 알려진 값만 갖는다
[PASS] auction_item에는 validation_reasons가 없다(사유는 레거시 표에만 있다)
```

두 번째는 **현재 사실을 고정하는 검사**다. 스키마에 `validation_reasons`가 추가되면
이 검사가 먼저 실패해서 "이제 사유를 노출할 수 있다"는 것을 알려 준다.

`appraisal_summary`를 저장하도록 바꾸는 것은 스키마 변경(승인 영역)이라 하지 않았다.
다만 **그렇게 하면 `validation_status`도 다른 컬럼들처럼 감사 가능해진다**는 점은
기록해 둔다.

## #103-7 ★ 내가 Sprint 101에서 내린 결론이 틀렸다 — 크롤러 목록 파싱은 검증할 수 있다

Sprint 101에서 이렇게 적었다.

> "크롤러 목록 파싱을 픽스처로 검증할 수 있는가 — **없다** (문서가 맞았다)"

**범위를 잘못 잡았다.** 근거로 든 사실(저장된 HTML 덤프에 목록 마크업이 없다)은 맞지만,
거기서 "따라서 파싱 검증 불가"로 넓힌 추론이 틀렸다.

이 저장소는 **이미 가짜 드라이버로 크롤러 파싱을 검증하고 있었다** —
`test_crawler_parsing.py`(2026-08-13 Sprint 85 신설)가 `parse_basic_info` /
`parse_section_table` / `parse_gamjung` / `clean`을 그 방식으로 검사한다.
나는 그 파일을 열어 보지 않고 `roadmap.md`의 오래된 서술만 확인한 뒤 결론지었다.
**"이전 Sprint 보고서를 사실로 가정하지 않는다"를 문서에는 적용하고 코드에는 적용하지 않은 것이다.**

두 가지는 서로 다른 문제였다.

```
XPath가 실제 법원 DOM과 맞는가      실크롤 필요 -> 여전히 검증 불가 (SKIP이 맞다)
DOM에서 꺼낸 값을 어떻게 조립하는가   가짜 드라이버로 검증 가능 -> 이미 하고 있었다
```

### 남아 있던 진짜 공백 — `collect_list_items()`

Sprint 85가 네 함수를 덮었는데 **`collect_list_items()` 하나가 빠져 있었다.**
그런데 이 함수가 파이프라인에서 **가장 앞**이다.

```
collect_list_items()  ->  crawl_court()가 이 목록을 그대로 돌며 상세를 수집한다
```

**여기서 빠진 물건은 그날 아예 수집되지 않는다.** 예외도 로그도 없이 목록이 짧아질 뿐이다.

같은 방식으로 20개 검사를 추가했다(`test_crawler_parsing.py` §5) — 사건번호/물건번호/
주소/감정가/기일 추출, `dtl_idx` 파싱, 링크 없음, 칸 부족, 복수 사건번호 `' / '` 결합,
상태 문구 없음, 기일 형식 불일치, `max_items` 상한, 빈 표.

### 전제 하나를 일부러 드러내 두었다 (고치지 않고)

```python
i += 2   # 물건 행을 찾으면 다음 행을 '상태 행'으로 소비한다 = "한 물건 = 두 행" 전제
```

실제 페이지가 한 행짜리 물건을 준다면 **바로 다음 물건이 상태 행으로 먹혀 통째로 사라진다.**
지금 이것이 결함인지는 **실제 법원 DOM을 봐야 알 수 있고**, 이 저장소는 회귀에서
실크롤을 돌리지 않는다. 그래서 고치지 않고 **전제를 검사로 드러냈다** —
누가 이 규칙을 바꾸면 검사가 먼저 실패해 "무엇을 바꾸는지" 알게 된다.

```
[PASS] 연속한 물건 행 2개는 1건으로 줄어든다(한 물건=두 행 전제)
```

### 변이 검증 — 6종 전부 검출

| | 변이 | 검출 |
|---|---|---|
| M28 | 칸 수(`len<8`) 가드 제거 | O |
| M29 | `dtl_idx`를 항상 0으로 (**엉뚱한 물건 수집**) | O |
| M30 | 상태를 못 찾아도 "진행"으로 지어냄 | O |
| M31 | `i += 2` → `i += 1` (한 물건=한 행) | O |
| M32 | 복수 사건번호를 첫 번째만 남김 | O |
| M33 | `max_items` 상한 무시 | O |

M29가 가장 중요하다 — `dtl_idx`가 틀리면 **목록의 A를 보면서 B의 상세를 수집한다.**
조용히 잘못된 데이터가 쌓이는 경로였는데 검사가 0건이었다.
