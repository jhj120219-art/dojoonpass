| 위치 | 분기 | 안 지키면 |
|---|---|---|
| `claim_next_item_rows()` 형제 루프 | `rowcount == 0` → `continue` | 두 워커가 **같은 문서를 중복 수집**한다(법원 부하 2배, 같은 다운로드 폴더 동시 접근) |

## 왜 스레드로 재현하지 않았나

경쟁 창은 `SELECT` 와 조건부 `UPDATE` 사이 수 마이크로초다. 스레드로 두드리면
**대개** 재현되지만 매번은 아니다 — 그리고 "대개 잡히는 검사"는 회귀 방어선이
아니다(아래 §3 이 그 실증이다).

`test_race_conditions.py` 가 결제에 쓰는 방식을 그대로 가져왔다:
`UPDATE document_queue` 를 대행하기 **직전에** 다른 커넥션으로 그 행의 상태를 바꿔
`rowcount = 0` 을 강제하는 커넥션 래퍼(`_QueueInterleavingConn`). 확률이 개입하지 않는다.

한 가지 주의: `claim_next_item_rows()` 는 커넥션을 **두 번** 연다. 첫 번째는 머리 행을
집는 `claim_next_queue_item()` 것이고, 형제 루프는 두 번째다. 그래서 래퍼는
`_patch_nth_connection(db, nth, ...)` 로 **n번째 호출만** 감싼다 — 아무거나 감싸면
재현하려는 것과 다른 자리에 끼어든다.

## 3. 그 과정에서 드러난 것 — BUGS #130 의 회귀 주장이 과장이었다

`docs/BUGS.md` #130 은 이렇게 적혀 있었다:

> **[회귀]** `test_refresh_trigger.py` §15 — 스레드 12개로 ...
> 변이 확인: `CLAIM_RACE_MAX_ATTEMPTS = 1` 로 되돌리면 **즉시 3건 FAIL**.

실제로 되돌려서 반복 실행했다:

```
CLAIM_RACE_MAX_ATTEMPTS = 1 인 상태로
  test_refresh_trigger.py   검출 4/5,  이어서 11/12   →  합계 15/17 (약 88%)
  test_worker_batching.py   검출 5/5                  →  검사 13 추가 후
```

즉 **8번에 한 번꼴로 방어선이 통과한다.** 스레드 12개가 매번 같은 순서로 얽히지
않기 때문이다. "즉시 FAIL" 은 그날 한 번 돌려 본 결과였고, 상시 참인 문장이 아니다.

이것을 "테스트가 가끔 실패한다"로 읽으면 안 된다 — 방향이 반대다. **결함이 있는
코드를 가끔 통과시킨다.** CI 에서 이 한 번이 걸리면 결함이 그대로 통과한다.

스레드 검사를 지우지는 않았다. 그것은 **실제 동시성**을 두드리는 유일한 검사고,
결정적 검사가 재현하지 못하는 얽힘(락 경합, busy_timeout)을 본다. 다만 이제
R4 의 방어선은 검사 13 이고, 스레드 검사는 보조다. BUGS #130 의 [회귀] 항목을
그렇게 고쳤다.

## 5. 연쇄 감사 — 같은 부류를 제품 전체에서 훑었다

큐 쪽을 닫고 나서, **같은 모양의 방어**("조건부 UPDATE + `rowcount` 확인")를
`api/`·`storage/` 전체에서 찾았다. `rowcount == 0` 분기는 8곳이고, 그중 3곳이
합산 커버리지에서 미실행이었다.

```
api/v1/payments.py:458       등기부 신청 선점 레이스 -> 롤백 + PAY_ALREADY_PROCESSED
api/v1/payments.py:602       환불 상태 CAS          -> 롤백 + RefundError(409)
api/v1/subscriptions.py:213  구독 상태 CAS          -> 롤백 + ConcurrentStatusChange
```

### 먼저 잰 것: 이 분기들은 **지금은 도달하지 않는다**

셋 다 함수 진입 직후 `BEGIN IMMEDIATE` 로 쓰기 락을 잡고 **그다음에** SELECT 한다.
그렇다면 끼어들 창이 애초에 없는 것 아닌가? 추측하지 않고 scratch DB 로 쟀다
(창을 1초나 벌려 준 상태에서):

```
[BEGIN IMMEDIATE 있음]   끼어든 쪽 1.075초 대기 후 실행   제품 rowcount=1   가드 미도달
[없음 (대조군)]          끼어든 쪽 0.002초 즉시 실행      제품 rowcount=0   가드 도달
```

즉 이 셋은 **락이 이미 닫아 놓은 창에 대한 이중 방어**다. 테스트로 억지로 도달시키는
것(같은 커넥션에서 끼어들기)은 실제 시나리오가 아니어서 의미가 없고, 지우는 것은
락 순서가 바뀌는 날 조용히 뚫리게 만든다. **그대로 두고, 도달하지 않는 이유를 기록한다** —
그것이 이 문단이다.

### 그래서 진짜 질문이 바뀌었다: **락 없이 쓰는 경로가 있는가**

구독/결제 상태를 쓰는 문장을 전수로 훑었다. 하나가 걸렸다.

```sql
-- api/v1/subscriptions.py  sync_expired_status()
UPDATE subscriptions SET status=?, updated_at=? WHERE id=?      -- CAS 없음
```

이 모듈의 다른 writer(`change_status()`, `renew()`)는 전부 `AND status=?` 를 건다.
여기만 없었다. 그리고 이 함수는 **읽기 경로**(`GET /api/v1/subscriptions/me`,
Admin 사용자 목록)에서 `BEGIN IMMEDIATE` 없이 불린다 — 이 저장소에서 창이 실제로
열려 있는 유일한 자리다.

커넥션 래퍼로 결정적으로 재현했다:

```
ACTIVE(만료됨) 을 읽음 -> 그 사이 사용자가 해지(CANCELLED) -> sync 가 EXPIRED 로 덮음
최종: EXPIRED   (해지가 사라졌다)
```

`CANCELLED` 는 최종 상태다(`state_machines.py`: `CANCELLED: set()`). 그러니 이것은
단순한 늦은 갱신이 아니라 **금지된 전이가 DB 에 남는 사건**이다. 바로 위 줄에
"전이 규칙을 우회하지 않는다"고 적혀 있고 실제로 `assert_subscription_transition()` 을
부르는데도 그렇다 — 판정에 쓰는 상태(읽었던 ACTIVE)와 덮어쓰는 대상의 상태(CANCELLED)가
다르기 때문이다. 게다가 EXPIRED 는 최종이 아니라서 해지된 구독이 재구독으로 되살아난다.
로그에는 `ACTIVE -> EXPIRED` 라는 사실이 아닌 문장이 남는다.

**고쳤다.** 같은 모듈의 기존 패턴을 그대로 적용했다(읽은 상태를 WHERE 에 다시 걸고,
`rowcount == 0` 이면 그 행을 건너뛴다). API/스키마 변경 없음. 자세한 것은 BUGS #180.

회귀 2건과 mutation 3/3:

```
17  자동 만료 동기화가 동시 변경을 덮지 않는다   (결정적 재현 + 멱등성)
18  구독 writer 전수: 조건 없는 UPDATE 가 없다  (다음에 추가될 경로를 막는다)

C1 CAS 조건을 다시 뺀다(원래 결함)            검출
C2 CAS 는 두되 진 것을 '바꿨다'고 센다         검출
C3 CAS 값을 읽은 상태 대신 목표 상태로 건다    검출
```

18번을 쓰다가 그 검사 자체의 결함을 하나 잡았다: 파이썬의 **인접 문자열 리터럴**을
잇지 않고 조각만 보면 `renew()` 의 `" WHERE id=? AND status=? AND expires_at IS ?"` 를
놓쳐 멀쩡한 CAS 를 "조건 없음"으로 오탐한다. 실제로 오탐했고, 이어 붙인 뒤 해소됐다.

## 6. 한 번 더 — 집는 쪽을 막았으면 **끝내는 쪽**은? (BUGS #181)

§5 의 전수 감사에서 상태를 **조건 없이** 쓰는 문장 6개가 남았다. 하나(`UPDATE auction`)는
크롤 데이터 컬럼이라 해당 없고, 나머지 다섯은 전부 큐 **종결** 경로였다.

집는 쪽은 Sprint 191/236 이 CAS 로 단단히 막아 뒀는데, **끝내는 쪽은 아무 확인도 하지
않았다.** 그리고 여기서는 상태 CAS 를 걸어도 소용이 없다 — 회수 뒤 다시 집힌 행도
똑같이 `in_progress` 라서 "내 claim" 과 "남의 claim" 이 구별되지 않는다.

성립 조건은 둘 다 이미 제품에 있는 값이다:

```
doc_worker.LOCK_STALE_HOURS = 5     5시간 넘게 남은 락은 죽은 것으로 보고 넘어간다
reset_stale_queue()  10분          10분 넘게 in_progress 인 행을 회수한다
```

scratch DB 로 결정적으로 재현했다:

```
A claim -> (10분 초과) -> B 의 stale 회수 -> B 가 다시 claim
  사례 1  A 가 성공으로 끝남   -> 행이 'done'                 B 는 헛돌고 있다
  사례 2  A 가 실패로 끝남     -> 행이 'pending' + retry 1    제3의 실행이 또 집는다
```

**해결: claim 토큰.** claim 시점에 써 넣은 `last_attempt_at` 을 함께 돌려주고, 종결이
그 값을 다시 건다. **스키마를 바꾸지 않고**(이미 있는 컬럼을 세대 번호로 쓴다)
시그니처도 깨지 않는다(`claim_token=None` 이면 예전 동작 그대로).

성공과 실패의 규칙을 다르게 뒀다 — 이유가 있다:

```
mark_queue_done    큐 상태만 건너뛰고 document_status/doc_raw 는 그대로 쓴다
                   파일은 **실제로** 받아졌다. 화면이 그 사실을 반영해야 한다(멱등).
mark_queue_failed  아무것도 쓰지 않는다
                   그쪽이 성공할 문서를 '수집실패' 로 보이게 하면 안 되고,
                   남의 claim 을 풀거나 남의 재시도 예산을 깎아서도 안 된다.
```

### mutation 7/7 — 그리고 **거짓 검출**을 하나 잡았다

처음 돌린 mutation 은 7/7 이었다. 그런데 그중 하나가 가짜였다:
`test_doc_worker_recovery.py` 의 `mark_queue_failed` **대역 4개가 인자를 2개로 고정**하고
있어서, 워커가 토큰을 넘기기 시작하자 **어떤 변이를 넣든** 그 파일이 터졌다.
대역을 실물과 같은 모양으로 맞추고 다시 돌리니 진짜 결과가 나왔다:

```
T7 워커가 성공 종결에 토큰을 넘기지 않는다      놓침 ★
```

단위 검사(14/15)는 `mark_queue_done/failed` 를 직접 부르면서 토큰을 넣는다. 그래서
**제품의 방어가 옳다**는 것은 증명하지만 **호출부가 그 방어를 쓰는지**는 증명하지
못한다. 검사 16 이 그 구멍이다 — 실제 `doc_worker.main()` 을 돌려 두 종결 경로 모두에
토큰이 넘어가는지, 그 값이 그 행의 실제 claim 값인지 본다. 이후 7/7 (전부 진짜).

교훈 두 개를 남긴다. **대역이 실물보다 좁으면 제품 결함이 아닌 것을 결함처럼 보이게
한다**, 그리고 **mutation 이 "전부 검출"로 나오면 그것부터 의심한다.**

### 남긴 것

`mark_queue_skipped_expired()` / `mark_queue_unsupported()` 도 같은 모양이지만 그대로 뒀다.
둘은 "기일이 지났다 / 지원하지 않는 종류다" 라는, **어느 실행이 판단하든 같은 결론이
나오는 사실**을 쓴다(진행 상태를 되돌리지도, 재시도 예산을 건드리지도 않는다).
토큰을 걸면 그 사실의 기록만 늦어진다. 판단이 실행마다 달라질 수 있게 되는 날 다시 볼 것.

## 7. 커버리지 감사를 이어서 — 조건부 요청의 나머지 절반

같은 방식(합산 커버리지로 "아무 테스트도 실행하지 않는 제품 코드" 찾기)을 계속 돌렸다.

먼저 `api/auth.py` 를 봤다. 좁은 부분집합으로 재면 63% 로 보이는데, **인증을 태우는
회귀 15개를 전부 합치면 100%** 다. 보안 핵심 모듈의 구멍인 줄 알았던 것이 측정
범위의 문제였다 — 잰 것과 잰 방법을 같이 남긴다.

그다음이 `api/http_cache.py` 였다. 45줄 중 12줄이 미실행이었고, 그 12줄이 하필
**조건부 요청 처리의 절반**이었다.

```
65      약한 ETag(`W/`) 접두사 벗기기
73-79   _http_date_to_timestamp()  전체
121-125 If-Modified-Since 분기     전체
```

깨지는 방향이 둘인데 둘 다 사용자에게 보이기 때문이다:

```

304 를 잘못 주면  바뀐 문서를 **옛것으로 보여준다**  <- 이쪽이 더 나쁘다
```

`test_api_cache_headers.py` 5절에 17개 검사를 넣었다(약한 비교 / 목록 / `*` /
