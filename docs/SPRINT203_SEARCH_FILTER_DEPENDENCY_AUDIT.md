## 1. 지금 무슨 일이 일어나는가

프런트는 파라미터 5개를 만든다 — 면적 4(`min/max_building_area`,
`min/max_land_area`) + `special_conditions`. 백엔드 `api/v1/search.py` 에는
그 이름의 `Query` 파라미터가 **없다.** FastAPI 는 모르는 쿼리 파라미터를 조용히 버린다.

실측(TestClient, 읽기 전용):

```
기준                              200  total=9
min_building_area=30              200  total=9
max_land_area=1                   200  total=9      <- 1㎡ 이하만 남아야 하는데 그대로
special_conditions=유치권          200  total=9
완전히없는파라미터=1                200  total=9
```

`max_land_area=1` 이 9건을 그대로 돌려준다. 오류도 경고도 없다.
**조건을 걸었는데 전체 결과가 나오는 상태**이고, 화면만 봐서는 구분할 수 없다.

지금은 무해하다 — 해당 UI 가 `준비 중입니다` 자리표시자라 값이 실릴 수 없다.
값이 들어오는 유일한 경로는 **URL 직접 편집**이다(`parseFormState()` 가 URL 에서
읽어 폼에 넣고, `buildSearchQuery()` 가 다시 실어 보낸다 — 왕복은 하는데 아무 효과가 없다).

**이미 가드가 있다.** `tests/frontend-contract.test.mjs` 의 "검색 파라미터 계약"
(Sprint 55/2026-08-14) 이 세 가지를 고정한다.

1. 프런트가 만드는 키가 백엔드 파라미터를 벗어나지 않는다 (미지원 5개는 화이트리스트)
2. 화이트리스트에 올린 것이 **실제로 아직 미지원인지** 역방향 확인 — 구현되면 실패한다
3. `buildSearchQuery()` 와 `FILTER_PARAM_KEYS` 가 같은 집합인지

가드가 **안 보는 것**: 백엔드가 모르는 파라미터를 조용히 무시한다는 사실 자체.
이건 FastAPI 의 기본 동작이고 이 저장소가 정할 문제는 아니지만,
**필터를 구현할 때 부분 구현이 가장 위험**하다는 뜻이다 — 4개 중 2개만 붙이면
나머지 2개는 계속 조용히 무시된다.

## 2. 면적 — 데이터는 이미 있다

### 2.1 어디에 있는가

법원 목록의 소재지 칸은 주소 뒤에 물건 표시를 대괄호로 붙여 준다.
실측(서울중앙지방법원 목록 페이지, 2026-08-18):

```
셀3: 서울특별시 종로구 성균관로7길 37(명륜3가) 2층202호 [집합건물 철근콘크리트구조 29.95㎡]
```

이 칸이 `collect_list_items()` -> `item_info["addr"]` -> `AuctionItem.address`
-> `normalize_address()` -> **`full_address` 로 그대로 저장**된다.
`normalize_address()` 는 `full_address` 에 원문을 손대지 않고 넣는다.

즉 **의도해서 보존한 것이 아니라 손대지 않아서 남아 있다.**

### 2.2 얼마나 있는가 (auction_item 1,876행 실측)

```
집합건물   1,100행 (58.6%)      [집합건물 철근콘크리트구조 17.08㎡]
토지         713행 (38.0%)      [토지 대 420㎡]
건물          49행 ( 2.6%)      [건물 ... 1층 13.23㎡ 2층 164.7㎡ ...]
차량/선박/중기 14행 ( 0.7%)     면적 개념 자체가 없다
```

수치를 뽑을 수 있는 행 **1,852 / 1,876 = 98.7%**.

### 2.3 그런데 "첫 번째 숫자"를 쓰면 안 된다

수치가 2개 이상인 행이 **44건**. 첫 값만 쓰면 이렇게 틀린다.

```
     6.00㎡ ->    618.81㎡  (103배)   4층 다가구주택 1층 6㎡ 2층 197.75㎡ 3층 197.75㎡ 4층 192.62㎡
    13.23㎡ ->    471.03㎡  ( 36배)   4층 다가구주택 1층 13.23㎡ 2층 164.7㎡ ...
     9.28㎡ ->    294.16㎡  ( 32배)   5층 제2종근린생활시설
```

1층이 필로티/주차장이면 첫 숫자가 유독 작다. **가장 흔한 건물 형태에서 가장 크게 틀린다.**

같은 계열의 함정 네 가지를 실측으로 확인했다.

| 함정 | 건수 | 무슨 일이 벌어지나 |
|---|---|---|
| 다층 건물 (수치 여러 개) | 44 | 첫 값 = 1층 면적. 최대 103배 과소 |
| 지분 매각 (`N분의 M`) | 128 (6.8%) | 표시 면적은 **전체**, 파는 것은 지분. 예: 임야 13,607,986㎡ 중 6930분의 529 |
| 평 단위 | 5 | `[토지 전 1048평]` — ㎡ 정규식이 0건으로 처리 |
| 대괄호 중첩 | 2 | `[토지 전[현황:묵전(죽림)] 105㎡ ...]` — 단순 `\[([^\]]*)\]` 가 깨진다 |
| 현황 병기 | 11 | `2층 7.60㎡(현황: 24.7㎡)` — 등기부와 현황이 다르다 |

그리고 상세페이지를 열면 더 나빠진다. `목록내역` 표의 셀 하나에 등기부 표제부가
통째로 들어 있다(실측, 2024타경3528):

```
1동의 건물의 표시 ... 1층1987.50㎡ 2층2129.50㎡ ... 6층408㎡
전유부분의 건물의 표시 ... 면 적 : 5.10㎡
대지권의 목적인 토지의 표시 ... 대 2142㎡   대지권의 비율: 2142 분의 1.57
```

같은 물건에 대해 **1987.50 / 5.10 / 2142 / 1.57** 이 동시에 있다.
정답은 건물 5.10㎡, 토지 1.57㎡ — 아무 숫자나 집으면 **400배 틀린다.**

### 2.4 결정해야 하는 것 (제품 정책 = 승인 영역, 이번 SKIP)

1. **`min_building_area` 를 걸면 토지 물건 713건(38%)은 어떻게 되는가?**
   전부 제외인가, 조건 무관으로 남기는가. 소스는 물건당 면적을 **하나**만 준다
   (집합건물이면 건물, 토지면 토지). 프런트는 건물/토지를 따로 받는다.
2. **다층 건물은 무엇을 면적으로 보는가?** 연면적 합계 / 1층 / 최대층.
3. **지분 물건은 전체 면적인가 지분 면적인가?** 128건(6.8%)의 결과가 바뀐다.
4. **등기부와 현황이 다르면 어느 쪽인가?** (11건)

이 넷은 전부 "무엇을 파는가"에 대한 판단이라 코드가 정할 수 없다.

### 2.5 만든다면 건드리는 곳

```
storage/database.py        컬럼 2개 + 마이그레이션 (auction_item, auction 양쪽 — 스키마 2세대)
normalizer/normalizer.py   대괄호 파서 (위 함정 4종 처리)
migrate_execute.py         REFRESH_DOC_TYPES_BY_FIELD 에 면적 변경이 문서 재수집을 부르는지
api/v1/search.py           Query 4개 + WHERE + 인덱스
src/app/search/SearchForm.tsx   "준비 중입니다" -> 실제 입력
tests/frontend-contract.test.mjs   KNOWN_UNSUPPORTED 에서 4개 제거 (안 빼면 검사 2가 실패)
```

**재크롤은 필요 없다.** 1,876행 전부 backfill 로 채울 수 있다.
다만 backfill 은 운영 DB 쓰기라 승인 영역이다.

## 3. 특수조건 — 소스는 있는데 읽지 않는다

### 3.1 어디에 있는가

법원 목록 표의 **6번째 칸(셀5)** 이다. 실측(서울중앙지방법원, 2026-08-18):

```
=== 물건행 (8셀) ===
  셀0: 서울중앙지방법원2024타경117502
  셀1: 서울중앙지방법원 2024타경117502          <- collect_list_items 가 읽는다
  셀2: 1                                        <- 읽는다
  셀3: ... [집합건물 철근콘크리트구조 29.95㎡]   <- 읽는다
  셀4: 지도
  셀5: 임차보증금반환채권승계인 주택도시보증공사의
       매수인에 대한 대항력 포기조건 매각        <- ★ 읽지 않는다
  셀6: 380,000,000                              <- 읽는다
  셀7: 경매4계 2026.08.19                       <- 읽는다
```

`collect_list_items()` 는 셀 0·1·2·3·6·7 만 쓴다. **셀5 는 코드에 등장하지 않는다.**
표본 3건 중 1건에 값이 있었다.

### 3.2 자유 문장이지 분류가 아니다

프런트의 특수조건은 체크박스 목록(유치권 / 법정지상권 / 지분매각 / 대항력있는임차인 …)이다.
소스는 위처럼 **문장 하나**다. 둘을 잇는 분류 사전이 필요하고,
그 사전이 곧 **"이 물건은 위험한가"를 서비스가 판정하는 기준**이 된다 — 제품 결정이다.

`specialSearchType`(AND/OR/제외 조합)은 더 나아간다. 백엔드에 대응 개념이 없고
프런트도 전송하지 않는다(주석에 명시). 조합 의미론 자체를 정의해야 한다.

### 3.3 그리고 이 칸이 전부가 아니다

유치권·법정지상권·분묘기지권은 목록 비고가 아니라 **매각물건명세서(spec.pdf)**
의 비고란에 적힌다. 그쪽은:

- PDF 는 이미 수집돼 있다 (`doc_raw` SPEC 197행)
- `pdfplumber` 도 이미 의존성에 있다
- `load_spec_data.py` 가 이미 SPEC 을 파싱한다 — 다만 **임차인현황 표만** 뽑는다
- ★ 그리고 `load_spec_data.py` 는 **어느 `run_*.bat` 에도 없다** (수동 스크립트)

즉 특수조건을 명세서에서 뽑으려면 "파서 추가"가 아니라
**"이 스크립트를 일정에 넣을 것인가"** 라는 운영 결정이 먼저다(기존 SKIP 항목).

### 3.4 만든다면 건드리는 곳

```
crawler/base_crawler.py    collect_list_items() 에 셀5 수집 (+1 필드)
models/auction_item.py     필드 추가
normalizer/normalizer.py   normalize_item() 에 매핑 추가  ★ 여기가 진짜 경계다
storage/database.py        컬럼 + 마이그레이션 (2세대 양쪽)
api/v1/search.py           Query + WHERE (AND/OR/제외 의미론 확정 후)
```

**재크롤이 필요하다** — 기존 1,876행에는 셀5 가 없다. 전량 크롤 약 3.1시간.

> **[정정 2026-08-18 Sprint 209] 위 문장은 틀렸다. 원문은 기록으로 남긴다.**
>
> 비용의 문제가 아니라 **불가능**이다. 크롤러는 법원별 **기일 목록**에 올라 있는
> 물건만 본다(`go_to_schedule()` -> 기일 링크 클릭 -> `collect_list_items(MAX_ITEMS)`).
> 기일이 지난 물건은 그 목록에 없고, 사건번호 직접검색으로도 조회되지 않는다
> (`enqueue_documents()` 주석의 실측 8건). 그래서 **기일이 지난 1,867건에는
> 특수조건을 영원히 채울 수 없다.**
>
> 그리고 `MAX_ITEMS = 10` 이라 1회 실행이 보는 상한은 60곳 x 10건 = **600건**이다.
> "전량 크롤 3.1시간"이라는 표현 자체가 성립하지 않는다.
>
> 올바른 서술: **특수조건은 앞으로 새로 기일 목록에 오르는 물건부터만 채워진다.**
> 과거분 소급은 이 파이프라인으로 불가능하다.
>
> ★ 면적은 이 정정의 영향을 받지 않는다 — 이미 `full_address` 에 저장돼 있어
> **DB 안에서** backfill 할 수 있다(재크롤 불필요). 그 부분은 그대로 유효하다.

## 4. 이번에 찾은 더 큰 것 — 수집해 놓고 버리는 경계

`crawl_detail()` 은 상세페이지에서 다섯 덩이를 모은다.

```
basic_info         parse_basic_info()          기본 정보 표
schedule           parse_section_table(기일내역)
property_list      parse_section_table(목록내역)      <- 등기부 표제부 전문(면적 포함)
appraisal_summary  parse_gamjung()
nearby_cases       parse_section_table(인근매각물건사례)
```

`normalize_item()` 은 이 중 **아무것도 저장하지 않는다.** 21개 필드만 통과한다.
`property_list` / `schedule` / `nearby_cases` 는 코드 전체에서 **읽는 곳이 없다**
(`grep` 결과: 정의와 대입뿐).

`appraisal_summary` 만 예외로 `ValidationEngine` 이 메모리에서 쓰고 버린다
(이미 `test_pipeline_integrity.py:859` 에 기록돼 있다).

그래서 **크롤러는 매 물건마다 이 표들을 긁는 비용을 치르고 결과를 버린다.**
면적 필터를 만들 때 "상세페이지에서 면적을 새로 가져와야 한다"고 판단하기 쉬운데,
사실은 **이미 가져오고 있고 버리는 중**이다.

다만 목록 셀3 의 대괄호가 더 나은 소스다 — 짧고, 종류 접두어가 붙어 있고,
1,876행에 이미 저장돼 있다. 목록내역 전문은 파싱 난도가 훨씬 높다(2.3 참고).

## 5. 이번에 실제로 한 것 (감사 범위 안)

필터는 만들지 않았다. 대신 **이미 갖고 있는 데이터를 조용히 잃는 경로**를 막았다.

`test_normalizer.py` — 주소 끝 대괄호 보존 가드(사례 4 x 검사 3 = 12건).

면적이 오직 `full_address` 대괄호에만 있는데, 그것을 지키는 검사가 하나도 없었다.
누가 "주소를 깔끔하게" 만들려고 대괄호를 떼면 **면적은 이 저장소에서 완전히 사라진다** —
오류도 빈 값도 아니고 주소가 예뻐질 뿐이라 알아챌 방법이 없다.

고정한 것:

1. `full_address` 가 입력과 **글자 하나까지 같다**
2. 대괄호와 그 안의 문자열이 그대로 살아 있다
3. **대괄호 안의 숫자(면적/연식)가 지번으로 새어 나오지 않는다**

변이 검증 2종:

```
full_address 에서 대괄호 제거          -> 8건 FAIL
지번이 대괄호 안 면적을 먼저 집게 함   -> 3건 FAIL
```

기대값을 처음에 내가 틀리게 적었다(도로명주소 `...로7길 37(명륜3가)` 는 지번이
빈 문자열로 나온다 — 숫자 뒤에 곧바로 괄호가 와서 lookahead 가 안 맞는다).
**실측으로 고쳤고, 기대값은 "이래야 옳다"가 아니라 "지금 이렇게 나온다"를 고정한 것**임을
주석에 명시했다. 그 지번 규칙 자체는 별개 사안이라 여기서 판단하지 않는다.

---

## 6. 하지 않은 것과 이유

| 하지 않은 것 | 이유 |
|---|---|
| 면적 컬럼 추가 + backfill | 의미 정의가 제품 결정. 운영 DB 쓰기 |
| 대괄호 파서 구현 | 위와 같음. 파서만 만들면 "무엇을 파싱했는지" 정의가 없다 |
| `collect_list_items()` 에 셀5 추가 | **과거분 소급 불가**(기일 지난 물건은 목록에 없다) + 분류 사전이 제품 결정 |
| 특수조건 분류 사전 | 서비스의 위험 판정 기준 = 제품 결정 |
| `load_spec_data.py` 배치 편입 | 운영 스케줄 결정 (기존 SKIP 유지) |
| `downloads/` 고아 8개 정리 | 소유자 확정 불가 (기존 SKIP 유지) |

## 7. 한 줄 요약

> 면적은 **정의가 없어서** 못 만들고, 특수조건은 **읽지 않아서** 못 만든다.
> 둘 다 코드 문제가 아니라 결정 문제이고, 그 결정은 승인 영역이다.
> 그동안 할 수 있는 것은 **이미 가진 데이터를 잃지 않는 것**이다 — 그것만 했다.
