## 1. 실측 (실브라우저 Chrome, `/search`, 2026-08-19)

```
검사한 텍스트                       199개
WCAG AA 대비(4.5:1) 미달             81개  (41%)
text-gray-400 on white 실제 대비      2.6:1   <- 기준의 58%
탭 타깃 53개 중 44px 미만             44개  (83%)
  그중 24px 미만                       5개   <- ★ 위반 아님. 아래 정정 참고
14px 미만 텍스트                     111개
```

### 가장 나쁜 것은 "무엇이" 작고 흐린가이다

| 화면 요소 | 크기 | 대비 |
|---|---|---|
| 물건 주소 | 12px | 2.6:1 |
| **"최저입찰가" 라벨** | **11px** | 2.6:1 |
| **"감정가 3.8억"** | **11px** | 2.6:1 |
| 건물 면적 | 12px | 2.6:1 |
| 헤더 내비(검색/관심물건/마이페이지/로그아웃) | 12px | 2.6:1, **탭 타깃 h=16px** |

**가격과 주소 — 이 서비스를 쓰는 이유 그 자체 — 가 화면에서 가장 읽기 어렵다.**

내비게이션 5개는 높이가 **16px** 다. Apple HIG 권장(44px)의 36% 다.

> ### ★ [2026-08-20 Sprint 225 정정] "WCAG 2.5.8 위반"은 **사실이 아니었다**
>
> 이 절은 원래 *"24px 미만이라 **규격 위반**"* 이라고 단정했다. **틀렸다.**
> SC 2.5.8 에는 예외가 다섯 개 있고, 그중 **간격(Spacing) 예외**가 여기 그대로 적용된다.
>
> > 24 CSS px 지름의 원을 각 타깃의 bounding box 중심에 놓았을 때 그 원들이
> > 서로 겹치지 않으면, 크기가 24px 미만이어도 적합이다.
>
> 실브라우저에서 그 기하를 직접 계산했다(2026-08-20, `/search`·`/properties/{id}`·`/mypage`).
>
> ```
> 24px 미만 타깃            /search 5개 · 상세 9개 · /mypage 5개
> 원이 겹치는 쌍            **0쌍** (세 화면 전부)
> 가장 가까운 중심 간 거리   54px   (임계 24px 의 2.25배)
> -> SC 2.5.8 위반 0건 — 간격(Spacing) 예외로 **적합**
> ```
>
> **왜 이 정정이 중요한가.** 아래 5절 개선안이 헤더 내비를 **1순위**로 올린 근거가
> 바로 *"WCAG 2.5.8 AA 위반이라 디자인 논쟁 여지가 가장 적다"* 였다.
> 그 전제가 사라지면 1순위도 사라진다 — 헤더 내비 확대는 규격 준수가 아니라
> **순수한 디자인 판단**이고, 규격 위반은 오히려 **대비(SC 1.4.3)** 쪽에만 있다.
>
> 크기 자체가 작다는 사실은 그대로다(어르신 사용성에는 여전히 불리하다).
> 다만 그것을 **"규격 위반"이라고 불러서는 안 된다.**

## 3. ★ 측정 도구가 한 번 틀렸다

처음 만든 대비 계산기는 CSS 색 문자열에서 **숫자만 뽑아 RGB 로** 읽었다.
그런데 이 저장소의 Tailwind v4 는 **`oklch()`** 로 색을 낸다.

```
oklch(0.546 0.245 262.881)  ->  잘못 읽으면 RGB [0.546, 0.245, 262.881]
                            ->  대비 1.06 같은 **불가능한 값**
```

그대로 보고했으면 멀쩡한 색을 결함으로 올렸을 것이다.
canvas 로 브라우저에게 변환을 맡기고 **알려진 값으로 도구부터 검증**한 뒤 다시 쟀다.

```
검증  흑백 = 21.0        (정답 21:1)
      #9ca3af on white = 2.54  (정답 2.54:1)
      oklch 파싱 -> [21, 93, 252]
```

이번 세션에서 측정 도구가 틀린 **다섯 번째** 사례다.
규칙은 그대로다 — **결함처럼 보이면 도구를 먼저 의심한다.**

### 재지 못한 것도 적는다

**모바일 뷰포트(390~412px)에서의 레이아웃은 확인하지 못했다.**
브라우저 자동화의 창 리사이즈가 이 환경에서 페이지 뷰포트에 반영되지 않았고
(`innerWidth` 가 1920 에서 안 바뀐다), 앱이 `X-Frame-Options: DENY` 라
iframe 으로 390px 를 만드는 우회도 막혔다(그 헤더 자체는 올바른 보안 설정이다).

즉 **"모바일에서 깨지지 않는다"는 아직 주장할 수 없다.** 확인한 것은
데스크톱 1920px 에서의 대비·글자크기·탭타깃과, 뷰포트 메타가 올바르다는 것뿐이다.

```
<meta name="viewport" content="width=device-width, initial-scale=1"/>   (Next.js 기본, 확인함)
확대 차단(user-scalable=no / maximum-scale=1)  없음 (확인함)
```

## 5. 개선안 (제품 결정 대기 — 임의로 하지 않는다)

우선순위는 **읽는 빈도 x 지금의 나쁨** 으로 매겼다.

| 순위 | 대상 | 지금 | 제안 | 근거 |
|---|---|---|---|---|
| ~~1~~ | 헤더 내비 5개 | h=16px | h>=44px(패딩만 추가) | ★ **근거 철회(Sprint 225)** — 간격(Spacing) 예외로 SC 2.5.8 **적합**(중심 간 54px vs 임계 24px). 규격 위반이 아니라 순수 디자인 판단이라 1순위가 아니다 |
| 2 | 물건 주소 / 가격 라벨 | 11~12px, 2.6:1 | 14px 이상, `text-gray-600`(4.6:1) | 판단에 쓰는 정보가 가장 안 보인다 |
| 3 | 상세페이지 전반 | text-xs 55곳 | 본문 최소 14px | 실제 판단이 일어나는 화면 |
| 4 | 큰글씨 모드 | 없음 | 루트 `font-size` 스케일 + `rem` 전환 | px 고정이 많아 **선행 작업이 필요**하다 |

> **[2026-08-19 Sprint 220 정정] 위 4번의 근거가 틀렸다.**
>
> 이 절은 처음에 *"지금 크기가 대부분 px 고정(`text-xs`, `text-[11px]`)이라 루트
> 글꼴만 키워도 본문이 따라 커지지 않는다"* 고 적었다. **재 보니 사실이 아니다.**
>
> 빌드된 CSS 를 직접 열어 확인했다 — Tailwind v4 의 이름 있는 크기는 **rem 기반**이다.
>
> ```
> --text-xs: .75rem      .text-xs { font-size: var(--text-xs) }
> --text-sm: .875rem     .text-sm { font-size: var(--text-sm) }
> ```
>
> 즉 `text-xs`(111곳)는 루트 글꼴을 키우면 **그대로 따라 커진다.**
> 닿지 않는 것은 **대괄호 임의값**뿐이고, 실측하면 **8곳**이다
> (`text-[11px]` 6 + `text-[10px]` 2). 나머지 임의값 2곳(`max-h-[420px]`,
> `max-w-[180px]`)은 상한이라 글자 크기와 무관하다.
>
> **그래서 선행 작업은 "전면 rem 전환"이 아니라 그 8곳을 rem 유틸리티로 바꾸는 것**
> 이다. 훨씬 작은 일이고, 큰글씨 토글은 그 뒤 바로 붙일 수 있다.
> `test_frontend_accessibility.py` 6 이 그 8곳을 상한으로 잠갔다
> (늘어나면 큰글씨가 닿지 못하는 자리가 그만큼 늘어난다).
>
> 교훈: **"대부분 px 고정"은 소스의 겉모습만 보고 내린 추정이었다.**
> 빌드 결과를 열어 봤어야 했다.
