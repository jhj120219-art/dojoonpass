> 앞 Sprint: `docs/SPRINT108_AUTHZ_COVERAGE_NARROWING.md`
>

> 다른 세션의 편집 대상이라 충돌을 피했다.

지시받은 감사 패턴 **"같은 의미인데 여러 코드가 서로 다르게 판단하는 문제"** 중
`deleted` / `visible` 쌍을 봤다. 지금 동작에는 결함이 없었지만,
**그 상태를 지키는 체크리스트가 실제 코드보다 짧았다.**

## 1. 현재 상태 (실측)

```
soft delete 컬럼이 있는 테이블 : favorites, search_presets  (deleted_at / deleted_by)
실제 삭제 방식                 : DELETE FROM ...        <- 하드 삭제
deleted_at 을 채우는 코드      : 0곳
조회에서 deleted_at 을 거르는 곳: 0곳
현재 deleted_at IS NOT NULL 행 : 0
```

**일관돼 있다.** 아무도 값을 채우지 않으므로 아무도 거를 필요가 없다.
컬럼은 Migration 016이 전환을 대비해 미리 만들어 둔 것이고, 이 사실은
`test_api_regression.py` §28 이 **이미 못 박아 두고 있었다**(Sprint 71).

## 2. ★ 그런데 "함께 고칠 곳" 목록이 3개뿐이었다

§28 에는 이런 의도가 적혀 있다.

> 소프트 삭제를 배선할 때 **함께 고쳐야 하는 조회 지점**을 소스로 고정해 둔다.

그리고 세 파일을 손으로 적어 뒀다.

```
favorites.py / search_presets.py / search.py
```

**그 테이블을 읽는 파일은 실제로 5개다.** 빠진 둘은 이렇다.

| 빠져 있던 곳 | 무엇을 읽나 | 배선 후 증상 |
|---|---|---|
| `api/v1/item.py:65` | 물건 상세의 **하트**(`SELECT 1 FROM favorites`) | 지운 관심물건인데 상세 화면에는 하트가 **켜진 채로** 남는다 |
| `api/v1/admin.py:590,605` | 사용자 목록 UNION, `favorite_count` | 관리자 통계가 **지운 즐겨찾기까지** 센다 |

이 목록의 용도가 "전환할 때 이것들을 함께 고쳐라"인데 목록 자체가 불완전하면,
그것을 믿고 전환한 사람은 **정확히 그 두 곳을 빠뜨린다.**
사용자에게는 "지웠는데 상세에는 남아 있다"로 보인다 ― 조용히 틀리는 종류다.

> Sprint 106의 "정적 확인 완료" 주석이 5개 중 2개에서 사실이 아니었던 것과 **같은 실패 모양**이다.
> 손으로 적은 목록은 코드가 늘면 어긋나고, 어긋난 사실은 아무도 알려 주지 않는다.

## 3. 고친 것 ― 목록을 손으로 적지 않고 코드에서 유도

`api/` 를 훑어 **그 테이블을 질의로 쓰는 파일**을 찾아, 각각에 `deleted_at` 이 없음을 확인한다.
새 라우터가 `favorites` 를 읽기 시작하면 목록에 **자동으로 들어온다.**

```
[PASS] 소프트 삭제 테이블을 읽는 파일을 실제로 찾았다
   대상 파일 5개: api/v1/admin.py, api/v1/favorites.py, api/v1/item.py,
                 api/v1/search.py, api/v1/search_presets.py
[PASS] 아직 어느 조회에도 deleted_at 조건이 없다: []
```

### 만들면서 걸린 것 두 가지 (둘 다 내 검사의 문제)

1. **주석에 컬럼명이 나오면 오판한다.** 앞선 스프린트에서 3번 겪은 실패라
   처음부터 `tokenize` 로 주석을 걷어낸 **코드만** 보게 했다.
2. **테이블명이 그냥 등장하는 것으로 고르면 안 된다.** 처음엔 파일이 6개 나왔는데,
   `api/constants.py` 가 설명 **문자열**에 `"...(api/v1/search.py, search_presets.py)"`
   라고 적어 둔 탓이었다. 질의(`FROM|INTO|UPDATE|JOIN`)로 좁혀 5개로 정정했다.
   목록이 부정확하면 그 목록을 믿는 사람도 부정확해진다.

## 변이 검증

| | 변이 | 새 검사 | 예전 3개 목록이었다면 |
|---|---|---|---|
| M71 | `item.py` 에 `AND deleted_at IS NULL` 배선 | **검출 O** ― 파일까지 지목 | **놓침** |
| M72 | `admin.py` 의 `favorite_count` 에 배선 | **검출 O** | **놓침** |

두 변이 모두 **예전 목록에 없던 파일**이다. 새 검사만 잡는다 ―
이 스프린트가 값을 더했다는 직접 증거다. 원복 후 전부 통과.

### 판정하지 못한 것 (정직하게 남긴다)

`readers >= 5` (목록이 조용히 줄어드는 것을 막는 자기보호 검사)의 **발동은 재현하지 못했다.**
`item.py` 의 질의를 다른 테이블로 바꾸는 변이를 두 번(M74, M74b) 시도했는데,
둘 다 **§28 에 도달하기 전에 실행이 멈췄다**(앞선 테스트가 먼저 실패). 출력에
`대상 파일` 줄 자체가 없었다 ― **검사가 실행되지 않았으므로 판정은 무효**다.
"가드에 구멍"이라고 적지 않는다. 이 검사는 정상값 5에서 통과하고 목록을 출력하는 것까지만 확인됐다.
