# 마이리스트 복붙/내보내기 — 구현 가능 범위 분석 (추측 없이)

2026-08-19. **구현하지 않았다.** `docs/roadmap.md` 향후 기능 1번의
*"단, 현재 구현 가능 범위를 먼저 분석한다. 상대 서비스의 실제 입력 형식과 호환 여부를
확인하고 추측하지 않는다"* 를 그대로 수행한 결과다.

---

## 0. 결론 먼저

**지금 우리 데이터만으로는 "붙여넣으면 그대로 들어가는" 내보내기를 만들 수 없다.**
막는 것은 기능이 아니라 **식별자 자체**다. 그리고 상대 서비스의 입력 형식은
**확인하지 못했다**(외부 서비스 조사는 이 작업의 범위 밖이다).

---

## 1. 우리가 가진 것 (실측, `auction_item` 1,876행)

내보낼 수 있는 필드는 전부 있다.

```
식별   court_name / case_no / item_no / id
값     appraisal_price / minimum_bid_price / bid_rate / fail_count
일정   auction_date / status
주소   sido / sigungu / dong / lot_number / full_address / property_type
```

`favorites` 테이블도 존재한다(마이리스트의 원천). **다만 현재 0행**이다 —
기능은 있으나 아직 쓰인 데이터가 없다.

---

## 2. 막는 것 — 식별자가 단일 값이 아니다 (실측)

### 2-1. 사건번호의 22.7% 가 **병합 사건**이다

```
단일 사건번호 (YYYY타경NNNNN)   1,451행  (77.3%)
병합 사건 ("A / B")               425행  (22.7%)
그 외                                0행
```

실제 값 예: `2008타경25092 / 2015타경19958`

**한 물건에 사건번호가 둘 이상 붙어 있다.** 상대 서비스가 사건번호 한 개를 기대한다면
이 425행은 **그대로 붙여넣을 수 없다.** 어느 쪽을 대표로 쓸지는 우리가 정할 수 없다 —
법원 원천이 둘 다 유효한 사건으로 표시하고 있기 때문이다.

(이 저장소는 이 값 때문에 이미 한 번 사고를 겪었다 —
`crawler/resume.py:case_no_matches_list_entry()` 가 부분 문자열 비교를 버리고
`" / "` 로 쪼개 정확히 비교하도록 고친 이유가 이것이다.)

### 2-2. 물건번호가 1이 아닌 행이 **629개(33.5%)** 다

```
item_no = 1    1,247행
      2          219행
      3          118행
      4           80행
      5           52행
      6           35행 ...
```

즉 **사건번호만으로는 물건을 특정할 수 없다.** 상대 서비스가
`사건번호`만 받는지, `사건번호-물건번호`를 받는지에 따라 3분의 1이 어긋난다.

### 2-3. 법원명 표기가 60종이고, 우리 표기가 표준인지 알 수 없다

```
...지방법원  18종
...지원      42종
그 외         0종
```

우리 표기는 `서울중앙지방법원` / `안산지원` 형태다.
상대 서비스가 같은 문자열을 쓰는지, 법원 코드를 쓰는지는 **확인하지 못했다.**

---

## 3. 확인하지 못한 것 (추측하지 않는다)

| 항목 | 상태 |
|---|---|
| 지지옥션의 실제 입력 형식 | **확인하지 못함** |
| 탱크옥션의 실제 입력 형식 | **확인하지 못함** |
| 사건번호 단독인지 물건번호 포함인지 | **확인하지 못함** |
| 법원 표기 방식(문자열/코드) | **확인하지 못함** |
| 병합 사건을 상대가 어떻게 받는지 | **확인하지 못함** |
| 한 번에 여러 건을 붙여넣을 수 있는지(줄바꿈/구분자) | **확인하지 못함** |

**"확인하지 못함"과 "없음"을 섞지 않는다.** 위 여섯 줄은 전부 전자다.

---

## 4. 그래서 지금 만들 수 있는 것 (제안, 미구현)

상대 형식을 몰라도 **손해 보지 않는 범위**가 있다.

### 4-1. 형식 중립 내보내기 (안전)

```
CSV / TSV 로 우리 필드를 그대로 내보낸다
헤더: 법원, 사건번호, 물건번호, 소재지, 감정가, 최저입찰가, 매각기일, 유찰횟수
```

- 상대가 무엇을 받든 **사람이 열에서 골라 붙일 수 있다**
- 병합 사건은 원본 문자열을 그대로 둔다(우리가 임의로 쪼개지 않는다)
- 구현 난이도 낮음, 되돌리기 쉬움

### 4-2. 클립보드 복사 (안전)

한 줄에 한 물건, 탭 구분. 스프레드시트에 그대로 붙는다.

### 4-3. 상대 서비스 전용 포맷 (**보류**)

**형식을 확인하기 전에는 만들지 않는다.** 잘못된 형식으로 내보내면
"붙여넣었는데 안 들어간다"가 되고, 그 실패는 우리 쪽에서 보이지 않는다
(이 저장소가 반복해 경계해 온 "조용한 실패"의 전형이다).

확인 방법은 **사람의 판단이 필요하다** — 상대 서비스 계정으로 실제 입력 화면을
보거나, 공개 도움말을 확인해야 한다. 자동 조사는 이 작업의 범위 밖이다.

## 5. 선행 조건

```
favorites 0행          마이리스트에 담긴 물건이 있어야 내보낼 것이 생긴다
데이터 공급 재개        검색 재고가 0이 되면 담을 물건 자체가 없다 (Release Blocker)
```

즉 이 기능은 **데이터 공급 재개 뒤**에 값을 갖는다. 지금 만들면 빈 목록을 내보낸다.

## 6. 승인/판단이 필요한 것

- 상대 서비스 입력 형식 확인(사람의 확인 필요)
- 병합 사건을 어느 쪽으로 내보낼지(**제품 결정** — 우리가 정하면 안 된다)
- CSV/TSV/클립보드 중 무엇을 먼저 낼지(제품 결정)
