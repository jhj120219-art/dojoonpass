# Sprint 229 — 변경 감지 감사: "없음" · "실패" · "관측 공백"의 구분

**날짜** 2026-08-20. 읽기 전용 감사 + 공허한 단언 1건 수정. **운영 DB 무변경.**

---

## 0. 이 감사가 묻는 것

Backlog #10 의 요구는 두 줄이다.

```
"없음"과 "실패"를 구분
관측 공백과 실제 변경 없음 구분
```

그래서 "0건"이라는 값이 나올 때마다 **왜 0인가**를 되물었다.

---

## 1. 상태 어휘는 구분되어 있다 (코드는 옳다)

```
document_status        COLLECTING 5,069 / READY 556 / FAILED 3
  READY       파일이 실제로 있다
  NO_IMAGE    법원이 제공하지 않는다   = **없음**(positive signal)
  FAILED      받으려다 실패했다        = **실패**
  COLLECTING  아직 모른다              = **관측 공백**
```

모순도 없다.

```
"사진 없음"인데 사진 행이 있는 물건   0개
"사진 READY"인데 사진 행이 없는 물건  0개
auction_image 45행 중 해시 없는 행    0개   (같은 사진 판정의 근거가 온전하다)
```

---

## 2. ★ "변경 0건"은 변경이 없다는 뜻이 아니었다

```
doc_raw            556행, doc_version 전부 **1**   (2 이상 0건)
큐의 refresh 행    0개
마지막 문서 수집 시도   2026-07-12T17:30   <- 39일 전
마지막 크롤             2026-08-12         <- 8일 전
```

`doc_version` 이 전부 1이면 "문서가 한 번도 바뀌지 않았다"로 읽고 싶어진다.
**그렇게 읽으면 안 된다.** 재수집이 39일 동안 한 번도 돌지 않았으므로,
바뀌었는지 **관측한 적이 없다.**

```
변경 없음  =  관측했는데 같았다
관측 공백  =  아예 보지 않았다        <- 지금은 이쪽이다
```

변경 감지 코드가 옳다는 증거도, 그르다는 증거도 여기에는 없다.
`test_asset_pipeline.py` 의 변경 감지 회귀(합성 픽스처)는 계속 통과하므로
**로직 자체는 검증돼 있다** — 없는 것은 운영 관측뿐이다.

---

## 3. ★ 절대 실패할 수 없는 단언을 또 찾았다 (수정)

`test_document_status_sync.py` §7 은 실제 DB 에서 "끝나지 않는 수집중"을 센 뒤
이렇게 단언하고 있었다.

```python
check_true("측정할 수 있다(조회 경로가 유효)", expired_collecting >= 0)
check_true("두 값을 구분해서 셀 수 있다", live_collecting >= 0)
```

`COUNT(*)` 는 **언제나 0 이상**이다. 조인이 깨져 0행을 세든, 컬럼 이름이 바뀌어 빈
결과가 나오든 똑같이 통과한다. *"측정 경로가 유효하다"* 를 검증한다고 적어 놓고
**아무것도 검증하지 않았다** — `docs/BUGS.md` #161(Sprint 226)과 같은 계열이다.

### 깨질 수 있는 불변식으로 바꿨다

```
만료 + 진행중 + 고아  ==  COLLECTING 전체
```

어긋나면 그 차이는 곧 **대응 물건이 없는 `document_status` 행**이다.
조인이 조용히 떨어뜨리는 행이고, **지금까지 아무도 세지 않았다.**

### 변이 — 옛 판본은 같은 결함을 통과시킨다

운영 DB 는 건드리지 않고 **사본**에 결함을 주입해, 검사가 쓰는 것과 같은 질의로 재현했다.

```
정상        만료 5069 / 진행중 0 / 전체 5069 / 고아 0
            지금 판본 -> 통과      옛 판본 -> 통과
고아 1행 주입  만료 5069 / 진행중 0 / 전체 5070 / 고아 1
            지금 판본 -> **FAIL**   옛 판본 -> **통과**
```

실측 결과 현재 고아 행은 **0개**다(코드는 옳다). 다만 그것을 **확인할 수단이** 없었다.

## 4. 보류된 제품 결정의 비용이 커지고 있다 (수치 갱신)

`mark_queue_skipped_expired()` 는 큐만 닫고 `document_status` 를 **일부러** 건드리지
않는다. Sprint 73 이 검토하고 보류한 상태다 — enum 에 "대상 아님"이 없고,
FAILED 로 쓰면 실패가 아닌 것을 실패로 표기하게 되기 때문이다(제품 판단).

그 판단은 지금도 옳다. 다만 **비용이 16배로 자랐다.**

```
                                      Sprint 73(2026-08-14)   지금(2026-08-20)
document_status=COLLECTING 총합                  5,069             5,069
  그중 물건 진행중                                   20                 0
  큐에 살아 있는 행이 없어 **영원히 안 끝남**         183             2,921
  (별개) 큐 행이 아예 없는 물건 715개 x 3종                          2,145
```

이 물건들의 상세 화면은 계속 **"수집중"**(=기다리면 온다)이라고 말하지만
**아무리 기다려도 오지 않는다.**

### 그래도 "결함"이라고 부르지 않는 이유

숫자가 커진 원인은 상태머신이 아니라 **크롤이 2026-08-12 이후 멈춰** 큐가 전부
만료된 것이다. 즉 지금 보이는 것은 **데이터 공백의 그림자**다.
"수집이 정상 가동 중인데도 이 상태가 남는가"는 수집이 재개된 뒤에 다시 재야 판정할 수 있다.

**지금 사용자 노출은 0이다** — 기본 검색에 뜨면서 COLLECTING 인 물건은 **0개**다
(전부 기일이 지나 검색에서 빠졌다). 도달 경로는 관심물건·최근 본 물건·직접 URL 뿐이다.
