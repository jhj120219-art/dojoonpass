## 1. BUGS #151 — 모달이 키보드 포커스를 가두지 않았다 (수정함)

### 실측한 결함 (수정 전, 실브라우저 `/properties/505`)

```
모달을 연 직후 document.activeElement   "대표 사진 크게 보기"  <- 모달 **뒤**의 버튼
모달 안의 포커스 가능 요소               3개
화면 전체의 포커스 가능 요소             24개   -> 21개가 오버레이 뒤에 그대로 살아 있다
Tab 한 번(진짜 키 입력)                  "전경도 1번 크게 보기" (top 415, left 346)
                                         = 검은 오버레이에 **완전히 가려진** 버튼
Escape 로 닫은 뒤                        포커스가 헤매던 자리 그대로 (여는 버튼으로 복귀 안 함)
```

보이는 사용자에게는 아무 일도 아니다. 키보드만 쓰는 사용자는 모달을 열자마자
**자기가 어디에 있는지 알 수 없고**, Tab을 누르면 보이지 않는 버튼 위에 서게 되며,
거기서 Enter를 누르면 의도하지 않은 동작이 일어난다.

`aria-modal="true"`는 이것을 막지 못한다 — 순차 포커스 이동은 브라우저 규칙이라 코드로 잡아야 한다.

### 수정

`src/lib/useFocusTrap.ts` 신설. 세 가지만 한다.

```
1. 열릴 때   모달 안 첫 번째 포커스 가능 요소로 이동 (둘 다 "닫기" 버튼)
2. 열린 동안 Tab / Shift+Tab 이 양끝에서 순환 (capture 단계에서 가로챈다)
             + Tab 이 아닌 경로(클릭 등)로 나가면 focusin 으로 되돌린다
3. 닫힐 때   열기 전 포커스로 복귀. 그 요소가 사라졌으면 억지로 되돌리지 않는다
```

★ 순서가 중요하다 — 복귀 **전에** focusin 감시를 꺼야 한다.
순서가 바뀌면 자기 감시기가 복귀 포커스를 다시 모달 안으로 끌고 들어온다(가드가 잠근다).

두 모달(문서 뷰어 / 사진 라이트박스)에 배선했다. **픽셀 무변경.**

### 수정 후 실측 (진짜 마우스 클릭 / 진짜 Tab 키, 창이 활성인 상태)

```
사진 라이트박스 열기     포커스 -> '닫기'(모달 안)
Tab x3                   닫기 -> 이전 사진 -> 다음 사진 -> 닫기 (순환)
Shift+Tab                닫기 -> 다음 사진 (뒤로도 순환)
Escape                   포커스가 **여는 버튼 바로 그 노드**로 복귀 (=== 비교)
문서 뷰어                열기 -> '닫기' / Escape -> '매각물건명세서' 버튼으로 복귀
모달 밖으로 강제 포커스   '로그아웃'에 주자 곧바로 '닫기'로 되돌아옴
```

### ★ 측정 도구가 없는 결함을 만들 뻔했다 (기록)

문서 뷰어를 열면 **첫 번째만 포커스가 안 간다**는 결과가 반복해서 나왔다.
PDF iframe이 포커스를 뺏는다는 그럴듯한 설명까지 세웠다. **전부 틀렸다.**

원인은 측정 환경이었다 — 탭이 **보이지 않는 상태**(`visibilityState: hidden`)에서
`element.focus()`를 부르면 `activeElement`는 바뀌지만 **focus/focusin 이벤트가 전혀
발생하지 않는다.** 직접 확인했다: 스크립트가 직접 단 focusin 리스너가 **0회** 호출됐다.

탭을 보이게 하고 **진짜 마우스 클릭**으로 다시 재니 첫 열기부터 정상이었다.
포커스는 창 포커스 상태에 의존하므로, 보이지 않는 탭에서 잰 값을 근거로 쓰면 안 된다.

(그 과정에서 넣은 `focusin` 감시는 **유지한다** — 없는 결함 때문이 아니라, 마우스로
배경 컨트롤을 눌러 포커스가 새는 실제 경로를 막기 때문이다. 실측으로 동작을 확인했다.)

## 2. BUGS #152 — 나중에 나타나는 안내가 아무것도 읽히지 않았다 (수정함)

### 실측 (수정 전, 실브라우저 `/search`)

```
aria-live / role="alert" / role="status" 를 가진 요소   **0개**
```

이 서비스의 실패 안내는 전부 비동기 결과로 나중에 나타난다 — 로그인 실패, 관심물건 담기 실패,
검색조건 저장 실패, 목록 로드 실패. 나타날 때 스크린리더에는 **아무 일도 일어나지 않는다.**
특히 로그인은 **제출해도 반응이 없는 화면**이 된다(WCAG 4.1.3 Status Messages, AA).

### 수정 — 두 갈래

**(a) 개별 상태 메시지 13곳에 `role="alert"` / `role="status"`**

```
로그인 오류 / 안내            로그인 화면
시/군/구 목록 로드 실패        검색 폼
검색조건 저장·목록 실패        검색조건 프리셋
관심물건 담기 실패             검색목록 하트 / 상세 하트
등기부 신청 안내               상세
구독·결제·등기부 내역 로드 실패  마이페이지 3곳
관심물건 / 최근 본 물건 로드 실패
```

조건이 감싸는 **여는 태그 자체**에 붙인다. 안쪽 자식에 붙이면 바깥이 나타나는 순간을 놓친다.

**(b) 검색 결과에는 "항상 존재하는 한 줄"**

검색은 `router.push()`를 transition 안에서 부르는 **클라이언트 전환**이라 페이지가 다시 읽히지 않는다.
결과 목록에 `aria-live`를 달면 0건일 때 그 문단이 통째로 사라져 아무것도 알리지 못한다.
그래서 `sr-only` 한 줄을 `SearchScreen`에 **무조건 렌더**한다.

```tsx
<p className="sr-only" role="status" aria-live="polite">…</p>
```

### 실측 (수정 후)

```
live region                1개 (role=status / aria-live=polite)
기본 상태 텍스트            "검색 결과 총 9건, 1 / 1 페이지"
소프트 전환(정렬 변경) 후    **같은 DOM 노드가 유지된다** (마킹 후 === 비교)
실제 검색 제출(0건 조건)      같은 노드 / 텍스트 "검색 결과가 없습니다"
렌더 크기                   1x1 px, position absolute -> 화면에는 보이지 않는다
```

노드가 유지되고 **글자만 바뀐다** — live region이 요구하는 바로 그 조건이다.

**(c) 오류를 그 컨트롤과 연결** — 시/군/구 목록 로드 실패는 `aria-describedby`로 select에 묶었다.
`role="alert"`는 나타나는 순간 한 번 읽히지만, 나중에 Tab으로 그 컨트롤에 도착한 사람은
"왜 목록이 비어 있는지"를 알 길이 없었다. 오류가 없을 때는 `undefined`를 줘 빈 번지를 가리키지 않는다.

## 3. BUGS #153 — 화면 4개에 `main` 랜드마크가 없었다 (수정함)

### 기존 가드의 맹점에서 나왔다

Sprint 221의 8번 검사는 `<main>` 사용 횟수를 **저장소 전체로 합산**해 `>= 1`만 봤다.
검색 화면 하나가 갖고 있으면 나머지가 전부 없어도 통과한다. 실제로 그랬다.

```
/search              main 1
/properties/{id}     main **0**   <- 가장 오래 머무는 화면
/favorites           main **0**
/properties/recent   main **0**
/login               main **0**
/mypage              main 1 (본문만, 로딩 분기는 0)
```

`<main>`이 없으면 스크린리더 사용자는 **헤더/내비를 건너뛰고 본문으로 갈 수단이 없다**
(WCAG 2.4.1 Bypass Blocks).

### 수정

감싸는 `<div>`의 **태그만** `<main>`으로 바꿨다 — className은 그대로다.
로딩·실패 분기에도 같은 방식으로 넣어 어느 상태에서도 랜드마크가 있다.

실측(픽셀 무변경 확인): 상세 grid `622px 622px` / 컨테이너 1320px / 가로 오버플로 0,
로그인 flex·`min-height: 911px` 그대로.

### 가드도 고쳤다

파일 단위 검사만으로는 **분기 하나가 랜드마크를 잃는 것**을 못 잡는다(변이로 확인했다 —
상세의 본문 `main` 하나를 `div`로 되돌려도 파일 단위 검사는 통과했다).
그래서 "화면 루트(`min-h-screen`) 개수만큼 `main`이 있어야 한다"를 함께 건다.
**맹점**: 화면 루트를 `min-h-screen`이 아닌 방식으로 쓰면 이 비교는 무력해진다 —
지금 저장소의 6개 화면은 전부 그 규칙을 따른다.

## 6. 성능 — 검색 API의 SQL 횟수를 처음으로 **쟀다** (BACKLOG 8)

"배치 조회를 쓴다"는 코드를 읽어 아는 사실이고, 몇 번 나가는지는 재야 아는 사실이다.
Sprint 145가 썸네일 배치 조회를 넣은 뒤로 실제 횟수를 잰 적은 없었다.

`sqlite3.Connection.set_trace_callback`으로 실측:

```
size=1  -> items 1 / thumbnails 1 / SQL 3
size=3  -> items 3 / thumbnails 3 / SQL 3
size=9  -> items 9 / thumbnails 9 / SQL 3

3회 = COUNT(*) + 페이지 행 + auction_image 배치(MIN(seq) GROUP BY)
상세 1건 = 7회 (전부 단건 조회, 개수에 비례하지 않는다)
```

**결과가 늘어도 SQL이 늘지 않는다 = N+1이 아니다.** 이제 회귀로 잠갔다 —
썸네일 조회를 물건마다 한 번씩 도는 코드로 바꾸는 변이를 넣으면 즉시 걸린다.

## 12. 남긴 사실 하나 — 회귀 1건이 빨간불이다 (코드 결함 아님)

`test_schema_hygiene.py`의 P0-B 가드가 이렇게 말한다.

```
[FAIL] 추적 파일이 미추적 파일을 import하지 않는다:
       src/app/properties/[id]/page.tsx:15 -> src/lib/useFocusTrap.ts
```

**가드가 옳다.** 새로 만든 `src/lib/useFocusTrap.ts`가 아직 git에 추적되지 않는데
추적 중인 화면이 그것을 import한다. 이 상태로 `git commit -a`를 하면 커밋된 트리에서는
그 모듈이 없어 화면이 깨진다 — 그것이 이 가드가 존재하는 이유다(BUGS #105).

해소는 `git add`뿐이고 **그것은 승인 영역이라 하지 않았다.**
커밋 시 `git add -A`(또는 `git add src/lib/useFocusTrap.ts`)를 함께 하면 그 즉시 초록으로 돌아온다.
