## 1. 대괄호 앞/뒤가 무엇인지 — 데이터로 확인

`^(.*?)\[(.*)\]\s*$` 로 1,876행 전부를 분해했다.

```
'앞[안]' 형태로 분해되지 않는 행     0
**앞**에 면적(㎡)이 섞인 행          0    <- '앞 = 주소' 가 성립한다
**안**에 시도명이 섞인 행            2    <- 아래에서 하나는 오탐, 하나는 진짜 결함
```

즉 **앞 = 주소, 안 = 물건 표시**가 전수로 성립한다.

### 대괄호 개수 — 지난 Sprint 서술을 정정한다

```
'[' , ']' 문자 개수      (1,1) 1,872행 / (2,2) 4행
정규식 \[([^\]]*)\] 로   전부 1쌍
```

지난 Sprint 에 "정확히 1쌍씩"이라고 적었는데 그건 **정규식 기준**이었다.
문자 기준으로는 **중첩 대괄호 4행**이 있다(정규식이 중첩을 못 본다). 같은 데이터를
어떻게 세느냐에 따라 답이 갈리므로, 이번에는 두 방법을 나란히 적는다.

### 분류 (대괄호 첫 토큰 = 실제 값 기준)

```
집합건물  1,100 (58.64%)   토지  713 (38.01%)   건물  49 (2.61%)
기타/예외    14 (0.75%)    카니발3 쏘나타2 BMW2 선박2 기타1 짚1 건설기계,중기1 스포티지1 트랙스1
```

★ 제품 `parseArea` 는 `inside.startsWith('토지')` 로만 갈라 **토지 / 건물 2분류**다.
집합건물·건물은 전부 '건물' 이 되고, 차량·선박은 면적이 없어 `null` 이 된다.
12종을 그대로 노출하지는 않는다 — 그것은 표시 정책이라 건드리지 않았다.

### 목표가 지목한 예외 유형 — 전수

```
빈 문자열 0 / 앞 공백 0 / 뒤 공백 0 / 대괄호 없음 0 / 대괄호 짝 불일치 0
```

## 3. ★ 중복 1건의 정체 — **법원의 사건 병합**이 원인이다

목표가 지목한 duplicate pair 를 끝까지 추적했다.

```
주소  경기도 안성시 삼죽면 진촌리 107-5 [토지 전 2139㎡]
id=442    case_no '2023타경4767'                      물건1  평택지원  수집일 2026-07-11
id=1421   case_no '2023타경4767 / 2026타경51196'       물건1  평택지원  수집일 2026-07-13
```

전 컬럼을 대조하니 **다른 것은 id / case_id / case_no / crawl_date / created_at 뿐**이고
주소·감정가·최저가·기일·상태·유찰횟수·검증상태가 전부 같다.

### 원인

법원이 2026-07-12 에 `2026타경51196` 을 기존 사건에 **병합**하면서 공고상 사건번호가
`2023타경4767 / 2026타경51196` 으로 바뀌었다. 이 저장소의 식별키는
`auction_case(case_no, court_code)` + `auction_item(case_id, item_no)` 이므로
**문자열이 바뀌면 새 사건·새 물건 행이 생긴다.** 옛 행은 남고, 법원이 더는 그 번호로
공고하지 않으므로 **영원히 갱신되지 않는다.**

레거시 `auction` 에도 둘 다 있고(442 / 711), `auction_case` 에도 둘 다 있다(237 / 238).

### 영향 (실측)

```
검색      안성시 검색 total=10 에 **두 행 모두** 포함   <- 같은 물건이 두 번 보인다
내보내기   CSV/TSV 에도 두 줄로 나간다 (제품 export 함수로 실제 생성해 확인)
문서수집   document_queue 에 같은 물건이 두 벌 = 6행 (3 done + 2 done/1 pending)
```

### 범위 — "조각이 겹친다"만으로 세면 **11건을 오탐한다**

```
case_no 에 ' / ' 가 있는 행                     425
그 조각이 단독 행으로도 존재하는 (사건,물건) 쌍     12
  그중 **주소까지 같은** 진짜 중복                 1   <- 위 쌍
  주소가 다른 것                                11   <- 정상
```

11건은 **병합 시 물건번호가 재부여되기 때문**이다. 병합 사건의 "물건 1"과 구성 사건의
"물건 1"은 서로 다른 물건이다(예: 상주 낙동면 공장용지 vs 공주 계룡면 답). 물건번호만
보고 중복이라 하면 안 된다.

### 남긴 것 — 탐지기(읽기 전용)

`detect_merged_case_duplicates_dryrun.py` 신설. 저장소 관례대로 `--apply` 가 없다.
**(주소, 법원, 물건번호)가 같은데 사건번호만 다른** 묶음만 세고, 기일·최저가까지 같은지를
덧붙여 판단 근거를 남긴다. 다른 cwd 에서도 동작하고 찌꺼기를 남기지 않는 것을 확인했다.

어느 행을 남길지는 제품 판단이다(옛 행에 사용자의 관심물건/최근본이 걸려 있을 수 있다).
**운영 DB 는 건드리지 않았다.**

이번 세션에 문제가 있었거나 경계에 있는 물건만 골라, **DB 원문 / 검색 API / 상세 API**

`property_type`)를 대조했다.

```
대상: 6442(대지권) 258·1610(중첩) 442·1421(중복쌍) 541(차량) 185(평) 505(평범)
결과: 8개 물건 전부 검색 결과에 포함 / **불일치 0건**
```

값이 변형되거나 누락되는 단계는 없다.

### 화면별로 실제 무엇이 그려지는가

| 화면 | 주소 | 사건번호·물건번호 | 면적 |
|---|---|---|---|
| 검색 목록 | O | `사건번호 (물건번호)` **항상** | **O** `건물 84.50㎡ (25.56평)` |
| 상세 | O (원문 그대로, h2) | `사건번호` + 물건번호는 **'1'이면 생략** | X |
| 관심물건 | O | `사건번호 (물건번호)` 항상 | X |
| 최근 본 물건 | O | `사건번호 (물건번호)` 항상 | X |
| CSV/클립보드 | O (소재지 열) | 법원·사건번호·물건번호 **별도 열** | X |

CSV 는 제품의 실제 `buildCsv`/`buildTsv`/`buildDelimitedText` 를 **실제 API 응답으로**
돌려 확인했다(mock 아님). 열 10개, `연립주택,다세대,빌라` 처럼 쉼표가 든 값은 CSV 에서
따옴표로 감싸고 TSV 에서는 그대로 — 형식대로다.

### 사건번호 혼선 — 없다 (API 실호출)

`case_no LIKE '%값%'` 이라 **병합 사건번호의 어느 조각으로 찾아도 걸린다.**

```
'2023타경4767 / 2026타경51196' -> 1건    '2026타경51196'(뒤 조각) -> 1건
'2023타경4767'(앞 조각)        -> 2건    <- 병합행 + 중복행. 검색 결함이 아니라 §3 중복 때문
'2025타경1990'(다른 병합의 조각) -> 4건
```

### 물건번호 표시 불일치 — 세어 보니 결함이 아니었다

상세만 `item_no !== '1'` 일 때 물건번호를 숨긴다(목록 3화면은 항상 표시). 처음엔
"다물건 사건의 1번을 구분할 수 없다"고 의심했다. **세어 보니 아니었다:**

```
item_no='1'                      1,247행 (66.47%)
물건이 2개 이상인 사건              192건
  그중 item_no='1' 이 있는 사건     154건
  형제 물건의 주소가 **모두 같은** 사건   0건   <- 192/192 전부 주소가 다르다
```

상세 화면은 주소를 h2 로 크게 보여 주므로 **주소만으로 항상 구분된다.**
화면 간 표기가 다른 것은 사실이나 사용자가 혼동할 근거는 실측에서 나오지 않았다.
표기 통일은 표시 정책이라 건드리지 않았다.
