### 무엇이 문제였나 — `29 → 31` 은 증상이지 원인이 아니었다

`docs/CLAUDE.md` 가 마이그레이션 끝 번호를 `029` 로 적고 있을 때 저장소에는 이미 `030`/`031` 이
있었다. 그 한 줄을 고치는 것으로 끝내면 다음 032 에서 같은 일이 다시 생긴다. 실제 질문은
따로 있었다 — **누가 마이그레이션의 정본인가.**

전수 검색 결과, 번호를 적어 둔 곳은 많았지만 그중 **강제되는 계약은 하나뿐**이었다
(`test_bootstrap` 의 부트스트랩 범위). 나머지는 전부 날짜 붙은 서술이거나
변수로 세는 코드였다. 그래서 **새 framework 를 만들지 않고**, 문서 한 줄과
검사 한 개를 정리한 뒤 마이그레이션 **사슬을 실제로 돌려 보는** 회귀를 하나 추가했다.

### 고친 것

| 분류 | 내용 |
|---|---|
| **TEST DEFECT** | `test_bootstrap` 의 범위 검사가 `docs/CLAUDE.md` 안의 **모든** `NNN~NNN` 을 잡아 시작=001 / 끝=최신을 요구했다. “011~013 처럼 테이블을 재작성하는” 같은 **정확한 역사 서술**을 결함으로 만들어, 가드가 사람에게 증거를 지우라고 압박했다(실증: 한 줄 추가 → 즐시 2건 오판). 부트스트랩을 안내하는 줄 하나로 좁히고, **그 줄이 정확히 하나 존재할 것** + **마지막 마이그레이션을 이름으로 언급할 것**을 추가로 요구해 약해지지 않게 했다 |

### 새 회귀 — `test_migration_chain.py`

기존 검사 셋은 “빈 DB 에서 부트스트랩이 되는가”(`test_bootstrap`), “.sql 이 깔끔히 쪼지는가”
(`test_migration_atomicity`), “디스크와 기록이 맞는가”(`test_schema_hygiene`)를 본다. 빠진 질문은
이것이었다 — **아직 안 돌린 마이그레이션을 지금 운영 스키마에 돌리면 실제로 되는가.**
적용이 승인 영역이라 저장소와 운영은 항상 벌어져 있고, 그 간격은 승인이 떨어진 날
처음 확인된다 — 가장 나쁜 시점이다.

```
(A) 빈 DB      -> init_db -> migrate_v4_1 -> 전체      31/31 적용
(B) 운영 사본  -> 남은 마이그레이션 11건            31/31 적용
integrity ok · FK 위반 0 · 중복 적용 0 · 번호 구멍 0
데이터 보존  auction_item 1,876 / recent_items 37 / document_queue 3,498  (전후 동일)
031 은 기존 행을 메우지 않는다 — first_viewed_at NULL 37행 유지(거짓 T2D 방지)
제품 질의 10개(기존 API · FIELD · T2D) 양쪽 경로에서 전부 실행
★ 두 경로의 표/컴럼/인덱스/적용이력 드리프트 **0**
```

기대값을 손으로 적지 않는다 — 전부 디스크의 `.sql` 목록과 그 DDL 본문에서
유도한다. **032 가 들어오면 사람이 이 파일을 고치지 않아도 그것까지 검증된다.**

### 이번 순회의 결론 둘

**(1) 일곱 중 다섯(#222·#223·#224·#225·#226)이 "가드 자신"의 결함이다.**

> ## ★ [2026-08-25] 사용자가 `.env` 에 두 키를 넣었다 — 아래 이력 전체가 이 시점에서 종결된다

> 전수         admin 라우트 16개 중 키 없이 500 인 것 **0개**
> ```
>
