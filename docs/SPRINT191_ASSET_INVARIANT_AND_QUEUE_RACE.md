## 2. BUGS #127 — 사진이 줄어도 파일은 안 줄었다

`save_auction_images()`는 DB 행만 지운다. **파일은 아무도 안 지웠다.**

### 재현 (2026-08-18, 스크래치 문서 루트)

```
1) 최초 5장 수집        디스크: 01..05.jpg
2) 법원이 3장으로 줄임   디스크: 01..05.jpg   <- 기대 3개
3) 다음 주기 previous_hash = 2c9401e6...
   방금 수집한 new_hash  = 502a9087...
   두 공식 일치?          False
```

### 영향

```
고아 파일   auction_image 가 가리키지 않는 파일이 계속 쌓인다
거짓 개정   _existing_set_hash() 는 **파일시스템**을 근거로 삼으므로 옛 파일까지 세고,
            수집 쪽 공식(이번에 받은 것만)과 갈라진다 -> 이후 매 수집이 "변경됨"
```

두 번째가 `#120`과 **완전히 같은 실패 방식**이다.

### 고친 것

- `crawler/image_crawler.py:_remove_files_not_in()` 신설 — 완전 수집이면 이번에 확보한
  순번에 **없는** 파일을 지운다. **부분 수집이면 절대 지우지 않는다**(DB 쪽 `complete`
  가드와 같은 규칙 — "판단할 수 없을 때는 남기는 쪽").
- `save_auction_images()`의 행 삭제를 `seq > max_seq` -> **집합 차집합**으로 바꿨다.
  법원이 **가운데 순번을 빼는 경우**(1,2,4만 제공)를 `>` 비교는 못 잡아 3번 행이
  살아남고, 그 행이 가리키는 파일은 이미 없다(= 화면은 있다는데 열면 404).
  파일 쪽도 같은 기준이라 두 근거가 갈라지지 않는다.

### 검사가 옛 semantics 를 굳히고 있었다

`test_asset_pipeline.py` §11 이 `save_auction_images()`를 **누적 빌더처럼** 쓰고 있었다
({1,2} 저장 -> {1,3} 저장 -> 행이 1,2,3 이 되기를 기대). 그게 통과하려면
"이번에 안 준 순번(2)의 행을 남긴다"가 참이어야 하는데 그건 이 함수가 막으려는 상태다.
옛 구현이 `seq > max_seq` 로만 지웠기 때문에 **우연히** 통과하고 있었다.
검사를 새 semantics 로 고치고 가운데-순번 케이스를 명시적으로 추가했다.

## 3. BUGS #128 — 법원이 사진을 전부 내려도 옛 사진이 영원히 남았다

사진 감소는 `save_auction_images()`가 처리하는데, `doc_worker` 는
`if result.get("images")` 로 가드하므로 **0장으로 줄어드는 경우만 그 함수에 도달하지
않는다**(빈 목록은 전체 실패와 구별되지 않으니 그 가드 자체는 옳다).

```
법원이 전부 내림 -> collect_images: no_asset=True, images=[]
                 -> document_status = NO_IMAGE   (상태만 바뀐다)
                 -> auction_image 행/파일은 그대로
                 -> _images_status() 는 "행이 있으면 무조건 READY"
                 -> **사용자는 법원이 내린 사진을 영원히 본다**
```

### 한 번 못 봤다고 지우지 않는다

"법원이 내렸다"와 "이번 관측이 실패했다"는 한 번의 관측으로 구별할 수 없다. 그리고
사진을 전부 지우는 것은 이 파이프라인에서 **가장 파괴적인 동작**이다. 그래서
**두 번 연속 확인**을 요구한다.

```
1회차: document_status 가 READY -> NO_IMAGE 로 바뀐다. 사진은 남긴다.
2회차: 이미 NO_IMAGE 인데 또 no_asset 이다 -> 그때 정리한다.
```

**새 컬럼이 필요 없다** — `document_status` 자체가 1회차를 기억한다.
`clear_images_if_absence_confirmed()`는 `mark_queue_done()` **보다 먼저** 불러야 한다
(그 함수가 상태를 덮고 나면 1회차인지 알 수 없다). 순서는 DB 행 삭제 -> 파일 삭제다 —
반대로 하면 "DB 는 있다는데 파일이 없다"가 된다.

## 4. BUGS #129 — 완료 기준과 서빙 대상이 서로 다른 파일이었다

```
doc_exists(status)              -> status.json 만 본다
api/v1/documents.py 가 서빙     -> status.html
```

```
status.json 만 남은 상태 -> doc_exists()=True  (영원히 재수집 대상에서 제외)
                         -> 뷰어는 404
                         = "화면은 READY 인데 열면 없다"
```

실측(2026-08-18): 실데이터에 json-only **0건**, html+json 163건 — 지금 터지는 버그는
아니었다. 그러나 **정의가 두 벌인 상태 자체**가 결함이고, `image_exists()`가 자기
docstring 에 적어 둔 원칙("쓰는 쪽과 읽는 쪽의 '있다' 정의가 갈라지면 화면은 READY 인데
뷰어는 404")을 문서 쪽만 안 지키고 있었다.

`DOC_REQUIRED_FILES` 를 신설해 완료 판정이 **필요한 파일 전부**를 보게 했고,
서빙 표(`DOC_TYPE_FILES`)의 파일명이 그 안에 있는지 **구조적으로** 검사한다
(목록을 손으로 맞추지 않는다 — 서빙 표에서 읽어 대조한다).

## 5. ★ 구조적 가드 — 인스턴스 대신 불변식을 건다

`test_asset_pipeline.py` 5-I. 시나리오 **표**를 돌리며 매 단계 불변식을 건다.

```
완전 수집이면:  set(디스크 순번) == set(수집 결과 순번) == set(DB 순번)
부분 수집이면:  디스크/DB 는 줄어들지 않는다
언제나:        DB 가 가리키는 파일은 실제로 존재한다
```

| 시나리오 | 결과 |
|---|---|
| 신규 3장 / 동일 재수집 / 2번만 형식 변경 / 1장 추가 | 세 근거 일치 |
| 가운데 1장 삭제 / 뒤 2장 삭제 | 세 근거 일치 |
| 부분 수집(4중 2 실패) | 디스크·DB 무손실 |
| 다시 완전 수집 4장 | 세 근거 일치 |

새 시나리오는 **표에 한 줄**만 추가하면 된다. `#120`을 고칠 때 `#127`을 놓친 이유가
"개별 검사를 하나씩 늘렸기 때문"이라, 여기서 방식을 바꿨다.

**변이 확인**: `_remove_files_not_in()` 호출을 무력화하니 즉시 4건 FAIL(그중
`[가운데 1장 삭제] 수집결과 == 디스크` 는 이 가드가 새로 잡은 것). 복원 후 전부 PASS.

## 6. BUGS #130 — 큐 경쟁에서 진 것을 "큐 비었음"으로 오해했다

`claim_next_queue_item()`은 두 가지 완전히 다른 사건에 **똑같이 `None`** 을 돌려줬다.

```
(a) 진짜로 가져갈 것이 없다
(b) 조회는 됐는데 UPDATE 에서 다른 실행에 밀렸다
```

`doc_worker.main()`은 `None` 을 (a)로 읽고 **그 실행 전체를 끝낸다.**
즉 claim 충돌 한 번이 그날 남은 큐를 통째로 다음 날로 미루고, 로그에는
`대기열 비어있음` 이라는 **사실이 아닌 문장**이 남는다(BUGS #47 계열).

### 실측 (스레드 12 / 대기 행 4)

```
수정 전   claim 성공 3건, 중복 0건, None 9건   <- 행이 남았는데 None 을 받은 스레드가 있다
          큐 분포 in_progress 3 / pending 1
수정 후   claim 성공 4건, 중복 0건, None 8건   <- None 8건은 전부 정직하다(행이 없다)
          큐 분포 in_progress 4
```

**중복 claim 은 원래 0건이었다** — 원자적 클레임은 정상 동작하고 있었다.
문제는 진 쪽의 처리였다.

### 고친 것

`CLAIM_RACE_MAX_ATTEMPTS = 5`. 경쟁에서 지면 **다른 행으로 다시 시도**한다.
`None` 은 SELECT 가 아무것도 못 찾았을 때만 돌려준다. 상한에 걸리면 `None` 을 주되
**왜인지 경고를 남긴다** — "비었다"와 구별되게.

`doc_worker` 는 락 파일로 동시 실행을 막지만, 5시간 stale 락 회수 경로와 운영자의
수동 실행이 겹치는 창이 있다.

**변이 확인**: `CLAIM_RACE_MAX_ATTEMPTS = 1` 로 되돌리니 즉시 3건 FAIL.
