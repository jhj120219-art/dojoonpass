## 1. 어떻게 찾았나

BUG #143 후속으로 여섯 시나리오를 다시 흘려보냈다. 그중 아직 검사한 적 없는 칸이
하나 있었다 — **실체는 저장됐는데 큐 성공기록이 실패하고, 그 뒤 재시도하는 경우.**

```
1회차  spec.pdf 저장 성공 -> mark_queue_done() 실패 -> 전부 롤백, 큐 pending   (설계대로)
2회차  파일이 이미 있다 -> "이미 존재. 스킵" -> files_saved=[]
       -> mark_queue_done -> _record_doc_raw() 가 `if not files_saved: return`
       -> 큐 done / 화면 READY / doc_raw 0행
```

실제 `collect_spec()`으로 재현했다(가짜 수집기가 아니다 — 스킵 분기는 driver를 건드리기
전에 return하므로 브라우저 없이 진짜 코드가 돈다).

**영구인 것이 핵심이다.** 다음 수집도 파일이 있으니 같은 분기를 탄다.
`overwrite=True`(재수집)만이 벗어나는 길인데 그 트리거는 별개 조건이다.

사용자에게는 `available=true` + `viewer_url`인데 `page_count`/`file_size`/`doc_version`
만 **영원히 null**로 보인다. 프런트는 쪽수가 null이면 페이지 이동 UI를 그리지 않는다 —
`mark_queue_done()`이 "뷰어 페이지 이동이 불가능했던 근본 원인"으로 적어 둔 그 상태다.

### 사진 쪽은 같은 자리를 처음부터 복구하고 있었다

`crawler/image_crawler.py:_describe_existing()`의 주석이 그대로 적고 있다 —
*"이미 받아 둔 사진은 다시 쓰지 않는다. 그래도 DB에는 실체를 다시 알려 줘야 한다 —
파일은 있는데 `auction_image` 행만 없는 상태(이 저장소의 단골 결함)를 여기서 스스로
복구한다."* **문서만 그 복구가 없었다.**

## 4-b. 두 번째 결함 — 잠금이 잠그지 않고 있었다 (BUGS #145)

같은 스프린트에서 `storage/checkpoint.py:RunLock` 을 읽다가 나왔다. 기존 회귀(§9)가
이 락의 계약을 **전부 순서대로** 검사하고 있었다 — 잡고, 또 잡아 보고, 놓고, 회수한다.
그런데 이 락이 막으려는 상황은 순서가 아니라 **같은 순간**이다
(모듈 주석: *"운영자가 수동으로 실행하는 동안 예약 실행이 겹치는 경우"*).

```
수정 전   스레드 8 x 200라운드   ->   200라운드 전부에서 8개가 동시에 성공
```

`os.path.exists()` 로 **보고 나서** `open(..., "w")` 로 **썼다.** 그 사이가 열려 있었다.
`O_CREAT|O_EXCL` 은 그 판정을 커널에 맡긴다 — 창 자체가 없다.

### ★ 회수 경로는 세 번 틀렸고, 세 번 다 측정이 잡았다

```
os.remove 로 회수                 4/1,000 라운드에서 둘이 성공
지우기 직전 mtime 재확인 추가      그대로 4/1,000
os.rename 로 회수 권한 중재        8스레드에서 2/40
회수 구역을 배타 토큰으로 감쌈      1,000라운드 전부 정확히 하나 (로깅을 끈 최악 조건)
```

**두 번째 줄을 기록으로 남긴다.** "재확인을 넣었으니 창이 좁아졌겠지"가 측정에서
그대로 틀렸다 — 좁아진 것이 아니라 **창의 종류가 같았다.** 재지 않았으면 개선했다고
적었을 것이고, 그 문장은 다음 사람을 잘못 안심시켰을 것이다.

회귀(§11)는 두 경우를 따로 보고 성공 수가 **정확히 1** 인지 본다 —
"둘 다 실패"도 결함으로 센다(겉보기엔 안전하지만 그날 배치가 통째로 안 도는 것이다).
토큰 잔재 0건도 함께 고정한다.

### 같은 계열 전수 검색

"존재를 확인하고 파일을 건드리는" 함수를 파이프라인 54개 파일에서 훑었다 — 8곳.
그중 락만 배타 생성이 필요했고, 나머지 7곳(`move_into_place`, 수집기 스킵 분기,
`_remove_other_ext_for_seq` 등)은 **큐 claim(원자적 UPDATE) + 이 락**이 위에서
단일 기록자를 보장한다. 즉 이 락이 그 보장의 뿌리였고, 그것이 깨져 있었다.

**★ 첫 번째 탐지 도구는 틀렸다.** 처음 만든 스윕은 "`if exists:` 블록 **안에서** 파일을
건드리는가"를 봤고 **0곳**을 보고했다. 그런데 `RunLock` 의 쓰기는 `if` 블록 **밖**에
있었다 — 즉 그 도구는 방금 찾은 결함조차 못 잡는다. 범위를 "같은 함수 안"으로 넓혀
다시 쟀다. **0건은 "없다"가 아니라 "이 도구로는 못 봤다"였다.**

## 5. 알고 있으나 고치지 않은 것 (근거 포함)

**큐 성공기록이 실패한 뒤 재시도하면 `document_version_log` 한 행을 잃는다.** 실측:

```
정상(대조군)              queue=done  version_log 1행  doc_raw v1,v2
큐 기록 실패 후 재시도     queue=done  version_log 0행  doc_raw v1,v2
```

이유는 구조적이다 — 재시도 시점에는 디스크가 이미 새 바이트라 수집기가 재는
`previous_hash`가 `new_hash`와 같아진다. 되살리려면 **수집 전에** 지문을 큐에 적어야 한다.

**하지 않는다.** `document_version_log`는 이 저장소에 **제품 독자가 없고**(쓰는 곳은
`mark_queue_done()` 하나, 읽는 곳은 일회성 리포트 스크립트뿐), **바뀌었다는 사실 자체는
`doc_raw`가 v1->v2로 지킨다.** 사용자 영향 0인 이력 한 행을 위해 큐 구조를 바꾸지 않는다.
대신 12-K가 이 상태를 **명시적으로 고정**한다 — 그 테이블에 독자가 생기는 날,
이 단언이 그때 다시 결정하도록 강제한다.

"정확히 하나"(1,000/1,000)가 된 것이다.

## 7-c. 실브라우저 — 검색 화면까지 실제로 그려지는가

`/search` 를 실제 Chrome 으로 열고 **픽셀이 실제로 생겼는지** 확인했다.
(HTTP 200 은 이미 [9] 가 전수로 봤다. 그것과 "사용자 화면에 보인다"는 다르다.)

```
총 9건 표기          "총 9건"        DB 의 미래 기일 물건 수와 일치
대표 이미지 <img>     9개            검색 결과 카드마다 하나
실제로 그려진 것      9개 / 깨짐 0
순번                 전부 seq=1     대표 이미지 규칙(캐러셀 첫 장)과 일치
자연 크기            522x700 / 700x393 / 700x525   (원본 비율 그대로)
콘솔 오류            없음
```

**★ 첫 측정은 "9개 전부 깨짐"이었다 — 그리고 그것은 틀렸다.**
페이지 로드 직후에 쟀는데 이 썸네일들은 `loading="lazy"` 다. 아직 로드가 시작되지도
않은 상태를 `complete=false, naturalWidth=0` 으로 읽고 **결함으로 보고할 뻔했다.**
스크린샷에는 사진이 멀쩡히 찍혀 있었고, `onload` 를 기다려 다시 재니 9/9 였다.

이번 세션에서 **측정 도구가 틀린 세 번째** 사례다(앞의 둘: 검색 대조 쿼리의 정규화 누락,
`if exists:` 블록만 보던 check-then-act 스윕). 규칙은 같다 —
**결함처럼 보이면 도구를 먼저 의심한다.**

경계도 분명히 적는다: **상세페이지(`/properties/[id]`)는 열지 않았다.**
로그인 게이트 뒤에 있고, 로그인 상태로 열면 `record_view()` 가 `recent_items` 에
**운영 데이터를 쓴다.** 읽기만 하기로 한 이번 작업의 범위를 벗어난다.
브라우저를 닫은 뒤 `recent_items` 가 35행 그대로임을 확인했다(세션 시작과 동일).

## 8-b. 운영 DB 에 대해 정확히 무엇을 했는가

**데이터는 바꾸지 않았다.** 다만 `auction.db` 의 **mtime 은 바뀌었다** — 프런트 계약
테스트를 제대로 돌리려고 `uvicorn` 을 띄웠고, `get_connection()` 은 읽기 전용이 아니라
일반 커넥션이라 SQLite 가 파일을 건드린다(내용 변경 없이도 mtime 이 움직인다).

그래서 **세션 시작 시점의 측정과 끝 시점의 측정을 나란히** 놓는다.

```
                       시작        끝
doc_raw                556         556
auction_image          45          45
document_version_log   0           0
auction_item           1,876       1,876
document_queue         186/559/2753  186/559/2753   (SKIPPED_EXPIRED/done/pending)
document_status        9종 전부 동일 (SPEC 197 READY 등)
```

바이트 단위 동일성까지 주장하지는 않는다(세션 시작 시점의 해시를 남겨 두지 않았다).
**행 수준에서 전 항목이 같다**는 것까지가 이 측정이 말할 수 있는 전부다.

성능 측정은 전부 **사본**에서 했고, 사본 측정 직후 원본의 크기·mtime 무변경을
그 자리에서 확인했다(그때는 아직 서버를 띄우기 전이었다).
