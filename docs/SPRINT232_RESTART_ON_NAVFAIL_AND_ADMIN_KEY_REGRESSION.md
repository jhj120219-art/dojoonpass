## 1. ★ "사건을 못 찾았다"로 드라이버를 통째로 재시작하고 있었다 (수정)

### 발견 경로

`MAX_ITEMS = 10` 이 눈에 띄어 조사를 시작했다. 두 곳이 같은 상수를 쓴다.

```
crawler/court_crawler.py:115   일일 크롤 — 법원별 목록에서 앞 10건만 수집
crawler/base_crawler.py:311    go_to_case_detail — 목록 앞 10행에서만 사건을 찾는다
```

**가설**: 목록 11번째 이후 사건은 doc_worker 가 영원히 못 찾는다.

### ★ 가설은 틀렸다 — 재기 전에 단정하지 않았다

`logs/doc_run.log` 에 `"사건 매칭 실패"` 가 **255회** 있었다. 그 사건들을 DB 와 대조했다.

```
서로 다른 (법원, 사건) 조합            77개
그중 auction_item 에 있는 것            62개
  그 (법원, 기일) 조합이 10건 초과       2개    <- MAX_ITEMS 가설과 맞는 쪽
  10건 이하                             60개   <- **다른 원인**이다
```

**60 대 2.** MAX_ITEMS 는 이 실패의 주원인이 아니다. 대부분은 기일이 지나 목록에서
빠졌거나 취하된 사건이다. 가설을 버렸다.

(MAX_ITEMS=10 자체는 여전히 구조적 상한이다 — (법원,기일) 조합 316개 중 14개가 10건을
넘고, 앞 10건 밖에 있는 물건이 31건(1.7%)이다. 다만 이번 실패의 원인은 아니므로
**바꾸지 않았다.** 크롤 정책 변경은 실제 크롤 없이 검증할 수 없다.)

### 그런데 그 과정에서 **진짜 결함**이 보였다

로그에서 매칭 실패 뒤에 언제나 이것이 따라붙었다.

```
[서울중앙지방법원] 사건 매칭 실패: 2023타경118942
[2023타경118942] spec 처리 중 오류: 사건 상세 진입 실패
드라이버 재시작 중...
====== WebDriver manager ======
```

코드가 그렇게 되어 있었다.

```python
ok = go_to_case_detail(...)
if not ok:
    raise Exception("사건 상세 진입 실패")     # 일반 예외로 올린다
...
except Exception as e:
    mark_queue_failed(...)
    driver = restart_download_driver(driver)   # -> 무조건 재시작
```

**`go_to_case_detail()` 이 False 를 돌려주는 것은 브라우저 고장이 아니다.**

```
1. 그 사건이 법원 목록에 없다 (기일 경과 / 취하 / 변경)
2. 물건번호가 모호해 **일부러 진입하지 않았다**  <- Sprint 230 이 넣은 사진 오염 방어
```

둘 다 브라우저는 멀쩡하다. 2번은 특히 나쁘다 — **옳은 판단이 드라이버 재시작을 부른다.**

### 비용은 추정하지 않고 로그에서 쟀다

```
매칭 실패 255회 / 전부 재시작이 뒤따랐고 시간을 잴 수 있었다
재시작 -> 재개까지   평균 5.9초 (중앙값 5.9 / 최소 5.6 / 최대 11.4)
합계 1,506초 = 25.1분
로그가 덮는 기간 11일  ->  하루 평균 2.3분 (실행 창 120분의 약 2%)
```

**시간 자체는 크지 않다.** 과장하지 않는다.

### 진짜 문제는 시간이 아니라 **연쇄**다

`restart_download_driver()` 가 실패하면 Sprint 137 의 방어가 발동해
**그 날 실행 전체를 중단**한다(남은 큐의 재시도 예산을 지키기 위한 올바른 설계다).

즉 **"사건 하나를 못 찾았다"는 무해한 사실이 운 나쁘면 하루치 수집을 통째로 죽인다.**
그럴 이유가 없다.

### 해결

전용 예외 `CaseNotReachable` 을 만들어 그 경우만 따로 잡는다.
재시작 없이 그 항목만 실패 처리하고 다음으로 넘어간다.
**재시도 예산은 종전대로 소모한다** — 큐 의미론은 바꾸지 않았다.

```python
except CaseNotReachable as e:
    logger.warning("... (브라우저 정상 - 재시작 없이 다음 항목으로)")
    mark_queue_failed(item["id"], item["retry_count"])
    continue

except Exception as e:          # 진짜 예외는 종전대로 재시작
    ...
```

### 회귀 2종 신설 + 변이 3/3

```
8. 사건 미발견은 재시작하지 않는다   재시작 0회 / 다음 항목은 그대로 성공 / 종료코드 0
9. **대조군** 진짜 예외는 여전히 재시작한다   (과잉 수정 방지)

변이  수정 전으로 되돌리기(일반 예외)     -> FAIL
      전용 except 무력화                  -> FAIL
      실패 기록 누락(예산 안 깎임)         -> FAIL
```

9번 대조군이 없으면 "이제 아무것도 재시작하지 않는다"로 망가져도 통과한다.

## 2. ★ Admin API 키가 다시 사라졌다 — P1 이 아니라 P0 다 (문서 정정)

`docs/BETA_RELEASE_CHECKLIST.md` 는 이렇게 적고 있었다.

> **2026-08-16 재실측(Sprint 134): 두 키 모두 설정 확인, 이제 정상 403/200 응답**
> — UI 없음만 남음 (P1)

**오늘 재니 사실이 아니다.** 비밀값은 열람하지 않고 두 가지 독립된 방법으로 확인했다.

```
(1) .env 의 변수명 존재 여부
      ADMIN_API_KEY           이름 **없음**
      SUPER_ADMIN_API_KEY     이름 **없음**
      PAYMENT_WEBHOOK_SECRET  이름 **없음**
      SUPABASE_JWT_SECRET     이름 있음 / 값 채워짐(88자)   <- 이것만 살아 있다

(2) OpenAPI 스키마에서 뽑은 **전 라우트 38개**를 토큰 없이 호출
      /api/v1/admin/* 13개 전부  ->  500 "관리자 키 미설정"
```

두 방법이 일치하므로 측정 오류가 아니다. `.env` 변동은 이번이 **세 번째**다
(08-08 있음 -> 08-13 없음 -> 08-16 있음 -> **08-20 없음**).

### 영향

```
등기부 신청 상태 변경 / 결제 환불 / 웹훅 재처리 / 구독·사용자·감사 로그 조회
-> 운영자가 할 수 있는 일이 하나도 없다
```

준비도 표를 `⚠️ P1` -> `❌ P0` 로 되돌리고, 근거를 함께 남겼다.
**`.env` 수정은 승인 영역이라 하지 않았다.**

### 곁다리 — 인증 없이 500 을 만들 수 있다(이번엔 고치지 않았다)

토큰 없는 요청이 13개 라우트에서 500 을 만든다. 이 저장소는 Sprint 146 에서
*"인증 없이 500"* 을 결함으로 보고 고친 전례가 있다. 다만 여기는 코드에 의도가
명시돼 있고(*"두 키 모두 없으면 Admin API 자체를 쓸 수 없다(기존 동작 유지: 500)"*),
**키가 채워지면 자연히 403 이 된다.** 근본 원인은 코드가 아니라 `.env` 라서
이번에는 코드를 바꾸지 않았다.

## 4. Cache — ★ 여기서 도구가 또 거짓말했다

첫 측정이 *"사진·문서에 ETag 도 Cache-Control 도 없다"* 고 했다. 대형 결함으로 보였다.
**curl 로 대조하니 있었다.**

```
etag: "314ab4f55110344dfee2fd2277286888"
last-modified: Mon, 17 Aug 2026 00:07:25 GMT
```

원인은 내 코드였다 — `dict(r.headers)` 로 굳혀 놓고 `h.get('ETag')` 로 찾았다.
와이어의 키는 **소문자**(`etag`)라 언제나 `None` 이었다.
HTTP 헤더는 대소문자를 가리지 않는다. 정규화해서 다시 쟀다.

```
/api/v1/item/505/images/1        235,194 B
    If-None-Match  -> 304 / 본문 0 B      ★ 절약된다
    틀린 ETag      -> 200 / 235,194 B     (검사가 공허하지 않다)
    If-Modified-Since -> 304 / 0 B
/api/v1/item/505/documents/SPEC  395,675 B   위와 동일하게 304

대조군 — JSON API 는 캐시 헤더 없음(항상 최신)
    /search · /item/505 · /stats   전부 etag/last-modified/cache-control 없음
```

### ★ focus-visible — 여기서도 도구를 두 번 고쳤다

```
1차: element.focus() 로 재기            -> 프로그램 포커스는 :focus-visible 을 켜지 않는다. 무효
2차: 진짜 Tab 키                        -> 이벤트 0개. 탭이 hidden 이라 focus 이벤트가 안 뜬다
3차: 스크린샷으로 렌더 강제 후 Tab       -> 30회 이동 관측
     그런데 focusin **핸들러 안에서** 스타일을 읽었더니 7개가 "표시 없음"으로 나왔다
4차: 포커스가 자리잡은 **뒤에** 읽기      -> 실제로는 링이 있었다
     boxShadow: ... lab(86.15 -4.04379 -21.0797) 0px 0px 0px 2px
     (focus:outline-none focus:ring-2 focus:ring-blue-200 이 정상 동작)
```

**결론: WCAG 2.4.7 위반 0건.** 3차에서 멈췄다면 없는 결함 7건을 보고했을 것이다.
