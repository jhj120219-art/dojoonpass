## 0. 무엇을 만들고, 무엇을 만들지 않았는가

Sprint 227 이 만든 **내보내기**의 짝인 **가져오기**다.

```
만든다        사용자가 다른 곳에서 관리하던 관심물건 목록을 **손으로 복사해**
              붙여넣으면 -> 파싱 -> 우리 물건과 매칭 -> 사용자 확인 -> 담기
만들지 않는다  외부 상용 서비스 로그인 / 자동 크롤링 / 스크래핑
              (`api/v1/favorite_import.py` 와 `normalizer/mylist_import.py` 에는
               HTTP 클라이언트가 한 줄도 없다. 입력은 붙여넣은 문자열뿐이다)
```

### 왜 이번에는 만들 수 있었나 — **방향이 반대이기 때문**

`docs/SPRINT219B_MYLIST_EXPORT_FEASIBILITY.md` 는 "상대 서비스의 입력 형식을
확인하지 못했으므로 전용 포맷을 만들지 않는다"로 끝났다. 그 제약은 **내보내기**의
것이다 — 우리가 상대의 형식을 맞춰야 하기 때문이다.

**가져오기는 우리가 형식을 정할 필요가 없다.** 사람이 이미 클립보드에 담아 온 것을
읽기만 하면 된다. 그래서 형식을 가정하지 않고 세 갈래를 전부 받는다.

```
(1) 우리 CSV/TSV 내보내기를 되붙임   헤더를 읽어 열로 매핑 (정확)
(2) 스프레드시트/웹 표에서 복사      헤더가 있으면 (1), 없으면 (3)
(3) 아무 형태의 자유 텍스트          정규식으로 식별자만 추출
```

**(1) 은 우리가 형식을 아는 유일한 경로**라 계약으로 고정했다 —
`src/lib/exportList.ts:COLUMNS` 의 헤더와 `HEADER_ALIASES` 가 갈리면 되붙이기가
조용히 자유형으로 떨어진다. `test_favorite_import.py` 13번이 문자열 비교가 아니라
**실제로 되붙여** 확인한다.

## 1. 값을 지어내지 않는다 (Sprint 219B 의 실측을 그대로 지켰다)

### 병합 사건을 쪼개 대표를 고르지 않는다

`auction_item` 1,876행 중 **425행(22.7%)** 의 `case_no` 가
`2008타경25092 / 2015타경19958` 형태다. 어느 쪽이 대표인지는 법원 원천이 정하지 않았다.

매칭은 `crawler/resume.py:case_no_matches_list_entry()` 와 **같은 규칙**이다 —
양쪽을 구성요소로 쪼개 **하나라도 겹치면 같은 물건**. 접두 부분문자열
(`2024타경1009` vs `2024타경100920`)은 여전히 걸러진다(BUGS #265 가 세운 규칙).

> 두 함수가 따로 있는 것은 의존 방향 때문이다 — `api/` 가 `crawler/` 를 import 하면
> API 서버가 Selenium 계열을 끌고 들어온다. **규칙이 갈리지 않는지는 검사가
> 두 함수를 나란히 태워** 고정한다(1번, 6쌍).

### 후보가 여럿이면 **고르지 않는다**

물건번호가 1이 아닌 행이 **629행(33.5%)** 다. 사건번호만으로는 물건을 특정할 수 없다.

```
후보 1건    MATCHED             담을 수 있다
후보 N건    AMBIGUOUS           화면이 후보를 나열하고 **사람이 고른다**
후보 0건    NOT_FOUND           원문을 그대로 보여 준다
사건번호 X  NO_CASE_NO          이 줄에서 무엇을 못 읽었는지 알려 준다
같은 키 2회 DUPLICATE_IN_INPUT  버리지 않고 사유와 함께 보여 준다
```

커밋 API 는 **텍스트를 다시 파싱하지 않는다.** 사용자가 확정한 `item_id` 만 받는다 —
미리보기와 커밋이 각자 파싱하면 두 결과가 갈릴 수 있다.

### 좁히기는 되돌릴 수 있어야 한다

법원명/주소는 후보가 여럿일 때만 쓰고, **그것으로 0건이 되면 되돌린다.**
상대의 법원 표기가 우리와 다를 수 있는데(코드일 수도 있다) 그 차이 때문에
"없습니다"라고 말하면 그것이 조용한 오답이다.

## 2. 멱등 — 같은 텍스트를 두 번 가져와도 안전하다

```
favorites        UNIQUE(user_id,item_id) -> 두 번째는 ALREADY_FAVORITED (실패 아님)
favorite_notes   UNIQUE 위에 UPSERT. **빈 값으로 기존 메모를 지우지 않는다**
                 (COALESCE(NULLIF(excluded.memo,''), favorite_notes.memo))
```

빈 값 보호가 왜 필요한가 — 사용자가 목록을 갱신해 다시 가져올 때 메모 칸이 비어
있다고 해서, 그동안 써 둔 메모를 날리면 안 된다. **지우는 것은 명시적인 메모
편집(`PUT`)의 일이다.** 두 규칙을 한 함수에 섞으면 어느 쪽도 정확하지 않게 된다.

★ 이 보호는 **변이 테스트가 처음에 생존해서** 발견된 공백이었다. 원래 검사는
셋 다 빈 값으로 재커밋했는데, 그러면 `_upsert_note()` 가 일찍 돌아가 **UPSERT 에
닿지도 않았다.** "출처만 갱신"이라는 현실적인 경로를 따로 검사에 넣었다.

## 4. `favorite_notes` 가 없는 환경에서도 죽지 않는다

migration **026 은 순수 가산**이지만(`CREATE TABLE/INDEX IF NOT EXISTS` 뿐,
`DROP`/`ALTER`/`DELETE`/`UPDATE`/`INSERT` 문장 0개 — 검사 12번이 고정한다)
**운영 적용은 승인 영역**이라 테이블이 없는 환경이 실제로 존재한다.

무조건 JOIN 했다면 `no such table: favorite_notes` 로 **관심물건 목록 전체가 500**
이 됐을 것이다. 아직 아무도 쓰지 않는 부가 정보 하나 때문에 이미 잘 돌던 핵심
화면이 죽는 셈이다. 그래서:

```
GET /favorites      테이블이 있을 때만 JOIN. 없으면 memo="" / tags=[]
commit              담기는 그대로 되고, `note_written:false` 로 **정직하게** 알린다
PUT  .../note       조용히 성공하지 않는다 -> FAVORITE_NOTE_UNAVAILABLE
화면                "메모·태그 저장은 아직 준비 중입니다"를 표시
```

★ 이 경로는 실측으로 확인했다 — 처음 HTTP 검증을 돌렸을 때 사본이 운영과 같은
**마이그레이션 020** 상태라 메모가 남지 않았고, 그것을 **결함으로 오해했다.**
두 상태(테이블 있음/없음)를 검사에서 명시적으로 갈라 두었다(14번 / 11번).

## 5. 새 API

| 메서드 | 경로 | 성격 |
|---|---|---|
| POST | `/api/v1/favorites/import/preview` | **읽기 전용.** 파싱 + 매칭. 저장 0 |
| POST | `/api/v1/favorites/import/commit` | 확정된 `item_id` 만 저장. 부분 성공 |
| PUT | `/api/v1/favorites/{item_id}/note` | 메모/태그/출처 **통째 교체**(빈 값 = 삭제) |

`GET /api/v1/favorites` 응답에 `memo` / `tags` / `note_source` **가산**.
기존 필드는 하나도 바뀌지 않는다(Breaking Change 없음).

> `preview` 가 읽기 전용인데 POST 인 이유: 붙여넣은 텍스트(최대 500줄)가 본문에
> 실려야 한다. URL 길이 제한 때문에 GET 으로는 보낼 수 없다.

새 Error Code 3종 — `FAVORITE_IMPORT_EMPTY` / `FAVORITE_IMPORT_TOO_LARGE` /
`FAVORITE_NOTE_UNAVAILABLE`. `docs/ERROR_CODES.md` 와
`test_schema_hygiene.py:EMITTED_ERROR_CODES` 양쪽에 등록했다.

## 6. `IN (...)` 변수 상한 (BUGS #243)

붙여넣은 사건번호 개수는 **사용자가 정한다**(500줄 x 병합 구성요소). 그래서
`chunked_for_sql()` 로 나눈다 — 직접 세면 SQLite 변수 상한을 넘겨
"too many SQL variables" 로 **가져오기 전체가 죽는다**(느려지는 것이 아니다).

후보 조회는 두 갈래다.

```
(1) 정확 일치  case_no IN (...)     DB 가 단일로 갖고 있는 경우. 인덱스를 탄다
(2) 부분 일치  case_no LIKE '%A%'   DB 가 병합으로 갖고 있는 경우.
                                   (1) 에서 못 찾은 구성요소에만 돈다
```

(2) 는 선행 와일드카드라 전수 훑기다. 비용을 정직하게 남긴다 — 최악의 경우
(붙여넣은 사건번호가 전부 DB 에 없음) 조각 수만큼 전수 훑기가 난다. 입력이 500줄로
제한되고 사용자가 직접 누른 1회성 작업이라 감수한다.

(2) 는 접두 오검출을 낼 수 있지만 **판정하지 않는다** — 후보를 모으는 자리이고,
같은 물건인지는 `resolve_row()` 가 구성요소 **정확 일치**로 다시 본다.

## 7. 화면 (`/favorites/import`)

새 공통 컴포넌트를 만들지 않았다. `SiteHeader` + `CONTAINER` + 카드 +
Loading/Empty/Error 는 `/favorites` 가 쓰던 것을 그대로 쓴다(Master Spec §11.2).

진입점 3곳: `/favorites` 상단(내보내기 옆) · `/favorites` **빈 상태**(막다른 길
방지 — 다른 곳에 이미 목록을 가진 사용자가 가장 먼저 만나는 화면이다) · `/mypage`.

인증 게이트는 `src/proxy.ts` 의 `/favorites` 접두사가 **이미 덮는다** — 새 게이트를
추가하지 않았다.

### 접근성 — 새 화면이 저장소의 래칫을 밀지 않게 했다

`test_frontend_accessibility.py` 는 작은 글씨/낮은 대비의 **상한**을 건다.
새 화면의 **본문 문장은 전부 `text-sm` + `text-gray-500` 이상**이다.

```
text-[0.6875rem]  늘리지 않음   태그 칩을 새 크기로 만들려다 기존 text-xs 로 되돌림
text-xs      117 -> 119        상태 배지 2개(기존 카드 배지와 같은 크기)
text-gray-400 110 -> 112       placeholder 색만(login/page.tsx 의 기존 관례)
```

placeholder 가 있는 입력에는 `aria-label` 을 붙였다 — 이 저장소의 규칙은
`<label>` 이 아니라 **태그 자신의 접근 이름**이다(placeholder 는 입력을 시작하면
사라지므로 이름이 아니다).
