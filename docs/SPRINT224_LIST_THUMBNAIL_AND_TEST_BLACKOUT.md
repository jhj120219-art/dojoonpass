## 1. 시한폭탄 — 데이터가 하루 낡자 N+1 가드가 눈을 감았다

### 증상

`test_search.py` 의 SQL 횟수 가드가 실패했다.

```
[FAIL] SQL 을 실제로 계측했다(검사가 공허하지 않다) -> {1: (2, 0), 9: (2, 0)}
[PASS] ★ 결과가 늘어도 SQL 횟수가 늘지 않는다(N+1 아님)
[PASS] ★ 검색 1회의 SQL 이 4회를 넘지 않는다
```

★ **주목할 것은 FAIL 이 아니라 그 아래 두 PASS 다.** 별표 두 개가 이 검사의 본체인데,
`(2, 0)` — 즉 **물건 0건**에서 `2 == 2` 로 **공허하게 통과**하고 있었다.

### 원인

`/api/v1/search` 는 기본값 `include_closed=false` 로 `auction_date >= 오늘` 을 건다.

```
DB 총 물건            1,876건
최신 매각기일          2026-08-19   (오늘은 08-20)
마지막 크롤            2026-08-12
-> 기본 검색 결과      0건
```

이 파일의 **다른 모든 호출은 이미 `include_closed=True`** 를 쓰고 있었다(파일 상단에
"매각기일 필터는 이 파일의 관심사가 아니다"라고 적혀 있다). Sprint 223 이 나중에 넣은
SQL 가드만 그 규칙을 따르지 않아, 크롤이 며칠 멈추면 자동으로 눈이 머는 상태였다.

### 이 공백이 실제로 결함을 놓쳤는가 — 확인했다

검색 API 에 진짜 N+1 을 주입하고 **고치기 전 방식**으로 재 봤다.

```
고치기 전 방식(include_closed 없음) + N+1 주입 -> {1: (2, 0), 9: (2, 0)}
  "결과가 늘어도 SQL 이 같다"  통과
  "SQL 이 4회를 넘지 않는다"   통과
```

**진짜 성능 회귀가 조용히 초록불로 통과했다.** 살아 있는 것은 "검사가 공허하지 않다"는
하한선 하나뿐이었고, 그 하나가 없었으면 아무도 몰랐을 것이다.

### 해결

가드도 파일의 나머지와 같이 `include_closed=True` 로 잰다. 측정 대상은
"행 수에 따라 SQL 이 늘어나는가"이지 "오늘 이후 물건이 있는가"가 아니다
(후자는 `test_pipeline_integrity.py` 가 따로 본다).

```
수정 후   size=1 3회 / size=9 3회   (COUNT + 페이지 행 + 썸네일 배치)
```

문서에 적혀 있던 "SQL 3회"가 이제야 실제로 재현된다.

### 변이

N+1 주입 -> 2/2 FAIL (`size1 3회 / size9 11회`).

## 2. 관심물건·최근 본 물건에 대표 사진이 없었다 (Backlog #3)

### 사실 확인

```
thumbnail_url 을 주는 API      api/v1/search.py    하나뿐
관심물건 화면 / 최근 본 물건    <img> 0개
```

사용자는 검색목록에서 **사진을 보고** 담는데, 관심물건을 열면 사진이 사라졌다.
`docs/CURRENT_STATE.md` 는 이것을 "미문서화 공백 / 제품 결정이라 고치지 않았다"로
남겨 두었다. 이번 Backlog 가 명시적으로 지시해 구현했다.

### 규칙이 네 군데로 흩어질 뻔했다

`/api/v1/item/{id}/images/{seq}` 라는 경로 규칙은 이미 **두 곳**에 따로 적혀 있었다
(`item.py:_image_url()`, `search.py:row_to_item()` 안의 문자열). 두 화면을 더하면 넷이 된다.
갈라졌을 때의 증상은 **"목록에는 사진이 나오는데 열면 404"** — 화면은 정상으로 보이고
로그도 조용해서 눈으로는 찾기 어렵다.

그래서 먼저 `api/v1/thumbnails.py` 하나로 모았다.

```
IMAGE_URL_TEMPLATE          경로 규칙의 유일한 출처
image_url(id, seq)          URL 1개
fetch_thumbnail_seqs(conn, ids)   대표 사진 순번 **배치 1회** (MIN(seq) GROUP BY)
thumbnail_url(id, seqs)     없으면 None
```

`search.py` / `item.py` 도 이 모듈을 쓰도록 바꿨다 — **중복을 늘리지 않고 줄였다.**

### 프런트

`ResultThumbnail.tsx` 를 `src/app/search/` 에서 `src/components/` 로 옮겨 세 화면이
같은 컴포넌트를 쓴다. 화면마다 따로 만들면 한쪽만 `onError` 를 빠뜨려 그 화면에서만
깨진 아이콘이 남는다.

`thumbnail_url` 이 **있을 때만** 그린다 — 사진 없는 물건에 빈 회색 칸을 만들면 카드가
오히려 나빠진다(이 저장소의 사진 보유율은 아직 낮다).

### 실브라우저 실측 (localhost:3000, 진짜 세션)

**최근 본 물건** — 운영 DB 그대로

```
카드 11개 중 사진 있는 것 4개
<img> 4개 전부 naturalWidth > 0  (= 브라우저가 실제로 디코딩했다)
  522x700 / 700x393 / 525x700 / 525x700  -> 전부 80x80 으로 렌더
카드 폭   사진 있음 411px == 사진 없음 411px
카드 높이 사진 있음 200px  / 사진 없음 184px
가로 오버플로 0 · main 1개 · 콘솔 오류 0 · hydration 경고 0
```

**관심물건** — 이 계정에 관심물건이 0건이라 운영 데이터로는 볼 수 없었다.
운영 DB 를 건드리지 않기 위해 **스크래치 사본**에 관심물건을 넣고 그 사본을 읽는 API 를
따로 띄워(포트 8001) 확인했다.

```
카드 6개 중 사진 있는 것 4개, <img> 4개 전부 디코딩 성공, 80px
카드 폭 411px · 가로 오버플로 0 · main 1 · h1 1
사진 없는 2건은 종전과 같은 텍스트 전용 카드 (빈 칸 없음)
확인 후 사본·임시 서버 전부 정리, 운영 DB favorites 는 0건 그대로
```

### 회귀 (`test_asset_pipeline.py` 16-B2 신설)

일부러 **1번 순번을 비우고** 2·3번 사진만 넣어 대표가 `MIN(seq)` 인지 본다.

```
1. 두 API 모두 thumbnail_url 키를 **항상** 준다 (없으면 null)
2. 대표 = MIN(seq)
3. 그 URL 이 **실제로 200 으로 열린다**   (저장 성공 != 서빙 성공)
4. 검색목록/관심물건/최근본물건/상세가 **글자 그대로 같은 URL**
5. 기존 키 15개가 하나도 사라지지 않았다
6. 건수가 늘어도 쿼리 수가 같다 -> 실측 (2건, 2회) / (10건, 2회)
```

### 변이 5/5 검출

```
관심물건을 물건마다 조회(N+1)          -> 쿼리 수 2 -> 11, FAIL
관심물건이 thumbnail_url 을 안 준다     -> "키는 항상 존재" FAIL
최근본물건이 없는 사진 URL 을 준다      -> 열어 보는 검사가 404 로 FAIL
대표를 MIN 대신 MAX(seq) 로            -> 상세와 어긋나 FAIL (네 화면 비교도 FAIL)
URL 규칙을 라우트와 다르게              -> 서빙 404 로 FAIL
```

## 3. 검사 하나가 프런트 계약 전체를 가리고 있었다

### 증상

```
npm run test:frontend
  pass 21 / fail 93
  실패 93건 전부 같은 원인: "백엔드에 검색 가능한 물건이 0건입니다 (total=0)"
```

### 원인 — before() 훅의 폭발 반경

전제 검사가 최상위 `before()` 안의 `assert` 였다. node:test 는 `before()` 가 실패하면
**그 아래 전부**를 실패로 떨어뜨린다.

그런데 이 파일의 50개 검사 중 **결과 데이터를 실제로 보는 것은 단 하나**였다.
나머지는 라우팅·리다이렉트 보존·랜드마크·h1·`aria-label`·레이아웃·레거시 경로처럼
**결과가 0건이어도 전부 판정 가능한** 것들이다.

즉 **크롤이 하루만 멈춰도 접근성·라우팅 계약이 통째로 관측 불능**이 되고, 화면에는
"93건 실패"로 보여 진짜 결함과 구별조차 되지 않았다. 관측 공백을 결함으로 보고하면
안 되고, 반대로 감춰도 안 된다.

### 해결

```
연결 실패 / 비200        여전히 hard fail (백엔드 없이 통과시키면 안 된다)
기본 검색 0건            전용 검사 **하나**만 실패시킨다
데이터 없이 판정 가능한 검사   전부 **실제로 실행**
데이터가 꼭 필요한 검사       skip (skip 은 통과가 아니다)
```

원인도 **뭉뚱그리지 않는다.** 예전 문구는 "비었거나 전부 만료됐습니다"였는데, 이 둘은
원인도 조치도 다르다. `include_closed=true` 로 한 번 더 물어 구분한다.

```
DB 에는 물건이 1876건 있으나 **매각기일이 전부 지났다** — 크롤이 멈춰 있다.
DB 가 빈 것이 아니다.
```

### 곁다리로 드러난 결함 — 한 번도 동작하지 않던 skip 분기

두 검사가 "결과 0건이면 건너뛴다"를 이렇게 쓰고 있었다.

```js
if (!homeHtml.includes('/properties/')) return    // 결과 0건 상태
```

`/properties/` 는 **헤더 네비게이션의 `/properties/recent` 링크에도 들어 있다.**
그래서 이 조건은 결과가 0건이어도 **항상 거짓**이었고, 건너뛰려던 분기가 한 번도
동작하지 않았다. 결과 카드만 정확히 가리키는 판정자로 바꿨다.

```js
function hasResultCards(html) { return /\/properties\/\d+\?ids=/.test(html) }
```

### 결과

```
수정 전   pass 21  / fail 93 / skip 0
수정 후   pass 110 / fail  1 / skip 3
          (유일한 실패 = 데이터 전제를 알리는 그 검사 하나)
```

### ★ 초록이 skip 덕분이 아님을 증명했다

검사를 느슨하게 만든 것이 아니라는 근거가 필요했다. 운영 DB 사본에 미래 매각기일
300건을 넣고, 그 사본을 읽는 API(8001) + 그것을 보는 Next 를 띄워 **데이터가 있는
상태로** 같은 스위트를 돌렸다.

```
pass 114 / fail 0 / skip 0
```

데이터만 있으면 **114개 전부가 실제로 판정된다.** 즉 3개의 skip 은 오직 데이터 부족
때문이고, 이번 구조 변경으로 잃은 검증력은 없다. 이 실행은 Sprint 224 의 썸네일 변경이
프런트 계약을 하나도 깨지 않았다는 것도 함께 확인해 준다.

## 4. 변화한 사실에 맞춰 가드를 갱신했다 (약화 아님)

### `test_search.py` — 목록 화면 계약을 가정이 아니라 소스에서 읽는다

앞 판본은 관심물건/최근 본 물건의 제공 필드를
`auction_item 컬럼 + {favorited_at}` 으로 **가정**했다. 그 가정은 `thumbnail_url` 처럼
**컬럼이 아닌 계산된 키**를 표현할 수 없어서, API 가 실제로 그것을 주기 시작하자
**없는 결함을 보고했다.**

소스에서 읽을 수 있는 사실을 손으로 베껴 적으면 반드시 이렇게 어긋난다.
상세페이지를 이미 AST 로 대조하고 있었으므로, 두 화면도 같은 방식으로 맞췄다.

스키마 결합은 **따로** 본다 — 응답 dict 가 읽는 `row["X"]` 의 X 가 실제
`auction_item` 컬럼인가(없으면 런타임 KeyError -> 500).

곁다리 정정: 앞 판본의 설명은 "`SELECT ai.*` 라 계약이 스키마에 묶여 있다"였는데,
실제 응답은 `dict(row)` 가 아니라 **명시적 dict 리터럴**이다. 근거가 스키마가 아니라
그 dict 라는 사실을 문서에도 반영했다.

### `test_frontend_accessibility.py`

`ResultThumbnail.tsx` 경로를 손으로 적고 있어 파일 이동과 함께 고쳤다.
(경로를 문자열로 박은 검사는 이동할 때 같이 옮겨야 한다.)

### `test_schema_hygiene.py`

`api/v1/thumbnails.py` 의 `placeholders` 를 SQL 보간 허용 목록에 추가했다.
`search.py` 에서 이미 허용돼 있던 **같은 것을 모듈로 옮긴 것**이다 — 내용은 항상 `?`
문자만 반복되고 개수만 가변, 값은 전부 `?` 로 바인딩된다.

**승인 영역이라 하지 않았다.** 커밋할 때 `git add -A` 로 함께 담으면 즉시 초록이 된다.

## 6. 확인하지 못한 것 (모른다고 적는다)

**모바일 실뷰포트** — 여전히 재지 못했다. 이번에는 iframe(390px)에 같은 화면을 띄워
재려 했는데 앱 자신의 `X-Frame-Options: DENY`(Sprint 127)에 막혔다. 앱이 옳게 동작한
것이고 측정 경로가 닫힌 것이다. 카드 폭·가로 오버플로는 데스크톱 폭에서만 실측했다.

**관심물건 화면의 운영 데이터 렌더** — 이 계정의 관심물건이 0건이라 운영 데이터로는
볼 수 없었다. 사본으로 확인했고, 운영 데이터에 관심물건을 만드는 것은 하지 않았다.
