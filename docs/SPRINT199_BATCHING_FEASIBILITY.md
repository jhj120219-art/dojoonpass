# Sprint 199 — 물건 단위 묶기 실증 + "실패 != 없음"의 직접 증거

2026-08-18. 기준 커밋 `73ac6eb`.

Sprint 197 은 `doc_worker` 의 이동 비용이 63% 라고 재고 "물건 단위로 묶으면 47% 절감
여지"라고 **추정**했다. 이번에는 그것이 **구조적으로 가능한지**를 호출 그래프와
**실브라우저**로 확인한다. 추정으로 끝내지 않는다.

---

## 1. 호출 그래프 — 수집기는 페이지를 떠나지 않는다

`crawler/doc_crawler.py` / `crawler/image_crawler.py` 의 수집 함수를 AST 로 훑어
**이동 호출**(`go_to_list` / `go_to_case_detail` / `driver.get`)과 **창 조작**을 분리했다.

| 함수 | 이동 호출 | 창 조작 |
|---|---|---|
| `collect_spec` | **없음** | `switch_to.window` -> `close` -> `switch_to.window` |
| `collect_status` | **없음** | 없음 (오버레이) |
| `collect_appraisal` | **없음** | `window` x2 -> `close` |
| `collect_document` | **없음** | 없음 (분배만) |
| `collect_images` | **없음** | 없음 (DOM 직접) |

즉 **어느 수집기도 상세페이지를 떠나지 않는다.** 새 탭을 여는 둘(spec/appraisal)도
`finally` 에서 탭을 닫고 원래 창으로 돌아온다.

---

## 2. 그러나 코드 구조만으로 판정하지 않는다 — 실브라우저 확인

AST 에 이동 호출이 없다는 것과 "이동 1회 뒤 두 번째 종류가 실제로 수집된다"는
다른 말이다. 탭을 닫는 과정에서 세션이 흐트러질 수도 있다. 직접 확인했다.

DB 무변경 / 문서 루트는 임시 디렉터리 / 법원 부하는 물건 1건 x 2종.

```
대상: 서울중앙지방법원 / 2024타경3528-1 (기일 2026-08-19)

1) go_to_case_detail            -> True      18.2초   창 1개
2) collect_document(spec)       -> False     32.9초   창 1개 (변화 없음)
                                                       URL 그대로: True
3) 상세페이지 생존 확인          -> 사진 요소 5개 (이동 재시도 없이 읽힘)
4) collect_document(image)      -> True       0.0초   사진 5장

VERDICT: 묶기 가능 - 이동 1회 뒤 두 번째 종류가 정상 수집됐다
```

### 핵심 수치: 이미지 수집은 **0.0초**다

상세페이지에 이미 있으면 사진은 DOM 에서 바로 읽힌다(base64). **사진의 전체 비용은
사실상 이동 비용 하나뿐**이라는 뜻이다. 묶기의 이득이 사진에서 가장 크다.

```
묶어서(이동 1회)  18.2 + 32.9 + 0.0 = 51.1초
현재(이동 2회)    18.2 + 32.9 + 18.2 + 0.0 = 69.3초
절감              18.2초 (26%)      <- 2종 기준. 4종이면 이동 3회를 아낀다
```

> **[증거 등급 표시 2026-08-18 Sprint 209]** 위 표의 마지막 칸("4종이면 이동 3회를
> 아낀다")은 이 Sprint 시점에는 **실증이 아니라 외삽**이었다. 실제로 돌려 본 것은
> **2종(spec + image)** 뿐이다. 그 구분이 본문에 드러나 있지 않아 여기 표시한다.
>
> **그 외삽은 이후 실측으로 뒷받침됐다** — `docs/SPRINT201_DOWNLOADED_BUT_DISCARDED.md` §4
> 가 가장 불리한 순서(새 탭 2종 연속 -> 오버레이 -> DOM)로 4종 전부를 돌려
> 창 1개·URL 유지·사진요소 5개 생존을 확인했고, 절감 **44%**(72.6초 vs 129.7초)를 쟀다.
>
> 즉 결론은 바뀌지 않았지만, **이 문서만 읽는 사람이 4종 실증을 여기서 했다고
> 오해하지 않도록** 시점을 명시한다. 증거 등급은 이렇게 나뉜다.
>
> | 주장 | 이 문서의 증거 | 최종 증거 |
> |---|---|---|
> | 수집기가 페이지를 떠나지 않는다 | 코드(AST) 확인 | 그대로 |
> | 이동 1회 뒤 2종이 이어서 수집된다 | **실브라우저 2종** | 그대로 |
> | 4종도 같다 | **외삽** | Sprint 201 실브라우저 4종 |
> | 절감률 | 2종 26% 실측 + 4종 외삽 | Sprint 201 4종 **44%** 실측 |

## 3. ★ 뜻밖의 소득 — "수집 실패 != 원래 없음"의 직접 증거

위 실행에서 `spec` 이 **다운로드 타임아웃(30초)** 으로 실패했다. 그런데 그 물건의
현재 상태를 보면:

```
document_status  SPEC / STATUS / APPRAISAL  전부 READY
document_queue   spec / status / appraisal  전부 done
디스크           spec.pdf 392,074 B  (실제로 있다)
```

**이미 정상 수집된 적이 있는, 실재하는 문서가 재시도에서 실패했다.**

이것은 Sprint 197 이 "문서의 '원래 없음'에는 신뢰할 positive signal 이 없다"고 판단한
근거를 **직접 실증**한다. 만약 "수집 실패 = 법원 미제공" 으로 상태를 만들었다면,
이 실행 하나로 **실재하는 문서가 '원래 없음'으로 기록**될 뻔했다.

그리고 BUGS #122 의 방어가 정확히 이 상황을 위한 것임도 확인된다 —
재수집이 최종 실패해도 화면 상태가 READY 면 그대로 둔다. 이 물건이 refresh 행이었다면
그 방어가 발동해 사용자는 계속 문서를 볼 수 있었다.

**문서 수집은 간헐적으로 실패한다.** 그것이 이 파이프라인의 성질이고,
`MAX_DOC_RETRY = 3` 과 BUGS #122 가 그 성질을 전제로 만들어져 있다.

## 4. 그래서 묶기를 구현하는가 — 하지 않는다 (근거)

**가능하다는 것은 증명됐다.** 그래도 지금 하지 않는다.

### 하지 않는 이유

```
1. claim 단위가 바뀐다        행 단위 원자적 claim -> 물건 단위. Sprint 191 이 고친
                              경쟁 처리(BUGS #130)와 Sprint 189 의 refresh 상태 보존이
                              전부 **행 단위**를 전제로 짜여 있다.
2. 재시도 예산이 행 단위다     MAX_DOC_RETRY 는 큐 행마다 센다. 묶으면 물건 중간에
                              죽었을 때 어느 행의 예산을 깎을지 새로 정해야 한다.
3. 지금 이득이 0이다          대기 중이면서 기일이 남은 물건이 **2개**다.
                              절감액은 초 단위다.
4. 위험이 가장 큰 시점이다     Sprint 189~194 가 claim/retry/partial 을 막 고쳤다.
                              그 직후에 그 셋의 전제를 흔드는 것은 순서가 나쁘다.
```

### 구현하게 될 때를 위한 설계 메모 (실측으로 확정된 제약)

```
가능   go_to_case_detail() 1회 후 collect_document() 를 종류별로 이어서 호출 가능.
       spec/appraisal 이 새 탭을 열고 닫아도 상세페이지·창 수·URL 이 보존된다(실측).
순서   image 를 마지막에 두면 이득이 가장 크다(비용 0.0초, DOM 이 이미 있다).
       단 spec/appraisal 이 탭을 닫고 돌아온 뒤에도 DOM 이 살아 있음은 확인됐다.
필요   claim_next_item_rows() 같은 **물건 단위 원자적 claim** 이 새로 필요하다.
       기존 claim_next_queue_item() 은 남겨 둔다(다른 호출부·회귀가 쓴다).
실패   물건 중간 실패 시 **남은 행은 건드리지 않고** 실패한 행만 mark_queue_failed
       하는 것이 현재 의미론과 가장 가깝다.
착수 조건  큐의 "대기 + 기일 남은" 물건이 수백 이상으로 자란 뒤(BUGS #123 해소 후).
```

## 5. 비용 모델 정정 — 24초는 평균이지 상수가 아니다

`DOC_COLLECT_SECONDS_PER_ROW = 24.0` 은 평균 근사다. 이번 실측 분해:

```
이동                18.2초   (Sprint 147 실측 15.2 와 같은 자릿수)
spec (타임아웃)     32.9초   (wait_for_download timeout=30 + 부대 비용)
image               0.0초    (DOM 이 이미 있다)
```

즉 종류마다 크게 다르다. 상한 계산에 쓰는 `DOC_COLLECT_SECONDS_PER_ROW` 는
**보수적 평균**으로서 유효하지만(실패 경로가 30초를 쓰므로 24는 낙관적일 수 있다),
`test_refresh_trigger.py` §17 이 이미 그 한계를 문서화하고 있다 —
*"실측을 사람이 옮겨 적은 값이라, 실제 수집이 느려졌는데 상수를 안 고치면 검사는
통과하면서 현실은 넘친다."*

이번 실측은 그 경고가 실제 위험임을 보여 준다(타임아웃 경로 32.9초 > 24.0초).
상한 60 의 여유(창의 80%)가 그 차이를 흡수한다: 60 x 2행(실측 조합) x 32.9 = 3,948초
= 창의 55%. **실측 조합 기준으로는 타임아웃을 다 맞아도 창 안이다.**
