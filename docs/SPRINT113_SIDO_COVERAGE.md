## 1. 프런트 쓰기 경로부터 (결함 0건)

먼저 FALSE SUCCESS 감사를 프런트 쓰기에 적용했다. `postJSON`/`deleteJSON` 은
`!res.ok` 에서만 던지는데, 백엔드의 `error_response()` 는 **HTTP 200 + `success:false`** 다.
즉 실패가 예외로 오지 않는다.

호출부 **6곳 전부** `result.success` 를 본다. 그리고 멱등 케이스를 도메인 Error Code 로
구분한다(`FAVORITE_ALREADY_EXISTS` / `FAVORITE_NOT_FOUND` 는 성공으로 취급).
백엔드도 짝이 맞는다 ― `OVERAGE_USAGE` 는 대상 신청이 없으면 **결제 자체를 만들지 않고**
`PAY_NO_TARGET_REQUEST` 로 끝낸다. **거짓 성공 없음.**

## 2. 정규화기 ― 지금 코드는 견고하다

```
함정 주소 7건 (부분문자열 오매칭 유도)      오답 0
실주소 1,876건, 뽑은 sido 가 앞머리에 없음   0건
정규화 중 예외                              0건
```

함정은 옛 데이터에서 발견한 실제 오류 모양을 그대로 썼다.

```
"경기도 시흥시 서울대학로 59-21"          옛 저장값 '서울'  -> 지금 '경기'  OK
"경상남도 양산시 물금읍 부산대학로 150"    옛 저장값 '부산'  -> 지금 '경남'  OK
"인천광역시 계양구 ... (효성동, 뉴서울아파트)" 옛 저장값 '서울'  -> 지금 '인천'  OK
```

**시/도 이름이 도로명·건물명 속 부분문자열로 들어간 경우를 전부 옳게 처리한다.**
그리고 이 회귀는 `test_normalizer.py` 의 `SIDO_POSITION_CASES` 가 **이미** 덮고 있었다 ―
사전 순서를 뒤집어도 결과가 같은지, validator 가 같은 함수를 쓰는지까지 본다. 중복하지 않았다.

저장값 드리프트(sido 4행 / sigungu 207행)도 다시 쟀는데
`test_pipeline_integrity.py` §12 의 상한과 **정확히 일치**했다. 독립 확인이다.

## 3. ★ 남아 있던 사각지대 ― `sido` 가 아예 빈 행

§12는 "저장값이 지금 코드 결과와 다른가"를 보는데, **새 값이 비어 있으면 세지 않는다**
(백필이 채워진 값을 빈 값으로 덮지 않으므로). 그래서 `sido` 가 **아예 빈 행**은
어느 검사에도 걸리지 않았다.

`sido` 가 비면 그 물건은 **어떤 시/도 필터에도 걸리지 않는다.**
오류도 빈 화면도 아니고 §12가 지적한 것과 같은 모양이다 ― **그냥 없는 것처럼 보인다.**
그리고 시/도 선택은 이 서비스의 가장 흔한 검색 진입점이다.

실측 결과 **3건**이었고 **전부 정상**이었다.

```
자동차  "사용본거지 : 순천시 삼산로 81, ..."      <- 소재지가 아니라 사용본거지
기타    "선적항 : 완도군 완도읍 [선박 동력선]"     <- 선박
기타    "선적항 : 여수시 삼산면 거문항 [선박]"
```

부동산 물건종류(아파트 201 / 다세대 246 / 전답 188 / 임야 123 / 상가 / 오피스텔 …)는
**결측 0건**이다.

### 그래서 개수가 아니라 **이유**를 고정했다 (§14 신설)

개수에 상한을 두는 것은 임의 정책이다. 대신 구분을 불변식으로 뒀다.

```
(a) 주소에 시/도가 애초에 없다      -> 정상. 채울 방법이 없다.
(b) 주소에 시/도가 있는데 못 뽑았다  -> 결함.
```

```
[PASS] 주소에서 시/도를 뽑을 수 있는데 비어 있는 행: []
[PASS] 소재지 주소인데 시/도가 비어 있는 행: []
```

판정은 **운영 정규화기에 직접 물어본다.** 규칙을 검사에 베끼면 두 기준이 갈라져도 통과한다.
스케줄러가 켜져 새 데이터가 들어와도 같은 기준이 적용된다.

> "순천시 → 전남" 처럼 시군구로 시도를 **추론**하는 것은 새 매핑 테이블이 필요한
> 설계 결정이라 하지 않았다. 이 저장소의 '추측하지 않는다' 방침과도 맞다.
