### ★ 문서가 말한 "944개 전환"은 **틀렸다**

브리핑과 이전 문서가 "944개 물건이 3종 완료 상태"라고 적고 있었다. 다시 세니 아니다.

```
큐 물건 조합 (실측 2026-08-21)
    903  3종 전부 pending
  ★ 160  3종 전부 done          <- 이것이 "3종 완료 -> image 추가" 전환 대상이다
     62  3종 전부 SKIPPED_EXPIRED
     36  done/done/pending
      5  나머지 혼합
   ----
  1,166  합계

944 = **pending 행을 가진 물건 수** (Sprint 241 이 잰 값)
160 = **3종이 done 인 물건 수**
두 값은 다른 것을 센다. 944 를 전환 규모로 쓰면 6배 과대평가다.
```

`test_image_queue_transition.py:test_population_matches_the_live_queue()` 가 이 두 값을
**실행 시점에 다시 세고 서로 다른지 확인**한다(숫자를 고정하지 않는다 — 크롤이 재개되면
값이 변하는 것이 정상이다).

### 전환의 방아쇠는 큐의 날짜가 아니라 **새 크롤 결과**다

```

```

그런데 `enqueue_documents(rows)` 의 `auction_date` 는 **새로 크롤한 행**의 값이다.
즉 전환은 "법원 목록에 다시 나온 물건"에서만 일어난다. 큐의 옛 날짜는 무관하다.

## 1. image 큐 전환 — 실제 함수로 관통 검증 (`test_image_queue_transition.py` 신설, 69검사)

`enqueue_documents()` -> `claim_next_item_rows()` -> `doc_worker.main()` 을 **진짜로 호출**한다
(브라우저와 수집기만 가짜). 격리 fixture DB — 운영 DB 무변경.

```
2. 3종 done 물건에 image 만 추가       added=1 / 전체 4행 / image=pending
                                        기존 3종 status 불변, 기일만 갱신(refreshed=3)
3. 재적재 5회                           (전체,image) = (4,1) x 5  <- 폭증 없음
4. image 가 done 이면                   added=0 / done 유지 / 워커 이동 0회
5. image 가 failed 면                   적재는 되살리지 않는다(failed·retry_count 보존)
                                        회수 규칙(reset_stale_queue)만 pending 으로 되돌린다
                                        회수 후 워커가 image 만 처리, 이동 1회(엄격)
6. image 실패(엄격진입/수집 둘 다)        기존 3종 done 그대로 / image 만 재시도 예산 1 소모
7. image 실패 + 형제 pending             문서 3종은 전부 done 이 된다(전파 없음), exit 0
8. 기일 경과 물건                        added=0 / skipped_expired=1 / image 행 자체가 안 생김
9. 실측 분포 재현(115물건)               image 109행 추가 = 재등장 물건 수와 정확히 일치
                                        만료 그룹은 image 0 / 3종 신규 생성 0 / done 부활 0
                                        워커 이동 109회 = 물건 수 (batching 유지), 전부 엄격
                                        pending 잔여 0
```

### Mutation 8종 — 전부 잡힘

```
M1 image enqueue 제거                    -> transition FAIL, batching FAIL
M2 INSERT OR IGNORE 제거(중복 허용)       -> transition FAIL, batching FAIL
M3 기존 done 을 재-enqueue(status 되살림)  -> transition FAIL
M4 기일 경과 사전제외 제거                 -> transition FAIL
M5 수집 실패를 done 으로 오판              -> transition FAIL, batching FAIL
M6 image 실패를 묶음 전체로 전파            -> transition FAIL, batching FAIL
M7 item-level batching 연결 누락           -> transition FAIL
M8 retry 대상 누락(failed 회수 제거)        -> transition FAIL
```

M5/M6 는 첫 패턴이 들여쓰기 때문에 빗나가서 **무효 변이**였다. 알아채고 행 번호로 다시
적용해 유효한 변이로 만든 뒤 판정했다(무효 변이를 "검출"로 세지 않는다).

### 3.3 URL 선택 오류(C)는 **구조적으로 성립하지 않는다** — 다만 한 곳을 고쳤다

사진에는 **URL 이 없다.** 바이트가 HTML 안에 base64 로 박혀 온다. 그러므로 "더 큰 원본
URL 을 두고 썸네일 URL 을 골랐다"는 경로 자체가 존재하지 않는다.

**단 하나 선택이 일어나는 지점**이 있었다 — 같은 순번의 후보가 둘 이상일 때.
옛 규칙은 **"먼저 나온 것을 쓰고 뒤엣것을 버린다"** 였고, 그 파일의 주석이 이미
*"캐러셀이 썸네일까지 같은 id 규칙으로 그리는 경우"* 를 위험으로 적어 두고 있었다.
DOM 순서상 썸네일이 먼저 오는 것이 자연스러우므로, 그 규칙은 **큰 사진을 두고 작은 것을
저장할 수 있었다.**

```
고침: 후보가 여럿이면 **가장 큰 것**(면적 -> 바이트)을 고른다. DOM 순서에 의존하지 않는다.
      후보가 하나면 동작은 완전히 동일하다(현재 운영 45장이 그 상태).
덤:   후보가 둘 이상이면 각 후보의 해상도를 로그로 남긴다
      -> **다음 실크롤이 "더 큰 변형이 존재하는가"에 스스로 답한다**(B/C 가설 검증기)
      alt 규칙에 안 맞는 **큰 data:image 요소**도 경고로 남긴다(법원 DOM 변경 감지)
```

### 3.4 프런트는 저장본을 줄이지 않는다 — E 배제

실제 브라우저 실측(상세 `/properties/505`):

```
히어로 img   currentSrc /api/v1/item/505/images/1   naturalWidth **522x700**
             표시 박스 578x420 / object-fit: contain  -> 왜곡 없음, 60% 축소 **표시**
썸네일 줄     같은 URL, 78x78 로 표시

```

즉 화면이 **작게 그리는** 것이지 **작게 저장한** 것이 아니다.

### 3.5 판정

```
A. 법원이 그 크기만 제공                 ★ 현재 증거가 가장 강하게 지지
B. 법원은 고해상도인데 우리가 썸네일 수집   증거 없음 (아래 근거로 반대 방향)
C. 원본 URL 은 있는데 추출 로직이 잘못     구조적으로 성립하지 않음(URL 자체가 없음)
                                        + 유일한 선택 지점은 이번에 "가장 큰 것"으로 고침
D. 다운로드/저장에서 리사이즈             배제 (바이트 sha256 동일, resize 호출 0건)
E. 프런트에서만 리사이즈                  배제 (저장본이 700px, 프런트는 표시만 축소)
```

**A 를 지지하는 근거**

1. 45장 전부 긴 변이 **정확히 700** — 원천에 일관된 정규화 규칙이 있다는 뜻이다.
2. EXIF 가 45장 전부 없다 — 카메라 원본이 아니라 **서버가 재인코딩한 산출물**이다.
3. 그런데 양자화 테이블이 **64(거의 무손실)와 1858(보통) 두 종류**로 갈린다.
   썸네일 생성 파이프라인이라면 하나로 통일됐을 것이다. 즉 "썸네일"이 아니라
   업로드/게시 단계의 **크기 정규화**로 보인다.
4. 663x700 짜리 한 장이 **536KB(1.16 bytes/px)** 다. 아무도 썸네일을 거의 무손실로
   인코딩하지 않는다. 이것은 법원이 **보여주려고 만든 이미지**다.
5. 바이트가 HTML 에 base64 로 박혀 온다. 더 큰 원본이 따로 있다면 그것을 이 방식으로
   넣을 이유가 없다(이미 장당 최대 536KB 가 페이지에 실려 온다).

**B/C 를 완전히 배제하려면** 살아 있는 법원 상세페이지를 열어 캐러셀 DOM 전체와
클릭 시 열리는 확대 경로를 봐야 한다. 그것은 **실크롤 = 승인 영역**이라 이번에 하지 않았다.
대신 §3.3 의 로그를 넣어 **다음 실크롤이 그 답을 자동으로 남기도록** 했다.

```
MF1 상세의 FAILED 분기 제거                      -> ★ 처음엔 **살아남음** -> 가드 신설 후 FAIL
MF2 상세의 NO_IMAGE 분기 제거                    -> 가드 신설 후 FAIL
MF3 두 분기 문구를 동일하게                       -> ★ 첫 가드가 **공허**했다 -> 고친 뒤 FAIL
```

MF1 은 실제 공백이었다: 재시도가 소진된 실패가 화면에서 "사진 수집 중입니다"로 보였는데
tsc/node/접근성/상태동기화 어느 것도 울지 않았다.
MF3 은 **내 가드가 공허**했던 경우다 — 조건문까지 포함해 비교하니 문구를 같게 만들어도
앞부분이 달라 늘 통과했다. 본문 문구만 뽑아 비교하도록 고쳤다.
