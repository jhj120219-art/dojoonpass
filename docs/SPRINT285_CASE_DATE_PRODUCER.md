## 2. ★ 이번 세션의 가장 큰 발견 — 유실된 작업을 찾았다

값을 배선하려고 보니 실데이터가 이상했다. `auction_case` 를 **생성일별로** 나눠 보니
생산자가 있었다가 없어진 모양이었다.

```
created_at   행수   filed_date  case_type  demand_deadline
2026-08-30    21        21          5           5
2026-08-31     2         2          0           0
2026-09-01    29         0          0           0     <- 여기서 끊긴다
2026-09-02    53         0          0           0
```

`git stash list` 에 답이 있었다.

```
stash@{0}: On master: HOME_BACKUP_BEFORE_STORE_SYNC_20260831
```

**2026-08-30 홈 세션이 이 기능을 이미 구현했고, 08-31 store sync 에서 그 작업이
통째로 되돌아갔다.** 저장소에 남은 것은 결과의 흔적뿐이었다:

* `auction.filed_date` 컬럼(값 313행)은 라이브에 남았다 → 매장 PC 가 그것을 보고
  `028_auction_filed_date.sql` 을 **역으로 복원**했다(그 파일 머리말이 "복원본"이라고
  적고 있다). 컬럼은 살렸는데 **채우는 코드는 못 살렸다.**
* `docs/BUGS.md` 는 #276 까지만 남았다. stash 에는 **#277~#288** 이 있다.

sync 가 일부는 가져오고 일부는 흘렸다 — 예를 들어 `record_collect_failure()` 는
HEAD 에 있는데 `failure_streak_days()` / `auction_has_filed_date()` / `_build_upsert_sql()`
는 없다.

### 그래서 새로 만들지 않고 **원본을 되살렸다**

처음에는 내가 직접 배선했다(모델에 필드 추가 + 크롤러에서 추출). 돌아가긴 했다.
그런데 원본을 찾고 보니 **원본이 더 나았다.**

```
내 판본                     원본
모델에 filed_date 필드 추가   basic_info 를 정규화기에서 직접 읽는다(파일 2개 덜 건드림)
UPSERT 문 한 벌              028 **미적용 DB** 를 위해 두 벌을 만들어 실행 시점에 고른다
```

원본 주석에 그 이유가 실측으로 적혀 있었다: 무조건 `filed_date` 를 쓰면 마이그레이션
전 DB 에서 **모든 행이 `no such column` 으로 실패**한다(*"스위트가 68/1 -> 62/7 로
무너졌다"*). 내 판본은 그 함정에 그대로 걸릴 것이었다.

같은 목적의 구현을 두 벌 만드는 것이 이 저장소가 'Frankenstein' 이라 부르는 바로
그것이라, **내 판본을 버리고 원본을 복원했다.**

빈 값을 NULL 로 바꾸는 이유가 그것이고, 변이 M5 가 그 한 줄을 되돌리면 죽는다.

## 5. ★ #278 — 재수집 상한이 물건을 **영구히 잃고 있었다**

유실된 작업을 훑다가 HEAD 에 **아직 살아 있는** 결함을 찾았다
(`storage/database.py:795`).

```python
cap = REFRESH_MAX_ITEMS_PER_RUN if max_items is None else max_items   # 60
...
logger.warning("... 이번 실행에서 미룬다(큐에 그대로 남아 다음 실행에서 다시 후보가 된다)")
changes = changes[:cap]
```

**로그가 사실이 아니다.** 잘린 물건도 `auction_item` 은 그 실행에서 이미 갱신되므로,
다음 실행의 변경 감지에 **다시 들어오지 않는다.**

### 재현 `[스크래치]`

빈 DB 에 200물건을 넣고 최저가를 전부 바꿨다.

```
2일차  변경 200물건 -> requeue {items:60, refreshed:60, skipped_over_cap:140}
       큐: done 740 / refresh 60
3일차  법원 자료가 2일차와 동일(정상적인 날) -> requeue {} (변경 0건)
       큐: 그대로 -> 140물건은 다시 후보가 되지 않았다
```

즉 **하루에 60물건 넘게 바뀌면 나머지는 옛 문서로 굳는다.** 게다가
`SELECT * FROM auction` 순서라 매번 같은 앞쪽 물건만 뽑혀, 뒤쪽 물건에는 차례가
영영 오지 않는다.

### 고친 방법 — 상한이 **잘못된 계층**에 있었다

상한 60 의 근거는 *워커가 하룻밤에 처리할 수 있는 양*이다(창 7,200초 / 물건당 최악
4행 x 24초 → 69물건). 그건 **소비**의 한계인데 **생산**(큐에 적는 일) 쪽에 걸려
있었다. 큐는 할 일을 담으려고 있는 것이라, 담기 전에 자르면 큐가 존재할 이유가 없다.

소비 쪽은 이미 스스로 제한한다 — `doc_worker` 의 02:00~04:00 창과
`ORDER BY priority ASC, auction_date ASC` 클레임 순서. 전부 적어 두면 오늘 밤은 급한
것부터 하고 나머지는 큐에 남아 다음 밤에 이어서 한다. 기일이 지나면
`SKIPPED_EXPIRED` 가 정리한다.

`max_items` 를 **명시적으로** 넘기면 여전히 조인다(검사·수동 실행용). 바뀐 것은
기본값뿐이다. 수정 후 같은 재현: `{items:200, refreshed:200, skipped_over_cap:0}`.

## 6~8. 게이트가 거짓으로 붉거나 기계를 타던 자리 셋

**(6) §15 생산자 검사가 기계마다 다른 답을 냈다.** "전체 행 중 하나라도 값이 있으면
생산자가 있다"로 판정했는데, 이 표에는 **옛 코드가 남긴 값**이 있다. 그래서 같은
코드가 매장 PC(낡은 DB, filed 0)에서는 통과하고 홈 PC(filed 217)에서는 실패했다.
판정을 **최근 생성된 행**(created_at 최신 3일)으로 바꿨다 — 묻는 것은 "값이 있는
행이 있는가"가 아니라 **"지금 도는 파이프라인이 이것을 채우는가"** 이기 때문이다.
누적 수치는 근거로 함께 찍는다("누적에는 옛 코드가 남긴 값이 있다").

**(7) 경로 검사가 `api/constants.py:LIKE_ESCAPE_CHAR = "\\"` 를 상대경로로 집었다**
(Sprint 284 가 만든 상수다). `"\\" in v` 갈래에 걸린 것인데, 구분자뿐인 문자열은
이름 성분이 없어 어떤 파일도 가리키지 못한다. 진짜 상대경로는 구분자 아닌 글자를
반드시 하나 이상 가지므로 탐지력은 깎이지 않는다(자기 검증에 이 모양을 고정했고,
가드를 되돌리면 죽는다).

**(8) `--apply` 검사가 SQL 문자열 **상수**를 쓰기로 봤다.** 원본이 보충 UPDATE 를
모듈 상수로 둔 것은 *검사가 그 문장을 그대로 태우게* 하려는 의도인데(베껴 쓰면 소스를
고쳐도 검사는 옛 문장을 태운다), 그 좋은 습관에 가드가 벌을 주고 있었다. 최상위
노드에 **호출이 하나도 없으면** 아무것도 실행되지 않으므로 건너뛴다. 잡으려던 두
파일(`fix_validator.py` / `add_test_queue.py`)은 실제로 호출하므로 그대로 잡힌다.
