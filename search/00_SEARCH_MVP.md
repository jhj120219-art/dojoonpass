# 개발 원칙

이 문서는 검색 기능 구현의 단일 기준(Single Source of Truth)이다.
Claude Code는 본 문서를 우선적으로 따르며, reference 폴더의 HTML은 구현 참고 자료로만 사용한다.
분석보다 구현을 우선하며, 기능은 반드시 테스트 후 다음 단계로 진행한다.

**v0.2 추가 원칙 — 기존 구현 재사용**

- 검색 화면 재정의는 **UI 구조(배치/폭/진입 경로) 변경**이며, 검색 기능 자체의 재구현이 아니다.
- 이미 구현된 `SearchForm` / `SearchPresets` / `SortBar` / `ResultList` / `Pagination` /
  `FavoriteButton` 및 `src/components/*`(PriceRangeSelect / RangeSelect / PropertyTypeTree /
  SearchAccordionSection)를 **그대로 재사용**한다. 같은 기능의 컴포넌트를 새로 만들지 않는다.
- `GET /api/v1/search`의 쿼리 파라미터, 응답 구조(`{ total, page, size, total_pages, items[] }`),
  offset 페이지네이션은 **변경하지 않는다**(`docs/search-engine.md` "절대 변경하면 안 되는 것").
- 즐겨찾기 / 최근조회 / 검색조건 저장의 기존 API 계약과 클라이언트 흐름도 변경하지 않는다.

# 1. 첫 진입 화면 (v0.2 신규 · 최우선)

## 1.1 정의

**`/`(localhost:3000)의 첫 화면은 "경매 물건 검색 화면"이다.**

- `/` 는 로그인 화면이 아니다.
- `/` 는 어떤 경로로도 **자동 redirect 하지 않는다**(로그인 여부와 무관).
- 첫 화면에 진입하면 **검색조건 입력 Form**이 곧바로 보이고,
  그 **아래에 경매 물건 목록(검색 결과)**이 이어서 보인다.
- 비로그인 사용자도 첫 화면에서 **즉시 검색조건을 입력하고 검색을 실행**할 수 있다.

## 1.2 첫 로드 시 목록

- 쿼리 파라미터가 없는 상태에서도 검색 결과 영역은 **비어 있지 않다.**
- 파라미터 없이 `GET /api/v1/search`를 호출하면 백엔드의 기본 동작
  (`include_closed=false` → `auction_date >= 오늘`, 기본 정렬 `auction_date DESC, fail_count DESC`)
  으로 진행 중인 물건 목록이 반환된다. 이 결과를 그대로 "기본 물건 목록"으로 노출한다.
- 별도의 "추천/인기 물건" 개념은 만들지 않는다(투자점수·AI추천 금지 규칙과 별개로, 신규 API 불요).

## 1.3 금지 사항 (해결 대상 문제)

아래는 v0.1 시점 구현에서 실제로 발생하던 문제이며, 전부 **해결 대상**으로 기록한다.

| # | 문제 | 현재 원인 |
|---|---|---|
| P1 | 첫 화면에서 로그인을 강제함 | `src/app/page.tsx`가 무조건 redirect(`/properties` 또는 `/login`) |
| P2 | 검색이 별도 진입 화면(`/search`)처럼 취급됨 | 첫 화면과 검색 화면이 분리 |
| P3 | 검색 결과가 첫 화면에 자연스럽게 이어지지 않음 | 검색 실행이 항상 `/search`로 페이지 이동 |
| P4 | 좌우 여백이 비정상적으로 넓음 | 모바일 1열 레이아웃이 데스크톱 폭에 그대로 늘어남 |
| P5 | 콘텐츠 중앙 정렬 · 적정 최대 폭 부재 | 화면별로 컨테이너 규칙이 제각각(`px-5` 풀블리드 / `max-w-[1320px]` 혼재) |
| P6 | 첫 화면에서 경매 물건을 바로 탐색하기 어려움 | 첫 화면이 로그인 폼이라 물건이 아예 노출되지 않음 |

# 2. 라우트 접근 정책 (공개 / 인증 필요)

## 2.1 원칙

**로그인은 검색을 막는 장치가 아니다.**
로그인은 **사용자 개인에게 귀속되는 데이터**(즐겨찾기 / 최근조회 / 검색조건 저장 / 구독 / 결제 /
등기부 발급)에서만 요구한다.

## 2.2 공개 라우트 (인증 불필요)

| 경로 | 내용 |
|---|---|
| `/` | 검색 화면(첫 진입 화면). 검색 Form + 검색 결과 + 물건 목록 |
| `/search` | `/`와 동일한 검색 화면. 기존 링크/북마크 호환을 위해 유지 |
| `/login` | 로그인 / 회원가입 |

- 공개 라우트는 **미들웨어에서 인증 검사로 차단하지 않는다.**
- 공개 라우트에서 사용하는 API도 인증 없이 동작해야 한다:
  `GET /api/v1/search`, `GET /api/v1/search/regions`.
  두 API는 이미 선택적 인증(`HTTPBearer(auto_error=False)`) 구조이며 **변경하지 않는다** —
  토큰이 있으면 결과의 `is_favorited`를 채우고, 없거나 검증에 실패해도 검색은 그대로 진행된다.

## 2.3 인증 필요 라우트 / 기능

| 대상 | 유형 | 로그인 요구 시점 |
|---|---|---|
| `/favorites` | 화면 | 화면 진입 시 |
| `/properties/recent` | 화면 | 화면 진입 시 |
| 즐겨찾기 토글(`FavoriteButton`) | 목록/상세 내 액션 | **버튼을 누른 시점** |
| 검색조건 저장/불러오기/삭제(`SearchPresets`) | 검색 화면 내 액션 | **저장/삭제를 누른 시점** |
| 등기부 신청 · 다운로드 | 상세 내 액션 | 액션 시점 |
| 구독 · 결제 | 상세 내 액션 | 액션 시점 |

- 인증이 필요한 액션은 **화면 진입을 막지 않는다.** 액션을 누른 시점에만
  `/login?redirect=<현재 URL 전체>`로 보내고, 로그인 후 **검색조건(쿼리스트링)을 잃지 않고**
  원래 위치로 복귀한다. 이 동작은 이미 구현되어 있으므로 그대로 유지한다
  (`FavoriteButton.currentSearchUrl()`, `SearchPresets.redirectToLogin()`).
- 비로그인 상태에서도 검색 화면에는 즐겨찾기 버튼과 검색조건 저장 UI가 **보인다**(숨기지 않는다).
  누르면 로그인으로 유도한다.

## 2.4 상세 화면(`/properties/[id]`) 접근 정책 — 확정 (2026-08-10)

**로그인 필수.** 더 이상 미결정 항목이 아니다.

- 비로그인 사용자가 **목록까지 보는 것은 허용**한다.
- 비로그인 사용자가 **검색 결과에서 물건을 클릭하는 순간 로그인으로 이동**한다.
- 게이트는 `src/middleware.ts`의 기존 `/properties/*` 검사를 **그대로 사용**한다(새 게이트 추가 없음).
- 로그인 후에는 **원래 이동하려던 상세 URL(쿼리스트링 포함)로 복귀**해야 한다.
  현재 `middleware.ts`가 `pathname`만 넘겨 `?ids=&i=`(목록 내 이전/다음 물건 컨텍스트)를 버리는 것은
  결함이며 수정 대상이다 — `docs/FRONTEND_MASTER_SPEC.md` §3.4 · §13(#2) 참고.

전체 Frontend 관점의 인증 경계는 `docs/FRONTEND_MASTER_SPEC.md` §3이 최상위 기준이다.

# 3. 화면 레이아웃 원칙

## 3.1 중앙 컨테이너 / 최대 폭

- 모든 콘텐츠는 **브라우저 중앙에 정렬된 단일 컨테이너** 안에 배치한다.
- 최대 폭은 **1320px**로 고정한다. (기존 `/search`가 이미 쓰던 값을 그대로 표준으로 채택 —
  새 값을 만들지 않는다.)
- 컨테이너 규칙: `max-w-[1320px] mx-auto` + 좌우 패딩(모바일 16px / 데스크톱 32px).
- **헤더도 동일한 컨테이너 기준으로 정렬한다.** 헤더의 배경(흰 배경 + 하단 보더)은 화면 폭 전체로
  깔되, 헤더 **내부 콘텐츠**(서비스명 / PrimaryNav / 로그인·로그아웃)는 같은 1320px 컨테이너에
  맞춘다. 그래야 헤더의 좌측 끝과 본문의 좌측 끝이 한 줄로 맞는다.
- 컨테이너보다 넓은 여백을 만들지 않는다. 콘텐츠를 화면 전체 폭으로 늘리지도 않는다.

## 3.2 세로 구조 (첫 화면)

```
┌──────────────────────────────────────────────┐
│ Header (풀블리드 배경 / 내용은 1320px 정렬)   │
│  콕찰 · 경매 물건 검색   [검색][최근][관심] [로그인/로그아웃] │
├──────────────────────────────────────────────┤
│ ▼ 1320px 중앙 컨테이너                        │
│ ┌──────────────────────────────────────────┐ │
│ │ 검색 Form  (핵심 영역)                    │ │
│ │  주소 / 법원 토글                         │ │
│ │  물건정보 · 가격조건 · 일정/유찰 · 면적 · 특수 │ │
│ │  [초기화]            [검색]               │ │
│ └──────────────────────────────────────────┘ │
│  검색조건 저장(SearchPresets)                 │
│  정렬 바(SortBar) + 총 N건                    │
│ ┌──────────────────────────────────────────┐ │
│ │ 검색 결과 / 경매 물건 목록 (ResultList)    │ │
│ └──────────────────────────────────────────┘ │
│  페이지네이션(Pagination)                     │
└──────────────────────────────────────────────┘
```

- 검색 Form과 결과는 **같은 페이지에 세로로 이어진다.** 결과를 위한 별도 화면/모달을 만들지 않는다.
- 검색 실행 후에도 사용자는 **위로 스크롤하면 그대로 검색 Form**을 다시 볼 수 있다.

## 3.3 반응형 원칙

브레이크포인트는 Tailwind 기본값을 그대로 쓴다(`md` 768px / `lg` 1024px / `xl` 1280px).

| 폭 | 검색 Form | 결과 목록 |
|---|---|---|
| < 768px (모바일) | 현재와 동일한 1열 아코디언 | 카드 1열 |
| 768 ~ 1279px | 아코디언 섹션 2열 배치 | 카드 2열 |
| ≥ 1280px | 아코디언 섹션 3열 배치 | 카드 3열 |

- 데스크톱에서 **입력 필드 하나가 1320px를 가로지르지 않게** 한다(P4의 직접 원인).
- 아코디언 섹션의 열 배치는 **레이아웃(컨테이너 클래스)만** 바꾸는 것이며,
  각 섹션의 필드 구성 · state · `buildSearchQuery()` 결과는 변경하지 않는다.
- 데스크톱에서 검색조건 영역의 기본 열림 상태는 조정할 수 있으나(밀도 확보 목적),
  **필드 자체를 추가/삭제하지 않는다.**

## 3.4 목록 표현 방식

- **1단계(현행 범위)**: 기존 `ResultList`의 카드(`ResultItemRow`)를 그대로 재사용하고,
  데스크톱에서만 그리드 열 수를 늘려 밀도를 확보한다. 카드 내부 정보 구성은 변경하지 않는다.
- **2단계(범위 밖 / 후속 결정)**: 탱크옥션식 표(table) 뷰. 정보 밀도는 더 높지만
  카드/표 이중 구현이 되므로, 도입 여부는 별도 결정 후 진행한다. 이번 범위에서는 만들지 않는다.

# 4. 검색조건 영역 (기존 구현 유지)

`src/app/search/SearchForm.tsx`에 이미 구현된 조건을 그대로 사용한다. **재구현 금지.**

| 그룹 | 조건 | API 연동 |
|---|---|---|
| 주소/법원 (토글) | 시/도, 시/군/구, 읍/면/동, 세부주소 · 법원 | `sido` `sigungu` `dong` `address_detail` `court_name` |
| 물건정보 | 사건번호(연도+타경+번호), 진행상태, 물건종류(트리, 다중선택) | `case_no` `status` `property_type`(콤마 join) |
| 가격 조건 | 감정가, 최저입찰가, 감정가 대비율 | `min/max_appraisal` `min/max_bid_price` `min/max_bid_rate`(%÷100) |
| 일정 · 유찰횟수 | 매각기일 범위(+당일/+7/+14/X 퀵버튼), 종결물건 포함, 유찰횟수 | `auction_date_from/to` `include_closed` `min/max_fail_count` |
| 면적 조건 | (준비 중) | 백엔드 미지원 — `auction_item`에 대응 컬럼 없음 |
| 특수조건 | (준비 중) | 백엔드 미지원 |

- 시/군/구 목록은 `GET /api/v1/search/regions?sido=`로 실시간 조회한다(하드코딩 아님).
- 면적/특수조건은 백엔드 미지원 상태이므로 "준비 중" 표기를 유지한다.
  **UI 재정의 과정에서 이 두 섹션을 임의로 활성화하지 않는다.**
- 검색 실행 시 정렬(`sort_by`/`sort_order`)과 페이지 크기(`size`)는 유지하고
  `page`만 초기화하는 현재 동작을 유지한다.

# 5. 검색 결과 영역

## 5.1 위치

- 검색 결과는 **검색 Form 바로 아래**, 같은 페이지 안에 표시한다.
- 검색 실행은 URL 쿼리스트링 갱신 → 서버 컴포넌트 재렌더 방식(현행)을 유지한다.
- **검색 실행이 다른 경로로 이동해서는 안 된다.** `/`에서 검색하면 `/`에 머물고,
  `/search`에서 검색하면 `/search`에 머문다(현재 URL 기준 push).

## 5.2 표시 항목 (현행 유지)

결과 목록에는 아래 정보를 표시한다.

- 사건번호 (+ 물건번호)
- 물건종류
- 소재지 (+ 면적 파싱값)
- 감정가
- 최저입찰가
- 최저가율
- 진행상태
- 유찰횟수
- 매각기일 (+ D-day 배지)
- 담당법원
- 즐겨찾기 버튼
- 조회수 — **미지원**(`auction_item`에 컬럼 없음, `-` 표기 유지)
- 대표 이미지 — **미지원**(이미지 컬럼 없음. 빈 placeholder를 두지 않고 텍스트 정보에 공간을 준다)

총 건수(`총 N건`)와 현재 페이지(`N/M페이지`)를 결과 상단에 표시한다.

## 5.3 결과 없음 / 오류

- 결과 0건: "검색 결과가 없습니다" (현행 유지). **검색 Form은 그대로 화면에 남는다.**
- API 오류: 오류 메시지를 결과 영역에만 표시하고, 검색 Form은 계속 사용 가능해야 한다.

# 6. 정렬

지원 항목 (`SORT_COLUMNS` 화이트리스트)

- 매각기일 / 감정가 / 최저입찰가 / 유찰횟수 / 감정가 대비율 / 사건번호 / 소재지

ASC / DESC 지원. 화이트리스트에 없는 값은 백엔드가 400으로 거부한다.
정렬 변경은 검색조건을 유지한 채 URL만 갱신한다(현행 `SortBar` 유지).

# 8. 기존 API 재사용 원칙

| 기능 | 엔드포인트 | 인증 | 비고 |
|---|---|---|---|
| 검색 | `GET /api/v1/search` | 선택적 | 응답/파라미터 변경 금지 |
| 시군구 목록 | `GET /api/v1/search/regions` | 불필요 | |
| 물건 상세 | `GET /api/v1/item/{id}` | 선택적 | 화면 게이트는 §2.4 미결정 |
| 즐겨찾기 | `POST/DELETE /api/v1/favorites` | 필요 | Error Code로 분기(문구 분기 금지) |
| 최근조회 | `GET /api/v1/recent-items` | 필요 | |
| 검색조건 저장 | `GET/POST/DELETE /api/v1/search-presets` | 필요 | |

- 위 엔드포인트의 **경로 · 파라미터 · 응답 구조를 변경하지 않는다.**
- 화면 재구성 과정에서 새 검색 API를 만들지 않는다.
- 클라이언트 호출은 `src/lib/api.ts`의 기존 래퍼(`fetchJSON` / `fetchAuthedJSON` /
  `postJSON` / `deleteJSON`)만 사용한다.

# 9. 구현 순서 (v0.2 UI 재정의)

기존 STEP 1~7(검색 UI → DTO → API → SQL → 결과 → 정렬 → 페이지네이션)은 **완료 상태**다.
v0.2는 아래 순서로 진행한다.

## STEP A — 첫 진입 경로 정상화
`/`가 검색 화면을 렌더링하도록 하고 redirect를 제거한다. `/search`는 계속 동작해야 한다.

## STEP B — 검색 실행 경로를 현재 URL 기준으로 변경
`SearchForm` / `SearchPresets`가 `/search` 하드코딩 대신 현재 pathname으로 push한다.

## STEP C — 중앙 컨테이너 · 헤더 정렬
공용 헤더와 1320px 컨테이너 규칙을 적용한다.

## STEP D — 반응형 밀도
검색 Form 섹션과 결과 카드의 데스크톱 열 배치를 적용한다.

각 STEP 완료 후 타입체크 · 빌드 · 실제 화면 확인을 거치고 다음 STEP으로 넘어간다.

# 완료 기준

□ `localhost:3000` 접속 시 로그인으로 redirect되지 않는다
□ 첫 화면이 경매 물건 검색 화면이다
□ 비로그인 상태에서 검색조건 입력 → 검색 실행이 가능하다
□ 검색 결과가 같은 페이지 하단에 이어서 표시된다
□ 첫 로드(조건 없음) 상태에서도 물건 목록이 보인다
□ 헤더와 본문이 같은 중앙 컨테이너(1320px) 기준으로 정렬된다
□ 데스크톱에서 좌우 여백이 과도하지 않고 입력 필드가 화면을 가로지르지 않는다
□ 모바일/태블릿/데스크톱에서 레이아웃이 깨지지 않는다
□ 비로그인 상태에서 즐겨찾기/검색조건 저장을 누르면 로그인으로 유도되고, 로그인 후 검색조건이 유지된 채 복귀한다
□ 정렬 / 페이지 이동 / 페이지 크기 변경이 기존과 동일하게 동작한다
□ 기존 기능 정상 · 오류 없음 · 테스트 완료
